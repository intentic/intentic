# @intentic/ui

Shared **Vue UI primitives + theme** for the platform web app. A small, reusable layer on top of PrimeVue + Tailwind 4 that [`@intentic/web`](../../_editor/web) composes: layout containers, a code/markdown primitive, the dark/light theme composable, and the design tokens.

## Responsibilities

- Provide primitives: `Page` (centered, width-constrained shell), `Card`, `ScrollFrame` (the bordered pane, which either scrolls its own body or, with `:scroll="false"` and `:sticky`, is sized by the whole of its content and pins only its header while the page behind it scrolls), `Code` (Shiki-highlighted block), `CodeField` (the same colours with a caret in them, the editable source surface), and `InfoHint` (hover/focus info card).
- Own theming: `useTheme` (dark/light `ColorScheme` + the accent colour, both persisted) + `installUi(app)` (the single design-system plugin: PrimeVue preset + cssLayer order + tooltip directive) + the `Theme` preset.
- Own the app's colour: the reader picks ONE, with `ColorPicker`, and `themeColor.ts` expands it into the twelve-step brand and neutral ramps every surface, border, link and fill resolves through, written as inline custom properties on `<html>`, so the whole UI repaints without a rebuild. The step LIGHTNESSES are fixed (they are what the contrast promises in `semantic-colors.css` are made of); a picked colour sets hue everywhere and how much chroma the ladders carry.
- Own how large the app reads: `useTextSize` (persisted, `compact`/`default`/`large`). Because every size in the tokens is a rem, this one knob moves type, spacing, control heights and radii together, `default` is the 110% the interface is drawn at, so a fresh window needs no browser zoom. It also publishes `--ui-scale`, which anything that must NOT grow divides by (the web app's navigation rail) and anything that paints its own text multiplies by (Monaco, xterm).
- Own the one markdown surface: `Markdown` renders sanitized prose, Shiki-coloured fenced blocks, and the fences that are FIGURES rather than code, `dag`/`bars`/`stats`, whose bodies are JSON the app lays out, and `mermaid`, which mermaid itself draws (lazily imported, in the app's own palette). A fence the renderer cannot understand stays a code block, so a broken figure costs itself and not the page. The engine renders a document as PARTS (prose runs plus the figures between them), which is what lets a surface with its own rendering, the chat transcript, which splits a live turn into a settled prefix and a still-writing tail, draw the same figures without giving up the split. The two heavy renderers load on demand: mermaid on the first document that holds a diagram, the graph canvas (Vue Flow + dagre) on the first that holds a `dag`.
- Own the one markdown surface people WRITE on, which is the same picture with a caret in it: `MarkdownDocument`. Displaying is always the rendered document; opening an editor is clicking the words, and the caret lands where you clicked; the block you are in reveals its own `##` and `- ` in the margin so nothing shifts; saving is one of two declared policies (`auto` for a document that IS the file, `explicit` for one every turn reads before it starts) behind one status line, one Ctrl-S and one flush on the way out. It exists because nine places in the product let somebody author a markdown document an agent then reads, and they had agreed on nothing: five ways of displaying one, six ways into an editor, four save policies, three vocabularies for saying which. The engine under it is `MarkdownDocumentSurface`, a `contenteditable` whose text IS the file (`sourceDom.ts` builds it, `edits.ts` is the formatting keys and list continuation as pure functions, `history.ts` is the undo stack the browser's cannot replace here) — deliberately NOT exported, so there is one public answer rather than two. On a phone the component falls back to `CodeField`, which is what that component is now for.
- Own the LIST ROW, in both of its states: `RowGroup` + `Row` (an optional lead mark, a title and description, a trailing cluster of facts and one of actions, at three density tiers), and `DisclosureRow` for the row that OPENS. The second one is why the first is worth naming here: fourteen lists across the app and six extensions had each built an expandable row alone, and between them they spelled the chevron five ways (two icon names swapped, `chevron-right` rotated 90°, `chevron-down` rotated 180°, and an `(i)` that toggled thirty pixels under an `InfoHint` whose `(i)` does not), indented the opened block to `pl-5`/`pl-8`/`pl-9`/`pl-10`, painted the open row four different colours, and got `aria-controls` onto two rows out of fourteen. The component owns the glyph, the hit area, the ARIA, the open wash, and the indent of the block beneath, which it DERIVES by drawing the row's own lead cluster a second time and hiding it, so no call site can spell that distance as a number again.
- Own every box that OPENS: `Modal` (the app's one centred dialog, in four named sizes plus `full`, each token carrying its own viewport clamp, `ConfirmDialog` and `InfoDialog` are built on it), `AnchoredOverlay` (a panel pinned to a trigger, placed against the window that trigger is in) and `ResponsiveOverlay` (the same panel, a bottom sheet on a phone, behind one open flag). Nothing outside the kit should reach for PrimeVue's `Dialog` or `Popover`: both measure against the module-scope `window`, which is the wrong one in a popped-out panel.
- Own the one way the app says something went wrong: `Notice`, a tinted box with an icon, an ARIA role and at most one action, taking either a `NoticeModel` (a failure turned into a sentence) or a slot (a message the view wrote as markup). `NoticeStack` ranks several by severity and collapses repeats.
- Own the two shapes an extension screen turns out to be twice: `NoteEditor` (one markdown note, read and curated, the Copy/Edit/Delete cluster, the in-place delete confirmation, and the one surface a file is both read and written on) with `useNoteDraft` behind it and `useKeyedDraft` above it (the unsaved edits, kept per note, because the pane is reused as the selection moves), and `RepoRail` (the narrowing "which repository" column, with the pinned "all" row and the same rail folded into a `Picker` once the split is too narrow). Knowledge and the pane before it had built the first twice; Maintenance and Pipelines the second, and in both pairs the copies had already drifted. Pipelines has since moved its choice into the top bar's `Picker` outright, because its body is a job graph and the column was costing the diagram the width it needed; the rail is Maintenance's, where the report always carries the workspace root alongside.
- Provide `vTw` (the `v-tw` Tailwind class-merge directive), `ui` (the Tailwind class recipes: `ui.input()`, `ui.sectionLabel()`, `ui.iconButton()`) and `useHighlighter` (the shared Shiki highlighter).
- Own what one COMPUTER's sandboxes look like, because two apps draw them: `DeviceDetail` (one row per sandbox, its folder, its localhost ports — or the fact that this computer was told to keep them off its localhost, which is the one state an empty port list cannot be read as — its image, its share of the machine, its container's state), `SandboxVerbs` (which buttons that row has, in which order, in which words, and which single one is red), `SandboxResourcesDialog` (the form behind the row's Resources… verb: the memory and CPU caps against the engine's rails, the privileged and GPU switches with the ones the approved environment demands drawn locked, and the restart that applying costs; its arithmetic is `sandboxResources.ts`, also on the `@intentic/ui/sandbox-resources` subpath so its tests need no DOM) and `DeviceRunLog` (the machine's own output under a row that is working). The web app's Devices tab and the desktop app's manager window manage the same containers on the same machine, and every one of the first three began as one app's copy that the other then diverged from, a log tail here and a Restart there, one card list drawn twice, two different sentences asking about the same deletion. The callers keep only what genuinely differs: how a click reaches that machine, and for the form, only the container's current share and the engine's size, which they hand over and forward the answer of unread.
- Own the one button that starts an agent for you: `AgentRunButton`, a split button whose primary half runs on the sandbox's standing model FOR THAT JOB (the caller names its role: a pipeline fix and a documentation sweep are the same button and not the same spend) and whose caret re-points that single run — the model, the tier it thinks at, whether it reasons first, which account pays and whether the work is bought at the faster rate — plus `useAgentRunPick`, the state behind it. Seven surfaces press it (both Fix buttons, Maintenance, Documentation, Acceptance, a deployment incident and a failed pre-push check), and before it existed each had reached a different answer about how you choose what a click spends. **Both halves emit the same `run`**: the panel the caret opens ends in a bar carrying this button's own label, so configuring a run and starting it are one press rather than a dismissal followed by a second click. It takes the picker WHOLE (`:picker="fixModel"`) rather than the four values derived from it, because a row that named one picker's model above another picker's caret looked entirely correct while lying about what a click would spend. The picker itself is NOT here: it is a live read of connected accounts and catalogs, so the caller passes it in as `ModelPicking` and the kit stays free of both the app's state and the extension API. A button standing beside a fix that already exists hands the picker that attempt too (`useAgentRunPick`'s third argument, an `AgentRunAttempt`): the panel's bar then names it and ends in **Continue** / **Start over** instead of the button's own label, and the verb pressed comes back as `resume`, because with an attempt on the table the press is a decision about that attempt and a bar saying "Fix with agent" over an agent that already tried is how a second press once silently resumed a session the reader believed they were replacing. How each attempt's state is drawn (icon, tint) is `fixStanceLook`, keyed by the contract's `fixStance` kinds, so a chip beside a red pipeline row and the one on the push question wear the same look for the same state.
- It is **presentational/shared only**: no app state or data fetching.

The shared `Icon` uses Intentic's own Khmer-inspired pack: square line ends, cut corners, lotus points,
and clear interiors at small sizes. [iconSets.ts](src/icons/iconSets.ts) owns the semantic names and the
section-to-icon mapping. The source drawings are grouped by navigation, actions, objects and states in
`src/icons/*Glyphs.ts`. The native [Icon](src/components/primitives/Icon.vue) binds their paths directly;
there is no icon package, generated collection, registration step or icon API request. [glyph.ts](src/icons/glyph.ts)
serializes the same drawings for Mermaid's `intentic:name` icons. Vendor marks retain their recognisable
artwork, stored locally with their [license](src/icons/REMIX-LICENSE.txt). New icons should express their purpose with
a distinct silhouette, without adding decoration inside a small control. Row lead marks have a 16px floor
and use the muted text colour, with the selected navigation mark taking the active accent. `Row` and
`DisclosureRow` pass `iconClass` alongside `mark` to custom lead slots, so selection checkboxes and icons
can share a column without the icons losing their tier's size.

The [versioned dependency patches](patches/README.md) make PrimeVue's fallback controls use the globally
registered native `Icon` and replace Mermaid's icon utilities with native SVG. The matching dependency
overrides remove the unused icon packages from the lockfile. Keep these patches in step with library upgrades.
Monaco's patched stylesheet also uses these drawings as SVG masks; editor symbols live beside the rest of
the pack in `editorGlyphs.ts` and its bundled icon font is not loaded.

## Key files / exports

- [src/index.ts](src/index.ts), the public surface, and the kit's own map: nearly every export carries a note saying what it replaced and why it exists. Read this before adding a component; the thing you want is usually already here under a name you did not guess.
- [src/components/](src/components): the `.vue` components, in one directory per KIND — `layout/` (page, card, rails, split view), `charts/` (bars, DAGs, mermaid, stat strips), `forms/` (pickers, fields, filter and search bars), `feedback/` (notices, badges, skeletons), `overlays/` (modal, dialog, context menu, anchored overlay), `rows/` (the row tiers), `sandbox/` (the device and sandbox surfaces the app embeds), `brand/` (avatar, mark, persona face), `markdown/` (the two document surfaces) and `primitives/` (button, icon, code, copy). Each component keeps its optional plain-TypeScript sidecar of the same name in camelCase beside it (`Picker.vue` + `picker.ts`) holding its types and pure logic, so a unit test can reach them without booting a DOM.
- [src/markdown/](src/markdown), the engine behind both of those surfaces, on the `@intentic/ui/markdown` subpath because it is plain TypeScript. Reading: `render.ts` (sanitize, the document's parts, and the streaming split), `code.ts` (fenced blocks), `figures.ts` (which fences are figures). Writing: `blocks.ts` (where each block SITS in the source, in spans that tile the document, so an edit can be read back and spliced in without disturbing a byte of the rest), `sourceDom.ts` (the block as an element whose text IS its source, markup included), `edits.ts` (the formatting keys and Enter-on-a-list as functions from text+selection to text+selection), `history.ts` (the undo stack, because rebuilding a block is a programmatic DOM write and drops the browser's own). This package runs no suite of its own, so all four are exercised from `_editor/web/src/design-system/markdown*.test.ts`, which is where `blocks.ts`'s tests already lived.
- [src/lib/](src/lib), everything that is plain TypeScript rather than a component or a composable: the colour maths (`oklch.ts`, `themeColor.ts`, `brandColor.ts`), `format.ts`, `path.ts`, `timeWindow.ts`, `ui.ts` (the class recipes), `anchorPlacement.ts` (where an anchored box goes, measured against the anchor's own window), the `tooltip.ts` directive, and `styleStability.ts` (`stabilizeStyleWrites`, the guard that keeps a `<style>` from being replaced by a write carrying the bytes it already holds — see the gotcha below). Most of these also ship as their own subpath export, so a node-environment test can import one without the component barrel.
- [src/plugin.ts](src/plugin.ts) (`installUi`) and [src/composables/](src/composables), `use*` composables ONLY, which is the rule: `useTheme` (scheme + accent refs, persistence, and the inline custom properties that carry the accent), `useTextSize` (also on the `@intentic/ui/text-size` subpath, so plain modules can ask how large the app is without booting the component graph), `useHighlighter` (lazy Shiki core; also on `@intentic/ui/highlighter`). Anything here that is not reactive state belongs in `lib/`.
- [src/styles/](src/styles): design tokens + `theme.ts` (the `Theme` preset that bridges Tailwind vars ↔ PrimeVue `--p-*`), PrimeVue overrides (`@layer primeng`), semantic colors. `index.css` is the whole design system in one import; `opt-in/` holds the three sheets only some consumers pay for (`prose.css`, `markdown-editing.css`, `extension-surface.css`). The first two are the two halves of one surface and are imported together: `markdown-editing.css` adds no type rules of its own, it only hides the markup a `MarkdownDocument` is holding, hangs a block's opening markers in the gutter and lights the block under the caret, so an app with one sheet and not the other shows an editor with every `##` on screen.

## How it fits

Consumed by the web app: `installUi(app)` runs once in `main.ts`; components import `Card`/`Page`/`Code`/`InfoHint` and use `useTheme` for the scheme toggle, `useHighlighter` for code, `v-tw` for conditional classes.

Also consumed by the [desktop app](../desktop-app), which is the reason a few of these components exist at all: it renders the same machine as the web app's Devices tab, from a different process, against a different backend.

## Conventions & gotchas

- `<script setup lang="ts">` SFCs + composables (module-level `ref` singletons), same as the web app; keep it free of app-specific logic so it stays reusable.
- The CSS cascade layer is named `primeng` (`installUi`'s `cssLayer.name` + `styles/primeng.css`): keep that name so `utilities` stays last and Tailwind utilities beat PrimeVue component styles.
- Semantic CSS variables (`--color-*`, `--radius-*`) are the styling contract: prefer them over hard-coded values. Consumed directly from source (no build step); `pnpm --filter @intentic/ui typecheck` runs `vue-tsc`.
- `CodeField` stacks a Shiki-highlighted `<pre>` and a transparent `<textarea>` in one grid cell, so every metric that can move a glyph is set once, in `styles/code.css` (`ui-code-field-box`), and applied to both. Split those two class lists and the text drifts off its own colours: silently, and only on the lines that wrap.
- **A class Tailwind cannot SEE is a class that ships as nothing.** Never build one by interpolation (`` `bg-${tone}` ``, `` `text-${size}` ``): write every variant out, or put it behind `@theme static`. This is the failure the series palette records in `semantic-colors.css`, and it is silent, the element simply renders unstyled.
- **Everything is on a scale, and off-scale is not an option for extensions.** `extension-surface.css` promises a class SURFACE to extension bundles and cannot enumerate arbitrary values, so a kit component drawn at `text-[0.65rem]` renders at a size no extension can match. Reach for `text-3xs`/`text-4xs`, `w-modal-*`, `max-w-read*`, `h-panel*`: and if the scale has no step for what you need, add one rather than an arbitrary value.
- **A screen scrolls in ONE place, and which place is the surface's decision rather than the pane's.** `SplitView`'s `scroll` prop names it: `panes`, where each column scrolls inside a clamped band, or `page`, where the shell's scrollport takes the whole screen and the columns hold their place with `sticky`. Running one contract inside the other is the bug that keeps coming back, and it is silent: a section written for `panes` inside a `page` hub puts a scrollbar in a card in a page, on a scrollport that has nothing to scroll. Two composables carry the parts `sticky` cannot. `useStickyTop` measures a pinned bar and publishes its height as `--pinned-top`, so everything pinning below it clears the same number instead of a `top-11` that is only right at one width. `useScrollReset` returns the scrollport to the top when the selection changes, which a clamped pane used to get for free from its own remount, and without which arrowing down an index four screens into one document lands you four screens into the next.
- **An identical stylesheet write is not free.** Assigning `style.textContent` replaces the element's text node whether or not a byte differs, and the browser answers by tearing the stylesheet down and building a new one: the document repaints, and DevTools rebuilds its Styles editor, which closes an open colour picker mid-drag. Two writers do it constantly and neither can be told not to — PrimeVue reloads its directive styles from every `updated` hook, and Vite's dev client re-pushes the ~900 KB Tailwind sheet on every source save because Tailwind watches each scanned file. `stabilizeStyleWrites(selector)` puts the guard on the element instead: identical assignment dropped, anything else through. `installUi` claims PrimeVue's nodes with it, the web app's dev-style manifest claims Vite's (`_editor/web/vite.shared.ts`).
- **There is a gallery.** `/kit` in the dev server renders every component in every state and every scale as a ruler. Open it before adding a component, and after changing one: it is the only place two look-alike parts sit side by side, which is where drift becomes visible.
