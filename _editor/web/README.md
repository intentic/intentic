# @intentic-app/web

The **Vue 3 SPA** (Vite + PrimeVue), the platform's workspace UI. A user signs in with Google, connects a sandbox, and then drives that sandbox's daemon **directly** over its own tunnel (authenticated by a renewable daemon session established from Google identity): chat with the Claude agent, browse the workspace, edit inventory, run infra plan/provision, and view topology + deployments. The platform API it talks to is thin, only sign-in (Better Auth) + the `setup.*` handshake (mint token, store the sandbox's URL); everything else is browser→sandbox-direct. Talks to [`@intentic-app/api`](../../_platform/api) via the oRPC client + to the sandbox daemon via `sandboxRequest`; shares types through [`@intentic-app/api-contract`](../../_platform/api-contract) and primitives through [`@intentic/ui`](../../_editor/ui). Dev server (Vite) on :47145; the SPA calls the API directly at `API_URL` (`https://localhost:6480` in dev, CORS-enabled), the base URL comes from the runtime `window.env` in [src/environments](src/environments), not relative paths.

## Responsibilities

- Render the post-login workspace shell, the page areas, and the persistent chat panel.
- Hold client state in composables (module-level `ref` singletons); fetch request/response data via **TanStack `@tanstack/vue-query`**; talk to the **platform** via the typed oRPC client (sign-in + `setup.connect`) and to the **sandbox daemon directly** via `sandboxRequest` (a Bearer daemon session, no cookies); consume the daemon's SSE/ndjson streams manually.
- Drive auth (Google sign-in via Better Auth), the setup gate, and the browser-direct workspace surface (chat, infra, inventory, deployments).

## Layout

- **[src/composables/](src/composables)**: module-level singletons + vue-query wrappers:
  - `useAuth.ts`: the reactive Better Auth session, cross-tab sign-in/out, profile + account deletion. Guards live in the router.
  - `useApi.ts`: the oRPC `ContractRouterClient` singleton; the platform surface is just `setup.*` (+ `me`).
  - `sandbox/useSandbox.ts`, the browser's sandbox state: `daemonUrl` (from `setup.binding`) + exact transport/action gate `reachable` (the live SSE probe in `useSandboxLiveness.ts`); the browser alone judges liveness. `sandbox/availability.ts` and `sandbox/useSandboxAvailability.ts` separately project that transport truth into `starting` / `warming` / `live` / `stale` / `busy` / `blocked` presentation states: established workspace views stay mounted through transient retries, short stalls remain visually online, and only a stall lasting 30 seconds earns a compact non-modal busy notice.
  - `useGoogleIdentity.ts`, Google Identity Services: mints the Google ID token, cached until it expires. ONE
    credential with two consumers: the daemon (which verifies it against Google, never against the platform) and
    the platform's own sign-in, which `Login.vue` establishes from the same mint. That is what removed the second
    Google prompt people used to meet right after signing in. Only the browser can produce it, so the direction is
    fixed: it goes out to both, and neither hands one back.
  - `sandbox/sandboxSession.ts` + `sandbox/sandboxAuthFetch.ts`: establish and renew the per-daemon bearer session, synchronize it across tabs, and give every client the same one-retry recovery after an authoritative 401. Only a call somebody is waiting on may ask Google for anything: a background reader spends the proof already in hand and takes "no" for an answer, and even a foreground call checks the daemon is answering before it raises a sign-in on that daemon's behalf.
  - `sandbox/sandboxClient.ts`, the browser→daemon-direct client (`sandboxRequest`/`sandboxJson`/`sandboxBlob`): snapshots one sandbox target and uses the shared authenticated-fetch policy for `${daemonUrl}${path}`. `sandboxJsonAt` aims the same call at another sandbox by id; `sandboxJsonQuietly` does that for the pollers nobody is waiting on, which is what keeps a stopped machine in the account from raising a sign-in gate over the workspace on screen.
  - `useChat.ts` + `conversation.ts`: the Claude agent, daemon-direct (`/agent`, `/agent/decision`, `/agent/answer`, `/sessions`, `/claude/*`).
  - `useDeployments.ts` / `useWorkspaceState.ts` (+ `workspaceStateProjection.ts`) / `useInventory.ts` / `useWorkspaceTree.ts`: the read-model + inventory as **vue-query** queries/mutations against the daemon; `intenticStream.ts` is the shared `/intentic` ndjson reader; `renderMarkdown.ts` sanitizes marked output (DOMPurify) for `v-html`.
  - `useLayout.ts` (chat panel + explorer sidebar width/side. Every width here is in **app pixels**) pixels at the app's base text size (`useTextSize`), which is what they were measured at, so a column keeps the same number of characters when the reader makes the app larger. `uiScale.ts` owns the trip to and from screen pixels and names the only two edges that take it: the pointer, and anything handed to the platform (a pop-out window's size, an editor's font size).
  - `workspace/codeAnalysis.ts` + `codeAnalysisClient.ts`: one TextMate walk produces the comment-free view and import locations; a lazy dedicated worker runs it, and a small recent-result cache lets the background loader, code-only stats, and an opened diff share that work.
  - `prefetch/`, **the background loader**: one reader that keeps ahead of the user across the whole app, so a click paints from cache instead of paying a tunnel round trip. `backgroundLoader.ts` is the loop and the whole of the pacing policy (one read at a time, only in browser idle, a gap proportional to what the last read cost, stand aside while anything the user asked for is in flight, nothing at all while no window is on screen, quiet failure with a cool-off after a run); `warmPlan.ts` is the registry each surface contributes a wish list to, ordered by four bands that say how close the user is (`now` → `near` → `work` → `rail`) rather than by an importance number; `sources/` holds the app's own contributors, the workspace review's rows, the agent board's cards (transcript + changes), and the rail's view lists, and registration order is the tie-break within a band. **The workspace review leads, from every route.** It is where a clean turn's work ends up (landing writes the delta into the user's tree as uncommitted changes) and where the user commits from, and it is the one surface whose whole contents are dropped on a schedule the user does not control: a turn ending invalidates the change list and every diff filed under it at once. Behind the board it was therefore re-read last, precisely when it had just been emptied, so the panel was reliably cold when opened; ahead of it, a card on a busy board pays its round trip more often, which is the cheaper wait (a card opens onto a stream, a review opens onto ± numbers that are wrong until read). The same reasoning removes the double read after a landing: an agent's own review and the workspace review reach the same file through **different questions**, the agent's branch against the main line as it stands (what this conversation wrote that you have not taken yet, landed rows included, since a clean turn lands within ms of finishing) versus the main tree against `HEAD` split by staged/unstaged/conflicted, so they cannot share a cache entry, and `sources/reviewsToRead.ts` instead stops reading a `landed` agent's rows ahead and leaves that work to the workspace review (unless that agent's own page is open). Work HELD on the branch (`ready`, auto-land off) is still read ahead: no other review can reach it. Started for the signed-in session by `shell/WorkspaceRuntime.vue`, beside the daemon stream and for the same reason. Every wish reads through the SAME query its screen reads, so warmed and clicked are one cache entry; a wish carries `have()` so a satisfied plan costs lookups rather than requests.
  - `buildEpoch.ts` / `selfHeal.ts`, why a stale browser never needs "clear site data": every mirror this app persists is invalidated automatically (a new build busts the query-cache buster and drops the transcript store; a replaced workspace sweeps that sandbox's remembered tabs/terminals/drafts via `sandbox/systemEventRouting.ts`), and a crash inside the startup window wipes the origin's storage and reloads once.
  - `clientDiagnostics.ts`, the app's only durable account of itself. Everything this app caught or measured used to end at the console: the perf ring buffer dies on reload, a render error reaches Vue's handler and stops, and the self-heal above *clears this origin's storage and reloads*, destroying the evidence for the bug class that reproduces least often. So when someone hit a bug in their own browser the record was nothing, and the only way to investigate was to re-drive a browser and hope, which across 728 real sessions meant 1,545 screenshots against 65 reads of a console and a quarter of all prompts arriving with a picture attached. Render errors, script errors, unhandled rejections, self-heal wipes and slow spans now post to the daemon's `POST /logs/client`, which appends them to `logs/client.jsonl` where the sandbox's diagnostic tools read them. Three rules, in this order: it never throws (its callers are an error handler and an unload hook), it never blocks (batched, fire-and-forget), and it never grows unbounded (identical reports coalesce to a count, the queue has a ceiling, a failed post drops the batch rather than retrying). The flush is `keepalive`, which is the load-bearing detail rather than a nicety: the two moments most worth reporting are a wipe-and-reload and a closing tab, and an ordinary fetch on either is cancelled with the page.
  - `extensions/`, the extension/capability data layer: `useExtensions.ts` (installed manifests from `GET /extensions`, `contributionOf(kind, id)` for a card's contribution, `enabled` for the extensions actually wired up, `settled` for load-gated decisions) and `useCapabilities.ts` (capability list + the streamed add + remove/secret mutations).
- **[src/extension-host/](src/extension-host)**, the real extension host: fetches `GET /extensions`, engine-checks and `import()`s git-installed bundles, activates the compiled-in first-party UI extensions (`builtins.ts`), everything through the manifest-gated `createExtensionApi` (`apiImpl.ts`).
- **[src/core-views/](src/core-views)**: the reactive runtime view registry the shell renders from, plus the three privileged *core* view contributions (`infrastructure`, `live-status`, `directory-ui`) that are extension-shaped but deliberately in-app. `registry.ts` also owns **what the rail shows and in what order**, for core tiles and extension tiles in one table: the bands (Work · Judge · Set up · Know) and, per id, whether it is `always` seated or seated only while it is **saying something**. Four tiles are permanent (Chat, Agents, Workspace, Preview: where you go, constantly); everything else, first-party and third-party alike, holds a seat while its badge is non-empty, while it is pinned, or while you are standing in it, and lives behind the rail's **More** menu the rest of the time. The scarce thing is seats, roughly nine above a 945px viewport, so a tile that can never tell you anything was spending one all day: this is the rule that evicted Memory and Activity to the sandbox hub, applied to every tile rather than to the two that were caught by it. Nothing became less reachable: More lists every area whether or not it is seated, each has a `view.*` command in the palette ([`composables/commands/useAreaCommands.ts`](src/composables/commands/useAreaCommands.ts)), and a right-click pins one back for good ([`shell/railPins.ts`](src/shell/railPins.ts)).
- **[src/shell/](src/shell)**, the persistent shell: `WorkspaceShell.vue` (rail | workspace | chat grid), `ShellDesktop`/`ShellMobile`, `AccountPanel.vue`, `GoogleSigninGate.vue`, `QuickOpen.vue`, plus the part that outlives it: `WorkspaceRuntime.vue` (mounted by `App.vue` for the whole signed-in session, the daemon's liveness stream, presence, and `PoppablePanels.vue`, the single chat + terminal + preview instances). The shell only lends those panels a place to dock (`dockSlots.ts`), so a route outside it (`/setup`) can't tear a popped-out window down.
- **[src/chat/](src/chat)**, the chat panel: `ChatPanel.vue` + its message view, tabs, and mode/provider menus. One instance with three exclusive homes: the side column, the rail (a Chat tile whose full-screen `/chat` area is the chat's only in-window surface, `pages/ChatArea.vue`; the user's choice between these two persists as `useLayout.chatHome`), or its own pop-out window. Which form the panel wears is derived from where it is actually drawn (`composables/chat/chatSurface.ts`). **The pop-out window earns one thing the other two homes do not**: a headroom rail down its right edge ([`ChatCapacityRail.vue`](src/chat/ChatCapacityRail.vue)), which subscriptions still have room and how much, so "what can I start next" is answerable without leaving a window that has no shell around it. It appears only in width no pane can use — the transcript stops widening at its reading measure, and that surplus and only that surplus is what the rail takes ([`chatCapacity.ts`](src/composables/chat/chatCapacity.ts), `railFitsBeside`) — and it lists offers rather than accounts: a spent pool, a dead credential or a standing refusal holds an account off it, and a provider with nothing left is named underneath with the instant it comes back, because an absent row otherwise means both "spent until Sunday" and "never connected". **The eight cards that ask the user something** — a plan, a question, a permission prompt, the browser and terminal help asks, the service, payment and capability offers — are one shell ([`ChatCard.vue`](src/chat/ChatCard.vue)) rather than eight hand-written copies of the same four lines of markup, which is what they had drifted into being: three different header tiers and two different opinions about a divider, across cards a user answers in the same turn. Each supplies its own body and its answers; how it says it is settled is [`cardStatus.ts`](src/chat/cardStatus.ts), one function per card instead of a chain of `v-if` spans inside the template. **The permission card is the one with real work in its body** ([`ChatCommandBlock.vue`](src/chat/ChatCommandBlock.vue)): a held command arrives as a program, not prose, so it is syntax-highlighted, and the daemon's own offsets say which fragment the rule stopped it for — [`commandPieces.ts`](src/chat/commandPieces.ts) merges those two rulers (a mark edge cuts the colour token it lands in, both halves keep the colour) the way `pages/workspace/searchSnippet.ts` already does for a search hit. Everything unmarked is dimmed rather than recoloured, so the grammar still reads while the eye lands on the mark. When the owner has switched on the quick model's plain-sentence pass, the sentence leads and the command folds behind a labelled disclosure — never a hover (no touch or keyboard equivalent, on a safety prompt) and never a tab — with the marked fragments staying on the card either way, because hiding the command may not hide the evidence for why it was held.
- **[src/sandbox-gates/](src/sandbox-gates)**: the sandbox connect/authorize gates and switcher wrapping the workspace surface. A full gate is reserved for blocked causes or a sandbox with no successful workspace snapshot; even an empty cached workspace remains mounted while transient failures recover automatically.
- **[src/presence/](src/presence)**: collaborator presence avatars/stack.
- **[src/push/](src/push) + [src/shell/](src/shell)**, how a notification reaches this device, and how the app knows when it is inside a native frame. One flow ([`composables/usePushNotifications.ts`](src/composables/usePushNotifications.ts)) over two transports behind one driver seam ([push/driver.ts](src/push/driver.ts)): every browser (the Play-store TWA included) is web push straight from the daemon ([push/webPush.ts](src/push/webPush.ts)); the iOS shell ([\_editor/ios-app](../ios-app)) has no web push, so [push/nativePush.ts](src/push/nativePush.ts) registers the APNs token with the platform's push relay and stores the grant on the daemon as its channel. [shell/capacitor.ts](src/shell/capacitor.ts) is the ONLY place the injected native bridge is named (no Capacitor dependency exists in this package) and [shell/notificationTaps.ts](src/shell/notificationTaps.ts) is the native twin of the service worker's click handler, turning a tapped notification into the in-app route it points at.
- **[src/skins/](src/skins)**, whole-interface looks, as opposed to the colour the accent picker sets: one stylesheet per skin, each scoped to a `data-skin` attribute on `<html>` and therefore inert until Appearance selects it. The one here, `sanctum.css`, is the marketing site's own design system worn by the app (ash stone with a whisper of tooth in it, one gold rule, a flat unlit shadow for the rail and the overlays, stone and bronze plaques for the two filled button tiers, eased corners, the site's type), and it works by restating the design system's surface ramp, role tokens and radius scale rather than by naming a thousand components. It keeps one rule that is worth reading the notes for: **every surface a word sits on is flat in the low frequencies and opaque**, so a gradient never lands under the reading, while a fine speckle, which has no low frequencies to vary, may. `useSkin.ts` owns the attribute, the preference, and the per-skin webfont fetched only while that skin is on. The directory is the whole feature: [its README](src/skins/README.md) lists the three call sites that reach it, so removing skins is deleting it and undoing three lines.
- **[src/styles/](src/styles)**, one sheet, and it is the **entry screens' material**: the marketing site's metals, ink, faces, carved display type, frame kit and two button plaques, scoped to `.entry` and therefore inert on every route but `/login` and `/setup`. Those two are the last stretch before the app's own look takes over — a visitor meets them within a minute of leaving intentic.dev, having picked no accent, no scheme and no skin — so they are dressed as the page they came from rather than as the workspace they have not seen. It lived inside `Login.vue` until `/setup` needed the same stone, which is the whole reason it is a file: the door and the room behind it share the material and differ only in composition. Two things in [its header](src/styles/entry.css) are worth reading before editing it — why it restates `--color-*` and never `--role-*` (a custom property's `var()` is substituted where it is *declared*, so re-pointing a role token from a descendant changes nothing), and why the radius scale is deliberately left alone. It is imported **after** the skin, and the skin excludes `.entry` from its route-element backdrop by name.
- **[src/pages/](src/pages)**, lazy-loaded areas: `Login`, `Setup`, `Sandbox`, `Infra` (topology + config/provision), `workspace/` (VSCode-like explorer + file viewer; **the editor area is two panes**, see below), `Capabilities.vue` (the rail's "+": static core cards merged with cards derived from ENABLED extensions' `contributes.capabilities`, a config form with a live "This will add to your sandbox" effects panel), `Secrets.vue` (the capability-secret inventory), and the `*Dialog.vue` overlays.
- **[src/preview/](src/preview) + [src/composables/preview/](src/composables/preview)**, the live app preview: an evidence-driven Preview rail tile whose one panel shows the real dev server (clickable, hot-reloading) full-bleed under a single toolbar strip, in the `/preview` area or a pop-out window on the chat's machinery. It previews five kinds of thing: a repository's dev server, one app inside a monorepo, a **forwarded port** (the answer for a server nothing here started), the workspace's served `public/` page, and **any address the user types**, because a discovered list is a closed one. `previewModel.ts` is the pure half, what counts as previewable, which target the panel lands on unasked, and **the one list both the panel and the rail tile are built from**: the tile's badge previously used a second opinion about what counts, so a monorepo with no `_apps/` badged "1 running" over a panel saying there was nothing to preview. `usePreviewTargets.ts` wires it to the live `/panels`, per-monorepo `/apps`, `/ports` and `/public` reads; `previewSurface.ts` holds the panel's own existence, selection and typed address (once opened it stays mounted, parked behind its tile, so the previewed app's state survives every trip to the code). The workspace tree's per-repo eye routes here; the per-repo iframe tab it replaced (the preview extension's fallback directory view) is gone. **Nothing is framed until the address answers for itself**: the panel probes the daemon's preview proxy over a CORS-open path (`@intentic/ui` `portPreview.ts`, the daemon's `PREVIEW_PROBE_PATH`) rather than treating any settled request as reachable, because an address that reaches no sandbox still gets an answer, the edge's own 502, whose `X-Frame-Options` renders inside the iframe as a bare "refused to connect" with nothing to act on. Everything the panel cannot frame is a screen with a way out instead: an address that reaches no sandbox, a repo still installing, and the ordinary monorepo whose `dev` fans out across packages that pin their own ports, which no single hostname can stand for and which the panel resolves by forwarding the one server the user picks (`usePreviewTargets.forward`, which lands on the forwarded port's own target).
- **[src/pages/sandbox/SandboxDiscover.vue](src/pages/sandbox/SandboxDiscover.vue)**: registry discovery. Official rows are actionable only with current deterministic-scan and agent-audit evidence bound to the full source identity; detail separates those checks from optional human review and states that manifest permissions do not confine browser code.
- **[src/pages/sandbox/agent/commandRules.ts](src/pages/sandbox/agent/commandRules.ts)** and the Agent tab's **Safety** section: the only surface that writes the daemon's own gates — `commandRules` (a verdict per kind of hard-to-undo shell command), `explainCommands`, and `actionRules`' `agents.spawn`. Every option is FOUR-valued, not three, and that is the one thing to know before editing it: the stored rulebook holds three verdicts plus an ABSENT key, and absence is a posture of its own, because both of the daemon's standing floors are written `rule === undefined` (the wipe-a-disk floor, and the outside-content floor over recursive deletes and leaving credential reads). So writing an explicit `allow` does not restate today's behaviour, it switches a hold off — which is why `Default` is selectable and annotated per row with what it resolves to.
- **[src/router/index.ts](src/router/index.ts)**: `/login` + `/setup` → guarded shell (`/`) with child areas; `beforeEnter` guards (`requireAuth`, `requireSetup`) replace the old route guards. The shell's own entry is mobile → `/agents`, desktop → `/workspace`. In-shell areas register through `asyncView` rather than as bare lazy imports, see **Navigation never waits** under Conventions.

The capability model itself: the fifteen kinds, which four of them take extension-contributed cards, the effects taxonomy (skills, secrets, image fragments,
scaffolds, profiles, …), and the environment-overlay rebuild flow: is documented under **Capabilities** in

## Conventions

- **`<script setup lang="ts">` SFCs**; state in `ref`/`computed`; shared state in composables (no Pinia). PrimeVue imported directly from `primevue/*`; register-once bits (theme, tooltip) via `installUi`.
- **vue-query for request/response** (`useQuery`/`useMutation`, keyed + refetchable); streaming (chat tokens, sandbox liveness) stays manual with `ref` + `fetch`/`EventSource`.
- **Navigation never waits.** A route registered as a bare `component: () => import(…)` hands vue-router a promise, and the router completes the navigation only once the chunk has arrived, the click freezes for the length of the download, charged to whichever destination is heaviest. So every in-shell area registers through [`components/asyncView.ts`](src/components/asyncView.ts): the route component is synchronous and the view flips in the same tick; the CODE arrives behind an outline the way DATA already arrives behind skeletons, gated by the one reveal-delay/minimum-hold threshold pair ([`composables/loadingReveal.ts`](src/composables/loadingReveal.ts)) so a warm chunk paints no placeholder at all. An index-and-body page's outline is [`components/SplitViewOutline.vue`](src/components/SplitViewOutline.vue) wearing the page's real title; full-bleed surfaces get none, their honest placeholder is the shell's background, and each draws its inner skeletons once mounted. [`router/prefetch.ts`](src/router/prefetch.ts) pulls every registered chunk at idle, which is what makes the outline a cold-network-only sight, and what keeps a long-lived window's chunks in hand across a redeploy. The stale-window recovery ([`router/staleChunk.ts`](src/router/staleChunk.ts)) is split accordingly: `router.onError` still covers the entry-point routes that load at route level, and `asyncView` owns it for the in-shell views, whose failures no router hook can see, the reload guard re-arms on a chunk RESOLVING, not on a navigation landing, because landing stopped being evidence the moment it became unconditional.
- **Memory vs disk is a rule, not a per-query choice** (`queryPersistence.ts`, asserted in `storageRule.test.ts`). The query cache is mirrored to IndexedDB *whole* (one structured clone of everything ever cached, per write) so the cost of a single heavy entry is charged to every other write for the rest of the session. Small, shape-stable things (rosters, lists, trees, view contents) go to memory **and** that mirror, which is what makes a reload paint instead of blanking. Anything measured in hundreds of KB does not: a file diff is two whole file texts (or, past the daemon's cap, a patch of the changed regions) and stays in memory alone, bounded by `gcTime`; a chat transcript is worth surviving a reload and gets a **per-record** store of its own (`chat/transcriptCache.ts`), so its size is charged to itself. Heavy queries say so by carrying `UNPERSISTED` in their key, on the query, where it cannot be forgotten, rather than in a denylist somewhere else. This matters more now that the background loader fills the cache on the app's behalf rather than only what someone clicked.
- PrimeVue components + Tailwind 4 utilities + `@intentic/ui` (`Page`, `Card`, `Code`, `InfoHint`, `useTheme`, `useHighlighter`); markdown via `marked` + DOMPurify; code via Shiki (`useHighlighter`). Full-file review analysis runs in its own worker; Monaco keeps its separate editor/diff worker.
- **SSE/ndjson consume pattern** (see `conversation.ts` / `intenticStream.ts`): read the `ReadableStream`, split on `\n\n`, take `data:` lines, `JSON.parse` into the event union, fold into refs.
- **Nothing reaches for the user's own machine unasked.** The loopback shortcut ([`composables/sandbox/endpoint.ts`](src/composables/sandbox/endpoint.ts)) is the one place the app fetches an address on the machine the browser runs on, and Chrome answers that with a Local Network Access prompt, a dialog about "devices on your local network" that names no benefit and, arriving unbidden at first paint, reads as the app looking around someone's computer. So the reach is gated twice: it is not attempted at all for a sandbox whose machine the platform placed elsewhere (a hosted VM can never be a loopback hop away), and for every other sandbox the app states the benefit in one sentence and waits for a yes ([`composables/sandbox/localShortcut.ts`](src/composables/sandbox/localShortcut.ts)). The yes is kept per browser, matching the scope of the permission it stands for; a no is kept per sandbox, so the day a user sets one up on the laptop in front of them the question is asked again. Any future call that leaves for `127.0.0.1` belongs behind the same gate.
- **The editor area is TWO panes, and almost nothing knows it.** The workspace's tab strip splits in two ([`pages/workspace/workspaceTabs.ts`](src/pages/workspace/workspaceTabs.ts) holds the model: an `EditorStrip` of a `main` pane and a `side` one, each with its own tabs, focus and preview slot; [`EditorPane.vue`](src/pages/workspace/EditorPane.vue) draws one and the desktop lays out two with a `ResizeSeam` between them). It exists for one reading the single pane could not hold: **a document beside the file it names**. A commit's changed-file list, a package's architecture page and the codebase-health report are all full documents WITH FILE LISTS IN THEM, and in one pane a click on a row replaced the very list that was clicked, so reading a commit was tab ping-pong. Hence the one routing rule, in `useWorkspaceTabs.openDiff`: **a diff asked for while a `document` tab is focused opens in the other pane.** It is keyed on the active tab rather than on who called, which is what makes the second file clicked land where the first did (by then the focused tab is a diff, not a document). Everything else opens where the reader is, because the Changes and Checkpoints lists live in the sidebar and were never covered up. Three properties keep this from leaking: `tabs` / `activeId` / `activeTab` / `previewId` are the FOCUSED pane's, so Quick Open, the URL mirror, the chat's context chip and the phone are untouched; `normalizeStrip` guarantees **no empty half** (the side empties → the split is over, the main empties → the side takes its place), so no pane can sit there as a blank column; and a split is open exactly while the side pane holds tabs, so there is no second flag to fall out of step. The surface tells the store whether a split may be opened at all (`splitAllowed`, false on a phone and on a pane too narrow for two readable halves) rather than the store asking the layout anything, and a pane that has just become too narrow folds its companion back in instead of closing the reader's tabs. **The explorer stands aside for a split** and says so with a dot on the toggle that brings it back — as its own ephemeral state, never the stored `sidebarCollapsed` preference, the same two-pieces-of-state rule the narrow drawer uses, so a split never changes what the reader will find in their next session. The chrome each pane teleports into is scoped per pane (`viewerChrome.ts`'s `CHROME_SCOPE`), because a teleport addresses its target by DOM id and two panes with one id would put the companion's breadcrumb above the main pane's file.
- **A running command's output is a terminal, never a box.** `useTerminalPanel().openFocused(session)`; the dialog beside it holds the state and the buttons, and is not modal. The rule, its two look-alike exceptions and the reasoning are in [`composables/terminal/useTerminalPanel.ts`](src/composables/terminal/useTerminalPanel.ts). Opening one names a session that may not exist yet, so the caller says what it started ("Running your pre-push check", and the command) and the panel waits for it: a standing wait that the daemon's own change feed resolves whenever the terminal appears, not a race that expires. After a few seconds it stops holding itself empty and says what it is still waiting for, with a shell one click away. **The pre-push check and the push itself are two instances of one shape**, a command the daemon runs on a click and reports as a `CommandRun`: one watcher follows either to its verdict ([`composables/workspace/runWatcher.ts`](src/composables/workspace/runWatcher.ts), behind `usePrepush` and `usePushRun`), one module says how a run ended and composes the fix it proposes ([`composables/workspace/fixProposal.ts`](src/composables/workspace/fixProposal.ts)), and one card floats the question ([`shell/PushQuestionBody.vue`](src/shell/PushQuestionBody.vue)). A refused push therefore reads exactly like a red check, command, terminal, "Fix with agent", and a fix is proposed only where the code is known to be wrong: the repository's own pre-push hook said no. A rejected ref or a dead host gets git's reason and Try again, on the rule that sends no agent after a check that could not run.
- **An irreversible action asks about the thing, not about the click, and the daemon has to hand it the words.** Killing a terminal ends a tmux session for good, and the strip is a row of near-identical pills with a hover-× four pixels wide, so one pill off is a build, a suite, or an editor's unsaved buffers gone with no account of what was lost. The guard could not be built from what the list already said: `running` is unconditionally true for a user's shell whether it holds a prompt or a two-minute build, and a confirm keyed on that fires on every close and teaches the reader to click through it, worse than no confirm. So the DAEMON was made to say what is actually happening (`command`, the live pane's foreground process, `system/system.routes.ts`), the strip shows it before anyone reaches for the ×, and the dialog asks "Kill the terminal running `pnpm build`?" rather than "are you sure?" ([`pages/TerminalPanel.vue`](src/pages/TerminalPanel.vue)). The generalisation for the next one: a guard is only worth having where there is something to lose, it belongs on every route to the action (button, menu row, chord, not just the one that was reported), and if the app cannot name what it is about to destroy, that missing name is the bug to fix first.
- **A panel in a window of its own is a WINDOW OF THE APP, not a picture painted from this one.** The chat, the sandbox-global terminal and the app preview each float onto `/floating/<panel>` ([`pages/FloatingArea.vue`](src/pages/FloatingArea.vue)), where a full copy of the app boots and renders that panel into the same dock slot the in-shell area publishes. Which window draws it is ONE shared fact: the floating window announces itself on a heartbeat and every window reads three views off that beat, `floats` (it is in a window of its own), `here` (and that window is this one), `shows` (this window is the one drawing it) ([`composables/floating.ts`](src/composables/floating.ts)). A window that goes away without saying so stops beating **and** stops holding its liveness token, and a claim is retired only when both agree, so a dock, a close, a crash and a killed window are the same event. Both, because a beat alone cannot tell a window that is GONE from one the browser has merely stopped running on time: a minimized window is a hidden page, whose timers Chrome throttles to about one a minute once it has been hidden five minutes, so a beat a minute read against a 2.5-second deadline was a killed window, and the chat somebody parked on a second screen and minimized was reclaimed out from under them — its rail tile back, the app navigating itself to `/chat`, a second live copy of the conversation mounted here. The token is a Web Lock named after the claim (uncontended by construction, since the name carries the claim's own id): held for as long as that realm exists, released BY THE BROWSER when it stops existing, and therefore not a thing a throttled or frozen window can fail to do on time. A floating window that hears an older claim on its panel closes itself, which is why there can never be two. **This replaced the opposite bet and the whole class of bug that came with it**: the panel's DOM used to be teleported into a near-empty second page over the `window.opener` bond, which bought a streaming turn riding along without re-attaching and cost ownership (the panel obeyed one copy of the app, and a click in any other was invisible out there with both windows healthy), multiplicity (`window.open`'s target name only deduplicates inside one browsing context group, so two tabs meant two floating chats), and a three-valued liveness protocol with a veil, two deadlines and two graces to tell a live panel from a photograph of one. Popping out and docking re-attach now, by seq cursor for a turn and by tmux redraw for a terminal, and that is the whole price. Everything downstream got simpler with it: `document` in this code is always this window's, "is anyone looking?" is one document's visibility ([`composables/onScreen.ts`](src/composables/onScreen.ts)), and an observer or an animation frame belongs to the window its elements are in by construction rather than by being re-homed on every move.
- **A link pressed in a popped-out window lands in the APP's window, and the panel does not move.** A floating window is one panel and no app, so following a link inside it replaced the chat the reader had deliberately put on a second screen with a view wearing an icon rail — the file mention was right and the window was wrong. Every in-app destination reached from a popped-out panel is therefore an *errand* handed to a window that has the shell in it ([`composables/mainWindow.ts`](src/composables/mainWindow.ts)), which opens it and raises itself; with no such window left, one is opened, and a file errand waits on the doorstep for it to boot. Which window gets it comes off the same kind of heartbeat the panels use, a window announces itself **while something is floating** (nothing popped out, nobody asking, no traffic) and says when its reader was last in it, so with two app windows open the errand follows the reader rather than seniority. The errand is addressed rather than broadcast, because two windows both deciding they were the right one would open the file twice and fight over the focus. Two doors into it, and they are the two shapes a destination has: a **file reference** carries more than a URL can say (the line, whose checkout the path names) and rides whole through [`openWorkspaceRef`](src/composables/workspace/openFileRef.ts), while every ordinary **link** is caught by one delegated listener in the capture phase ([`pages/FloatingArea.vue`](src/pages/FloatingArea.vue)) — before a `RouterLink` acts on its own click, and on the `document` rather than the panel's box, because the panel's overlays teleport to the body and their links are links too. A modified click (new tab, new window) is left to the browser everywhere, as it already was for file mentions.
- **A secure-context api is not an api this app has.** `crypto.randomUUID` exists on https and on localhost and is simply undefined anywhere else, and "anywhere else" is a self-hosted instance opened at `http://192.168.1.x:port`. Every id in the app therefore comes from [`composables/uuid.ts`](src/composables/uuid.ts), which uses that generator where it exists and shapes the same v4 bytes out of `crypto.getRandomValues` (unrestricted) where it does not. This was not theoretical: the throw landed in the floating window's route setup, so that window booted, crashed, self-healed by wiping the origin's stored state, and came back an empty rectangle. Anything else reached for off `window` gets the same treatment before it ships.
- **A sandbox's view state belongs to that sandbox, and may only show what that sandbox has.** Switching sandboxes is switching machines, so anything that names or arranges one machine's things is remembered per sandbox and re-read on the switch ([`composables/sandbox/sandboxScope.ts`](src/composables/sandbox/sandboxScope.ts) is the one place that does the re-reading): the editor's open files, the tree, the chat, whether the terminal panel is open, and how its tabs were split. The second half is the part that bites: remembered state is restored INSTANTLY and the machine's own answer arrives over a tunnel, so a view must never draw a remembered thing as though it existed. The terminal strip is the worked example, its tabs are derived from the daemon's session list intersected with the remembered arrangement ([`composables/terminal/useTerminal.ts`](src/composables/terminal/useTerminal.ts)), because a tab restored out of storage for a session that isn't there cannot be clicked, and sat unresponsive over a panel saying nothing was open. A list that FAILS is the same case with no recovery of its own, every other thing that relists reacts to a list that ARRIVED, so a request the daemon refused changes nothing anyone is watching. It therefore re-asks a few times itself, and an outage longer than that ends with a relist the moment the daemon is reachable again. Left alone, the pane sat empty over a sandbox whose shells were running, until a `+` click made it list by accident. **The waiting itself gets a shape** (the rule `chat/providerAccounts.ts` states for accounts): the strip holds the remembered arrangement's places as inert skeleton pills and says it is looking, rather than stating "No terminals open." about a question still in flight, three different facts (nothing here, not asked yet, asked and refused) that used to share one sentence. And because a switch is not the end of those terminals, each one's scrollback is snapshotted under the sandbox being LEFT, so coming back shows the output you walked away from instead of a fresh prompt.
- **…and it runs as more than one copy.** Every browser tab with the app open is a full copy with its own chat-tab state, and the chat panel is drawn by exactly one of them at a time (a popped-out chat is a window of its own). Everything the chat says to the other windows travels on ONE channel ([`composables/chat/chatChannel.ts`](src/composables/chat/chatChannel.ts)), stamped with the sandbox it is about, so notes arrive in the order they were sent and a window pointed at another box drops them all. Three kinds ride it. A *summons* ([`composables/chat/summon.ts`](src/composables/chat/summon.ts)): a gesture that shows something in the chat (a board card, New agent, an accepted suggestion, opening a run) is never a plain store call but a broadcast, and every window applies the identical reveal ([`useChat.reveal`](src/composables/chat/useChat.ts)) to its own panel; closing from the board is a summons for the same reason, since a card is the conversation seen from the board rather than a tab of the window it is drawn in. Gestures **inside** the panel act there, under the rules only that surface knows, and then say what they pointed at (`relaySummons`). Acts (sending a queued prompt) happen once, in the window that was pressed, and reach the others as the daemon-side turn they become. The *strip* ([`composables/chat/chatEcho.ts`](src/composables/chat/chatEcho.ts)): the window drawing the chat publishes every open tab as a card would draw it, plus the focus and the panes ([`composables/chat/tabFacts.ts`](src/composables/chat/tabFacts.ts)), and everything outside the panel — the fleet board, its ring, the cross-sandbox board — reads the chat through one projection, [`chatStrip`](src/composables/chat/useChat.ts): this window's own tabs while it draws the chat, the published strip while it does not, never a mix. A window that is not drawing the chat still holds a tab list, but it is a *shadow*, frozen at the moment the panel left plus every summons since, kept only as the surface its own actions run on and replaced from the seed when the panel returns ([`composables/windowStore.ts`](src/composables/windowStore.ts)). Every defect the popped-out chat has had was a reader taking one fact from that shadow and another from an echo: a draft card swept because the shadow looked empty, an unsent chip kept because the shadow still held sent words, a card that vanished and came back because the shadow was closed a beat before the drawing window said so. The strip carries the first line of an unsent message, never the message, since a card only needs a name; that line, the mark and the message's age are said by one component on the board's card and the rail's row alike ([`components/UnsentMark.vue`](src/components/UnsentMark.vue)). The *set-aside drafts* ([`composables/chat/closedDrafts.ts`](src/composables/chat/closedDrafts.ts)): the words in a composer are the one thing a close must not be able to destroy, so closing a chat that holds an unsent message keeps its whole tab in a per-browser store, the board goes on drawing the card (undated, like every card the daemon has no row for), and opening it puts the message back. Only the window drawing the chat sets words aside, any other window's copy being the frozen shadow; the words are claimed once, by the window whose gesture reopens the chat, and ride the summons to the rest (`claimedSummons`), because a store with one reader and a reveal with many otherwise gave the message to whichever window asked first — the board's, which draws no chat. The only press that throws a message away is the second × on that card, asked for on a card visibly wearing an unsent mark. When the tab holding the focus closes, from the rail or from the board, the focus goes to the tab it was on before, not to whichever sits last in a strip sorted by lane.
- **A preference is one answer per account, so it is declared, not hand-rolled.** Which colour the app wears, how big its type is, whether a transcript draws its tool calls, which model and account the composer opens a new chat on: every one of these is `definePreference` ([`@intentic/ui` `composables/preference.ts`](../ui/src/composables/preference.ts)), which owns the guarded read, the guarded write, the DOM apply and telling the OTHER windows, as one definition. The last of those four is the reason it exists. Each setting used to own its own copy of the first three and none of the fourth, so a change on `/settings/appearance` repainted the window the reader was in and nothing else, and the chat they had deliberately put on a second screen sat in the old theme until it was reloaded: not a stale render but a different copy of the preference, which is why nothing in the panel could have noticed. The change travels two ways on purpose, a `BroadcastChannel` posted by the window the choice was made in (the mechanism a floating window's own existence already rides, so it demonstrably reaches exactly this pair of windows), and the browser's `storage` event, which catches what a posted note structurally cannot: a `localStorage.clear()` from the self-heal path, the anti-flash script in `index.html`, a hand edit in devtools. Both land in one seam (`receivePreferenceChange`), and **adopting a change is not making one**: the window that hears it applies and stops, because `read` normalizes (a column width is clamped to what THIS window can hold) and a window echoing its own reading back would ratchet the wide window's column down to fit a screen it isn't on. The line against window state is the namespace: preferences are `ui-*`, a window's own view state is `intentic.*` and stays out ([`composables/windowStore.ts`](src/composables/windowStore.ts)), which is why `terminalOpen` sits in [`composables/useLayout.ts`](src/composables/useLayout.ts) beside fifteen preferences without being one. **The composer's remembered picks are the case that shows why hand-rolling one is not a style question** ([`composables/chat/turnDefaults.ts`](src/composables/chat/turnDefaults.ts), [`composables/chat/accountPreference.ts`](src/composables/chat/accountPreference.ts)): they were read once at load into a private ref, which was harmless while a popped-out panel was DOM teleported into a bare window and shared the opener's realm, and became a bug the day that pop-out became a router-backed window running its own copy of the app. Two windows, two copies, neither told about the other: a model or account chosen in the floating chat was invisible to the fleet board's window, so "New agent" pressed on the board built the conversation from whatever that window had loaded with — hours earlier — and broadcast it to everyone, which is the whole of "it keeps switching my model and account back". Declared, the pick travels the moment it is made. A per-sandbox preference keeps the sandbox id IN its key (`ui-chat-accounts-<id>`) so a replaced workspace's sweep still finds it. **And a preference is declared when its module LOADS**, which is the one thing left to think about: a window that never imports the module holds no such preference, hears nothing, and never applied the stored value either. Harmless for a setting read by the surface it governs, since the window drawing that surface is the window that imported it — and wrong for the four that paint `<html>` (the scheme, the base text size, the skin, an imported VSCode theme), which apply to everything and are read by nothing in particular. `useSkin` was imported by the settings page and nothing else, so a popped-out chat never loaded it: the window still LOOKED right on the way out, because the anti-flash script writes `data-skin` from storage on every load, and then never changed again for the life of the window. The same gap hid a second bug in every window, `applyFont` is the skin's, so the face a skin asks for was missing until somebody opened `/settings/appearance` on that load. Those four are therefore installed for every window in one place, from `main.ts` ([`composables/theme/documentAppearance.ts`](src/composables/theme/documentAppearance.ts)), and a new preference that paints the document belongs in that list.
- **Anything that floats over the app is one channel with one host, and where it appears is not a per-component choice.** Eight surfaces had grown up independently and no two agreed on anything: a receipt pill at the bottom centre, a second copy of that pill on the fleet board with its own store, its own dwell timer and its own transition CSS; a loopback offer dodging the receipt lane at a hardcoded `bottom-16`; a stale-build card and a degraded-transport card both at the bottom right, at the same z-tier, neither able to know the other existed, so whichever appeared second simply sat on the first; an upload panel underneath both by nothing more principled than its z-index; a failed push and a busy sandbox each taking the top of the viewport from a different tier; and the composer saying "The sandbox is busy" as raw text at the same moment the gate said it in a pill. Position said nothing about what kind of message it was, only about which file drew it, and that is not a system anyone can learn. There is now one store ([`composables/notifications.ts`](src/composables/notifications.ts)) and one lane ([`shell/NotificationHost.vue`](src/shell/NotificationHost.vue), mounted by `App.vue` above the router and outside any session), and the only thing that varies between items is how long they stay and what can be pressed on them — which is the thing that should vary. **Three kinds carry that difference**: a `receipt` happened and is over, so it retires itself and needs no acknowledgement; a `condition` is TRUE RIGHT NOW, so it stays exactly as long as it is true; a `question` is owed an answer, so only answering or waving it off retires it. **The two halves of the store are shaped by that split.** A receipt is imperative (`say`, `warn`): it happened at a moment, there is no state to read, one at a time, newest wins, because two stacked receipts is a notification centre and the second is always the one the reader wants. A condition or a question is DECLARED (`hold`) as a pure function of state, re-read every tick, with no `raise` and no `remove` — which is what makes "on screen" and "true" unable to drift apart, and why Dismiss runs the OWNER'S callback rather than splicing a local list the next tick would argue with. Every source is declared in one file, in a deliberate order ([`composables/notificationSources.ts`](src/composables/notificationSources.ts)); an item whose content is not two strings (a composed agent turn, an upload's per-folder progress) hands the lane a body component. **The stacking order is geometry, not severity**: the column is anchored to the bottom of the viewport and grows upward, so its last child never moves and its first child is the one that does. Receipts go on top, because the thing that appears and vanishes several times a minute must not shift a card someone is reading or reaching for; questions take the corner, the one position in the lane that is fixed. **The line against the in-flow `<Notice>`** ([`@intentic/ui` `components/notice.ts`](../ui/src/components/notice.ts)) is what the message is ABOUT: the lane is for the app and the session, and a failure that belongs to one form, one panel or one chat pane stays beside the control that raised it, where two chats side by side can each say it about themselves.

## How to extend

**Default: write an extension, not a shell edit.** A new user-facing feature (a sidebar panel, a file
viewer, a command) is a contribution to the extension system, not a new page baked into the shell. This is
the whole point of the lean-core split: see the extension system in [ARCHITECTURE.md](../../ARCHITECTURE.md).

- **New panel / area:** add a first-party extension under [`_extensions/`](../../_extensions) (a
  `intentic-extension.json` manifest + an `activate` that calls `api.views.register`), and wire it into
  [src/extension-host/builtins.ts](src/extension-host/builtins.ts). It reaches the daemon only through the
  routes its manifest declares, and consumes the shared UI slice via `@intentic/extension-ui`. Start from an
  existing extension (e.g. [`_extensions/logs`](../../_extensions/logs)) as the template.
- **New file viewer:** contribute a `viewers` entry from an extension (see
  [`_extensions/viewers`](../../_extensions/viewers)): the host owns the fetch and hands your component the
  bytes. Don't add a branch to `FileViewer.vue`.
- **New sandbox call from an extension:** add the daemon route, declare it in the extension's manifest
  route allowlist, then call it via `api.sandbox.json` (validate the response against the
  `@intentic/sandbox-contract` schema). An undeclared route is refused by the host.

**Reserved for core** (edit the shell directly only for these): the editor surfaces themselves
(`WorkspaceTree`, `CodeView`, `FileViewer`, chat), the router/shell scaffolding in `router/index.ts` /
`WorkspaceShell.vue`, and the three privileged core view contributions in
[src/core-views/coreViews.ts](src/core-views/coreViews.ts) (`infrastructure`, `live-status`, `directory-ui`)
that are coupled to platform/onboarding internals a clean extension must not reach. New client state for a
core surface: a composable exposing a module-level `ref`.

## Key files

- [src/pages](src/pages): one file per route; the map of the whole app.
- [src/composables](src/composables), where the state actually lives: `chat/`, `agents/`, `terminal/`, `workspace/`, `sandbox/`. `workspace/workspaceScope.ts` holds the one that is easy to miss: WHOSE copy of the workspace the view is showing. An isolated conversation works in its own checkout, so a file link written in its chat carries that conversation (`/workspace/…?agent=`), the tree and every file read follow it, and a banner names it, otherwise the same path quietly opens the shared tree's different file. Scoped files are read-only.
- [src/chat](src/chat): the conversation panel, its tabs and tool cards. A tool card draws an ACT (a file
  written, a command run); the one exception is a DOCUMENT the turn wrote for the reader, which
  `ChatDocumentBody.vue` draws as prose, and which the question and plan cards carry as the subject they are
  asking about.
- [src/agents](src/agents), the fleet board: cards, detail, review.
- [src/extension-host](src/extension-host): how an extension's views reach the app.
- [src/router/index.ts](src/router/index.ts): the full route table.
