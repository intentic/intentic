# @intentic-app/web

The **Vue 3 SPA** (Vite + PrimeVue) — the platform's workspace UI. A user signs in with Google, connects a sandbox, and then drives that sandbox's daemon **directly** over its own tunnel (authenticated by a renewable daemon session established from Google identity): chat with the Claude agent, browse the workspace, edit inventory, run infra plan/provision, and view topology + deployments. The platform API it talks to is thin — only sign-in (Better Auth) + the `setup.*` handshake (mint token, store the sandbox's URL); everything else is browser→sandbox-direct. Talks to [`@intentic-app/api`](../../_platform/api) via the oRPC client + to the sandbox daemon via `sandboxRequest`; shares types through [`@intentic-app/api-contract`](../../_platform/api-contract) and primitives through [`@intentic/ui`](../../_editor/ui). Dev server (Vite) on :47145; the SPA calls the API directly at `API_URL` (`https://localhost:6480` in dev, CORS-enabled) — the base URL comes from the runtime `window.env` in [src/environments](src/environments), not relative paths.

## Responsibilities

- Render the post-login workspace shell, the page areas, and the persistent chat panel.
- Hold client state in composables (module-level `ref` singletons); fetch request/response data via **TanStack `@tanstack/vue-query`**; talk to the **platform** via the typed oRPC client (sign-in + `setup.connect`) and to the **sandbox daemon directly** via `sandboxRequest` (a Bearer daemon session, no cookies); consume the daemon's SSE/ndjson streams manually.
- Drive auth (Google sign-in via Better Auth), the setup gate, and the browser-direct workspace surface (chat, infra, inventory, deployments).

## Layout

- **[src/composables/](src/composables)** — module-level singletons + vue-query wrappers:
  - `useAuth.ts` — the reactive Better Auth session, cross-tab sign-in/out, profile + account deletion. Guards live in the router.
  - `useApi.ts` — the oRPC `ContractRouterClient` singleton; the platform surface is just `setup.*` (+ `me`).
  - `sandbox/useSandbox.ts` — the browser's sandbox state: `daemonUrl` (from `setup.binding`) + exact transport/action gate `reachable` (the live SSE probe in `useSandboxLiveness.ts`); the browser alone judges liveness. `sandbox/availability.ts` and `sandbox/useSandboxAvailability.ts` separately project that transport truth into `starting` / `warming` / `live` / `stale` / `busy` / `blocked` presentation states: established workspace views stay mounted through transient retries, short stalls remain visually online, and only a stall lasting 30 seconds earns a compact non-modal busy notice.
  - `useGoogleIdentity.ts` — Google Identity Services: mints the Google ID token, cached until it expires. ONE
    credential with two consumers — the daemon (which verifies it against Google, never against the platform) and
    the platform's own sign-in, which `Login.vue` establishes from the same mint. That is what removed the second
    Google prompt people used to meet right after signing in. Only the browser can produce it, so the direction is
    fixed: it goes out to both, and neither hands one back.
  - `sandbox/sandboxSession.ts` + `sandbox/sandboxAuthFetch.ts` — establish and renew the per-daemon bearer session, synchronize it across tabs, and give every client the same one-retry recovery after an authoritative 401.
  - `sandbox/sandboxClient.ts` — the browser→daemon-direct client (`sandboxRequest`/`sandboxJson`/`sandboxBlob`): snapshots one sandbox target and uses the shared authenticated-fetch policy for `${daemonUrl}${path}`.
  - `useChat.ts` + `conversation.ts` — the Claude agent, daemon-direct (`/agent`, `/agent/decision`, `/agent/answer`, `/sessions`, `/claude/*`).
  - `useDeployments.ts` / `useWorkspaceState.ts` (+ `workspaceStateProjection.ts`) / `useInventory.ts` / `useWorkspaceTree.ts` — the read-model + inventory as **vue-query** queries/mutations against the daemon; `intenticStream.ts` is the shared `/intentic` ndjson reader; `renderMarkdown.ts` sanitizes marked output (DOMPurify) for `v-html`.
  - `useLayout.ts` — chat panel + explorer sidebar width/side. Every width here is in **app pixels** — pixels at the app's base text size (`useTextSize`), which is what they were measured at — so a column keeps the same number of characters when the reader makes the app larger. `uiScale.ts` owns the trip to and from screen pixels and names the only two edges that take it: the pointer, and anything handed to the platform (a pop-out window's size, an editor's font size).
  - `workspace/codeAnalysis.ts` + `codeAnalysisClient.ts` — one TextMate walk produces the comment-free view and import locations; a lazy dedicated worker runs it, and a small recent-result cache lets the background loader, code-only stats, and an opened diff share that work.
  - `prefetch/` — **the background loader**: one reader that keeps ahead of the user across the whole app, so a click paints from cache instead of paying a tunnel round trip. `backgroundLoader.ts` is the loop and the whole of the pacing policy (one read at a time, only in browser idle, a gap proportional to what the last read cost, stand aside while anything the user asked for is in flight, nothing at all while no window is on screen, quiet failure with a cool-off after a run); `warmPlan.ts` is the registry each surface contributes a wish list to, ordered by four bands that say how close the user is (`now` → `near` → `work` → `rail`) rather than by an importance number; `sources/` holds the app's own contributors — the agent board's cards (transcript + changes), the workspace review's rows, and the rail's view lists. Started for the signed-in session by `shell/WorkspaceRuntime.vue`, beside the daemon stream and for the same reason. Every wish reads through the SAME query its screen reads, so warmed and clicked are one cache entry; a wish carries `have()` so a satisfied plan costs lookups rather than requests.
  - `buildEpoch.ts` / `selfHeal.ts` — why a stale browser never needs "clear site data": every mirror this app persists is invalidated automatically (a new build busts the query-cache buster and drops the transcript store; a replaced workspace sweeps that sandbox's remembered tabs/terminals/drafts via `sandbox/systemEventRouting.ts`), and a crash inside the startup window wipes the origin's storage and reloads once.
  - `extensions/` — the extension/capability data layer: `useExtensions.ts` (installed manifests from `GET /extensions`, `contributionOf(kind, id)` for a card's contribution, `enabled` for the extensions actually wired up, `settled` for load-gated decisions) and `useCapabilities.ts` (capability list + the streamed add + remove/secret mutations).
- **[src/extension-host/](src/extension-host)** — the real extension host: fetches `GET /extensions`, engine-checks and `import()`s git-installed bundles, activates the compiled-in first-party UI extensions (`builtins.ts`) — everything through the manifest-gated `createExtensionApi` (`apiImpl.ts`).
- **[src/core-views/](src/core-views)** — the reactive runtime view registry the shell renders from, plus the three privileged *core* view contributions (`infrastructure`, `live-status`, `directory-ui`) that are extension-shaped but deliberately in-app.
- **[src/shell/](src/shell)** — the persistent shell: `WorkspaceShell.vue` (rail | workspace | chat grid), `ShellDesktop`/`ShellMobile`, `AccountPanel.vue`, `GoogleSigninGate.vue`, `QuickOpen.vue` — plus the part that outlives it: `WorkspaceRuntime.vue` (mounted by `App.vue` for the whole signed-in session — the daemon's liveness stream, presence, and `PoppablePanels.vue`, the single chat + terminal instances). The shell only lends those panels a place to dock (`dockSlots.ts`), so a route outside it (`/setup`) can't tear a popped-out window down.
- **[src/chat/](src/chat)** — the chat panel: `ChatPanel.vue` + its message view, tabs, and mode/provider menus. One instance with three exclusive homes: the side column, the rail (a Chat tile whose full-screen `/chat` area is the chat's only in-window surface — `pages/ChatArea.vue`; the user's choice between these two persists as `useLayout.chatHome`), or its own pop-out window. Which form the panel wears is derived from where it is actually drawn (`composables/chat/chatSurface.ts`).
- **[src/sandbox-gates/](src/sandbox-gates)** — the sandbox connect/authorize gates and switcher wrapping the workspace surface. A full gate is reserved for blocked causes or a sandbox with no successful workspace snapshot; even an empty cached workspace remains mounted while transient failures recover automatically.
- **[src/presence/](src/presence)** — collaborator presence avatars/stack.
- **[src/pages/](src/pages)** — lazy-loaded areas: `Login`, `Setup`, `Sandbox`, `Infra` (topology + config/provision), `workspace/` (VSCode-like explorer + file viewer), `Capabilities.vue` (the rail's "+": static core cards merged with cards derived from ENABLED extensions' `contributes.capabilities`, a config form with a live "This will add to your sandbox" effects panel), `Secrets.vue` (the capability-secret inventory), and the `*Dialog.vue` overlays.
- **[src/pages/sandbox/SandboxDiscover.vue](src/pages/sandbox/SandboxDiscover.vue)** — registry discovery. Official rows are actionable only with current deterministic-scan and agent-audit evidence bound to the full source identity; detail separates those checks from optional human review and states that manifest permissions do not confine browser code.
- **[src/router/index.ts](src/router/index.ts)** — `/login` + `/setup` → guarded shell (`/`) with child areas; `beforeEnter` guards (`requireAuth`, `requireSetup`) replace the old route guards.

The capability model itself — the fifteen kinds, which four of them take extension-contributed cards, the effects taxonomy (skills, secrets, image fragments,
scaffolds, profiles, …), and the environment-overlay rebuild flow — is documented under **Capabilities** in
[ARCHITECTURE.md](../../ARCHITECTURE.md).

## Conventions

- **`<script setup lang="ts">` SFCs**; state in `ref`/`computed`; shared state in composables (no Pinia). PrimeVue imported directly from `primevue/*`; register-once bits (theme, tooltip) via `installUi`.
- **vue-query for request/response** (`useQuery`/`useMutation`, keyed + refetchable); streaming (chat tokens, sandbox liveness) stays manual with `ref` + `fetch`/`EventSource`.
- **Memory vs disk is a rule, not a per-query choice** (`queryPersistence.ts`, asserted in `storageRule.test.ts`). The query cache is mirrored to IndexedDB *whole* — one structured clone of everything ever cached, per write — so the cost of a single heavy entry is charged to every other write for the rest of the session. Small, shape-stable things (rosters, lists, trees, view contents) go to memory **and** that mirror, which is what makes a reload paint instead of blanking. Anything measured in hundreds of KB does not: a file diff is two whole file texts and stays in memory alone, bounded by `gcTime`; a chat transcript is worth surviving a reload and gets a **per-record** store of its own (`chat/transcriptCache.ts`), so its size is charged to itself. Heavy queries say so by carrying `UNPERSISTED` in their key — on the query, where it cannot be forgotten, rather than in a denylist somewhere else. This matters more now that the background loader fills the cache on the app's behalf rather than only what someone clicked.
- PrimeVue components + Tailwind 4 utilities + `@intentic/ui` (`Page`, `Card`, `Code`, `InfoHint`, `useTheme`, `useHighlighter`); markdown via `marked` + DOMPurify; code via Shiki (`useHighlighter`). Full-file review analysis runs in its own worker; Monaco keeps its separate editor/diff worker.
- **SSE/ndjson consume pattern** (see `conversation.ts` / `intenticStream.ts`): read the `ReadableStream`, split on `\n\n`, take `data:` lines, `JSON.parse` into the event union, fold into refs.
- **Nothing reaches for the user's own machine unasked.** The loopback shortcut ([`composables/sandbox/endpoint.ts`](src/composables/sandbox/endpoint.ts)) is the one place the app fetches an address on the machine the browser runs on, and Chrome answers that with a Local Network Access prompt — a dialog about "devices on your local network" that names no benefit and, arriving unbidden at first paint, reads as the app looking around someone's computer. So the reach is gated twice: it is not attempted at all for a sandbox whose machine the platform placed elsewhere (a hosted VM, a cloud machine in the user's provider account — those can never be a loopback hop away), and for every other sandbox the app states the benefit in one sentence and waits for a yes ([`composables/sandbox/localShortcut.ts`](src/composables/sandbox/localShortcut.ts)). The yes is kept per browser, matching the scope of the permission it stands for; a no is kept per sandbox, so the day a user sets one up on the laptop in front of them the question is asked again. Any future call that leaves for `127.0.0.1` belongs behind the same gate.
- **A running command's output is a terminal, never a box.** `useTerminalPanel().openFocused(session)`; the dialog beside it holds the state and the buttons, and is not modal. The rule, its two look-alike exceptions and the reasoning are in [`composables/terminal/useTerminalPanel.ts`](src/composables/terminal/useTerminalPanel.ts). Opening one names a session that may not exist yet, so the caller says what it started ("Running your pre-push check", and the command) and the panel waits for it — a standing wait that the daemon's own change feed resolves whenever the terminal appears, not a race that expires. After a few seconds it stops holding itself empty and says what it is still waiting for, with a shell one click away.
- **The app renders into more than one window.** A popped-out chat or terminal is drawn by the tab's own realm into a real second window ([`composables/usePopout.ts`](src/composables/usePopout.ts)), so `document` in this code is always the tab's and says nothing about the window the user is reading. "Is anyone looking?" is [`composables/onScreen.ts`](src/composables/onScreen.ts), never `document.visibilityState`; an overlay inside a poppable panel derives its document from its anchor (`AnchoredOverlay` in `@intentic/ui`).
- **A sandbox's view state belongs to that sandbox — and may only show what that sandbox has.** Switching sandboxes is switching machines, so anything that names or arranges one machine's things is remembered per sandbox and re-read on the switch ([`composables/sandbox/sandboxScope.ts`](src/composables/sandbox/sandboxScope.ts) is the one place that does the re-reading): the editor's open files, the tree, the chat, whether the terminal panel is open, and how its tabs were split. The second half is the part that bites: remembered state is restored INSTANTLY and the machine's own answer arrives over a tunnel, so a view must never draw a remembered thing as though it existed. The terminal strip is the worked example — its tabs are derived from the daemon's session list intersected with the remembered arrangement ([`composables/terminal/useTerminal.ts`](src/composables/terminal/useTerminal.ts)), because a tab restored out of storage for a session that isn't there cannot be clicked, and sat unresponsive over a panel saying nothing was open. A list that FAILS is the same case with no recovery of its own — every other thing that relists reacts to a list that ARRIVED, so a request the daemon refused changes nothing anyone is watching. It therefore re-asks a few times itself, and an outage longer than that ends with a relist the moment the daemon is reachable again. Left alone, the pane sat empty over a sandbox whose shells were running, until a `+` click made it list by accident. **The waiting itself gets a shape** (the rule `chat/providerAccounts.ts` states for accounts): the strip holds the remembered arrangement's places as inert skeleton pills and says it is looking, rather than stating "No terminals open." about a question still in flight — three different facts (nothing here, not asked yet, asked and refused) that used to share one sentence. And because a switch is not the end of those terminals, each one's scrollback is snapshotted under the sandbox being LEFT, so coming back shows the output you walked away from instead of a fresh prompt.
- **…and it runs as more than one copy.** Every browser tab with the app open is a full copy with its own chat-tab state, and a popped-out panel obeys only the copy that opened it — so a gesture that shows something in the chat (a board card, New agent, an accepted suggestion, opening a run) is never a plain store call: it is a *summons* ([`composables/chat/summon.ts`](src/composables/chat/summon.ts)), broadcast to every window of the origin, each of which applies the identical reveal ([`useChat.reveal`](src/composables/chat/useChat.ts)) to its own panel. Gestures **inside** the chat panel stay local — the reader is pointing at the thing itself. Acts (sending a queued prompt) happen once, in the window that was pressed, and reach the others as the daemon-side turn they become.

## How to extend

**Default: write an extension, not a shell edit.** A new user-facing feature (a sidebar panel, a file
viewer, a command) is a contribution to the extension system, not a new page baked into the shell. This is
the whole point of the lean-core split — see the extension system in [ARCHITECTURE.md](../../ARCHITECTURE.md).

- **New panel / area:** add a first-party extension under [`_extensions/`](../../_extensions) (a
  `intentic-extension.json` manifest + an `activate` that calls `api.views.register`), and wire it into
  [src/extension-host/builtins.ts](src/extension-host/builtins.ts). It reaches the daemon only through the
  routes its manifest declares, and consumes the shared UI slice via `@intentic/extension-ui`. Start from an
  existing extension (e.g. [`_extensions/logs`](../../_extensions/logs)) as the template.
- **New file viewer:** contribute a `viewers` entry from an extension (see
  [`_extensions/viewers`](../../_extensions/viewers)) — the host owns the fetch and hands your component the
  bytes. Don't add a branch to `FileViewer.vue`.
- **New sandbox call from an extension:** add the daemon route, declare it in the extension's manifest
  route allowlist, then call it via `api.sandbox.json` (validate the response against the
  `@intentic/sandbox-contract` schema). An undeclared route is refused by the host.

**Reserved for core** (edit the shell directly only for these): the editor surfaces themselves
(`WorkspaceTree`, `CodeView`, `FileViewer`, chat), the router/shell scaffolding in `router/index.ts` /
`WorkspaceShell.vue`, and the three privileged core view contributions in
[src/core-views/coreViews.ts](src/core-views/coreViews.ts) (`infrastructure`, `live-status`, `directory-ui`)
that are coupled to platform/onboarding internals a clean extension must not reach. New client state for a
core surface: a composable exposing a module-level `ref`.

## Key files

- [src/pages](src/pages) — one file per route; the map of the whole app.
- [src/composables](src/composables) — where the state actually lives: `chat/`, `agents/`, `terminal/`, `workspace/`, `sandbox/`. `workspace/workspaceScope.ts` holds the one that is easy to miss: WHOSE copy of the workspace the view is showing. An isolated conversation works in its own checkout, so a file link written in its chat carries that conversation (`/workspace/…?agent=`), the tree and every file read follow it, and a banner names it — otherwise the same path quietly opens the shared tree's different file. Scoped files are read-only.
- [src/chat](src/chat) — the conversation panel, its tabs and tool cards.
- [src/agents](src/agents) — the fleet board: cards, detail, review.
- [src/extension-host](src/extension-host) — how an extension's views reach the app.
- [src/router/index.ts](src/router/index.ts) — the full route table.
