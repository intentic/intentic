# @intentic/web

The **Vue 3 SPA** (Vite + PrimeVue), the platform's workspace UI. A user signs in with Google, connects a sandbox, and then drives that sandbox's daemon **directly** over its own tunnel (authenticated by a renewable daemon session established from Google identity or from a passkey registered with that sandbox): chat with the Claude agent, browse the workspace, edit inventory, run infra plan/provision, and view topology + deployments. The platform API it talks to is thin, only sign-in (Better Auth) + the `setup.*` handshake (mint token, store the sandbox's URL); everything else is browser→sandbox-direct. Talks to [`@intentic/api`](../../_platform/api) via the oRPC client + to the sandbox daemon via `sandboxRequest`; shares types through [`@intentic/api-contract`](../../_shared/api-contract) and primitives through [`@intentic/ui`](../../_editor/ui). Dev server (Vite) on :47145; the SPA calls the API directly at `API_URL` (`https://localhost:6480` in dev, CORS-enabled), the base URL comes from the runtime `window.env` in [src/app/environments](src/app/environments), not relative paths.

## Responsibilities

- Render the post-login workspace shell, the page sections, and the persistent chat panel.
- Hold client state in composables (module-level `ref` singletons); fetch request/response data via **TanStack `@tanstack/vue-query`**; talk to the **platform** via the typed oRPC client (sign-in + `setup.connect`) and to the **sandbox daemon directly** via `sandboxRequest` (a Bearer daemon session, no cookies); consume the daemon's SSE/ndjson streams manually.
- Drive auth (Google sign-in via Better Auth), the setup gate, and the browser-direct workspace surface (chat, infra, inventory, deployments).

## Layout

- **[src/features/](src/features)**: one directory per feature, and everything that feature is made of lives in it —
  its screens, its components and the module-level singletons and vue-query wrappers behind them. A feature is
  named for the wire group it speaks to (`agents`, `workspace`, `capabilities`, `terminal`, `settings`,
  `extensions`, `sandbox`, `browsers`, `preview`, `setup`, `auth`), with one documented exception: `chat` is the
  UI's name for wire group `agent`, because that is what the surface is called. Inside a feature, one more level
  says what part of it (`chat/composer`, `chat/transcript`, `workspace/explorer`, `sandbox/environment`), never two.
  - [`features/auth/useAuth.ts`](src/features/auth/useAuth.ts): the reactive Better Auth session, cross-tab sign-in/out, profile + account deletion. Guards live in the router.
  - [`lib/useApi.ts`](src/lib/useApi.ts): the oRPC `ContractRouterClient` singleton; the platform surface is just `setup.*` (+ `me`).
  - `features/sandbox/client/useSandbox.ts`, the browser's sandbox state: `daemonUrl` (from `setup.binding`) + exact transport/action gate `reachable` (the live SSE probe in `useSandboxLiveness.ts`); the browser alone judges liveness. `sandbox/availability.ts` and `sandbox/useSandboxAvailability.ts` separately project that transport truth into `starting` / `warming` / `live` / `stale` / `busy` / `detached` / `removed` / `blocked` presentation states (the last three are ENDINGS, never inferred from silence: `detached` is the edge's own verdict that nothing is dialled in for this sandbox, `removed` is a deletion the removing machine reported; a sandbox that is merely quiet is still a wait): established workspace views stay mounted through transient retries, short stalls remain visually online, and only a stall lasting 30 seconds earns a compact non-modal busy notice.
  - `useGoogleIdentity.ts`, Google Identity Services: mints the Google ID token, cached until it expires. ONE
    credential with two consumers: the daemon (which verifies it against Google, never against the platform) and
    the platform's own sign-in, which `Login.vue` establishes from the same mint. That is what removed the second
    Google prompt people used to meet right after signing in. Only the browser can produce it, so the direction is
    fixed: it goes out to both, and neither hands one back.
  - `sandbox/sandboxSession.ts` + `sandbox/sandboxAuthFetch.ts`: establish and renew the per-daemon bearer session, synchronize it across tabs, and give every client the same one-retry recovery after an authoritative 401 or a 428 (the daemon took the proof but the sandbox requires a passkey). Only a call somebody is waiting on may ask for a sign-in: a background reader spends the proof already in hand and takes "no" for an answer, and even a foreground call checks the daemon is answering before it raises a sign-in on that daemon's behalf.
  - `sandbox/signInPrompt.ts` + `sandbox/gates/SignInWall.vue`: the one sign-in question the session module can ask and the overlay that answers it. With nothing in hand, Google's button and (once the daemon says one is registered for this origin) a passkey beside it, racing; after a 428, the step-up: the passkey held, or adding a first one under the Google proof just taken, or the owner's recovery code. `sandbox/session/passkeySignIn.ts` is the WebAuthn half; the daemon is the relying party, so nothing here touches the platform. Managing passkeys and the owner's require switch is `sandbox/access/PasskeysSection.vue`.
  - `sandbox/sandboxClient.ts`, the browser→daemon-direct client (`sandboxRequest`/`sandboxJson`/`sandboxBlob`): snapshots one sandbox target and uses the shared authenticated-fetch policy for `${daemonUrl}${path}`. `sandboxJsonAt` aims the same call at another sandbox by id; `sandboxJsonQuietly` does that for the pollers nobody is waiting on, which is what keeps a stopped machine in the account from raising a sign-in gate over the workspace on screen.
  - `chat/useChat.ts` + `chat/conversation.ts`: the Claude agent, daemon-direct (`/agent`, `/agent/decision`, `/agent/answer`, `/sessions`, `/claude/*`). `useChat.ts` is the composable and the sandbox reset; the store behind it is split by topic into `useChat-tabs.ts` (the tab list, the focus, the panes, the tab snapshot), `useChat-strip.ts` (the strip every surface outside the panel reads), `useChat-sessions.ts` (history and transcript hydration), `useChat-catalog.ts` (model catalogs, slash commands, the trial), `useChat-accounts.ts` (provider accounts), `useChat-connect.ts` (the native, minted and translator sign-in flows), `useChat-view.ts` (the per-pane facade) and `useChat-reveal.ts` (what a summons applies).
  - `agents/useAgents.ts`, the fleet store, is the composable and the store-wide reset over four topic modules that depend strictly downward: `useAgents-registry.ts` (the daemon's roster and archived list as revisioned snapshots, pending moves, held wakes, the pull that fills them), `useAgents-fleet.ts` (`FleetAgent`, the registry/tab/draft merge into cards, lanes, counts), `useAgents-archive.ts` (archive, restore, purge, undo, what each says, which cards are busy), `useAgents-actions.ts` (per-agent writes and opening a card). Import a name from the module that declares it; the composable is what components call.
  - `useDeployments.ts` / `useWorkspaceState.ts` (+ `workspaceStateProjection.ts`) / `useInventory.ts` / `useWorkspaceTree.ts`: the read-model + inventory as **vue-query** queries/mutations against the daemon; `intenticStream.ts` is the shared `/intentic` ndjson reader; `renderMarkdown.ts` sanitizes marked output (DOMPurify) for `v-html`.
  - `useLayout.ts` (chat panel + explorer sidebar width/side. Every width here is in **app pixels**) pixels at the app's base text size (`useTextSize`), which is what they were measured at, so a column keeps the same number of characters when the reader makes the app larger. `uiScale.ts` owns the trip to and from screen pixels and names the only two edges that take it: the pointer, and anything handed to the platform (a pop-out window's size, an editor's font size).
  - `workspace/codeAnalysis.ts` + `codeAnalysisClient.ts`: one TextMate walk produces the comment-free view and import locations; a lazy dedicated worker runs it, and a small recent-result cache lets the background loader, code-only stats, and an opened diff share that work.
  - `prefetch/`, **the background loader**: one reader that keeps ahead of the user across the whole app, so a click paints from cache instead of paying a tunnel round trip. `backgroundLoader.ts` is the loop and the whole of the pacing policy (one read at a time, only in browser idle, a gap proportional to what the last read cost, stand aside while anything the user asked for is in flight, nothing at all while no window is on screen, quiet failure with a cool-off after a run); `warmPlan.ts` is the registry each surface contributes a wish list to, ordered by four bands that say how close the user is (`now` → `near` → `work` → `rail`) rather than by an importance number; `sources/` holds the app's own contributors, the workspace review's rows, the agent board's cards (transcript + changes), and the rail's view lists, and registration order is the tie-break within a band. **The workspace review leads, from every route.** It is where a clean turn's work ends up (landing writes the delta into the user's tree as uncommitted changes) and where the user commits from, and it is the one surface whose whole contents are dropped on a schedule the user does not control: a turn ending invalidates the change list and every diff filed under it at once. Behind the board it was therefore re-read last, precisely when it had just been emptied, so the panel was reliably cold when opened; ahead of it, a card on a busy board pays its round trip more often, which is the cheaper wait (a card opens onto a stream, a review opens onto ± numbers that are wrong until read). The same reasoning removes the double read after a landing: an agent's own review and the workspace review reach the same file through **different questions**, the agent's branch against the main line as it stands (what this conversation wrote that you have not taken yet, landed rows included, since a clean turn lands within ms of finishing) versus the main tree against `HEAD` split by staged/unstaged/conflicted, so they cannot share a cache entry, and `sources/reviewsToRead.ts` instead stops reading a `landed` agent's rows ahead and leaves that work to the workspace review (unless that agent's own page is open). Work HELD on the branch (`ready`, auto-land off) is still read ahead: no other review can reach it. Started for the signed-in session by `shell/WorkspaceRuntime.vue`, beside the daemon stream and for the same reason. Every wish reads through the SAME query its screen reads, so warmed and clicked are one cache entry; a wish carries `have()` so a satisfied plan costs lookups rather than requests.
  - `buildEpoch.ts` / `selfHeal.ts`, why a stale browser never needs "clear site data": every mirror this app persists is invalidated automatically (a new build busts the query-cache buster and drops the transcript store; a replaced workspace sweeps that sandbox's remembered tabs/terminals/drafts via `sandbox/systemEventRouting.ts`), and a crash inside the startup window wipes the origin's storage and reloads once.
  - `clientDiagnostics.ts`, the app's only durable account of itself. Everything this app caught or measured used to end at the console: the perf ring buffer dies on reload, a render error reaches Vue's handler and stops, and the self-heal above *clears this origin's storage and reloads*, destroying the evidence for the bug class that reproduces least often. So when someone hit a bug in their own browser the record was nothing, and the only way to investigate was to re-drive a browser and hope, which across 728 real sessions meant 1,545 screenshots against 65 reads of a console and a quarter of all prompts arriving with a picture attached. Render errors, script errors, unhandled rejections, self-heal wipes and slow spans now post to the daemon's `POST /logs/client`, which appends them to `logs/client.jsonl` where the sandbox's diagnostic tools read them. Three rules, in this order: it never throws (its callers are an error handler and an unload hook), it never blocks (batched, fire-and-forget), and it never grows unbounded (identical reports coalesce to a count, the queue has a ceiling, a failed post drops the batch rather than retrying). The flush is `keepalive`, which is the load-bearing detail rather than a nicety: the two moments most worth reporting are a wipe-and-reload and a closing tab, and an ordinary fetch on either is cancelled with the page.
  - `app/perf.ts` + `app/renderTrace.ts`, the two halves of "the UI feels slow". `__intenticPerf` (always recording) answers what took time — a ring buffer of spans, a table ranked by total time, slow spans warned to the console and posted durably through `clientDiagnostics`. `__intenticRender` (dev-only, idle until `__intenticRender.on()`) answers the question time cannot: WHY a component nothing on screen changed redrew, which is the only form an excess redraw takes. It reports redraws per component per instance (off Vue's own `app.config.performance` measures) beside the reactive writes that woke them, each with the frame that did the writing — and the gap between the two columns is itself the finding, since a component woken often and redrawn never is subscribed to more than it reads. [docs/audits/ui-rerender-analysis.md](../../docs/audits/ui-rerender-analysis.md) is what it found the first time it was pointed at the app, including the two suspects it cleared.
  - `extensions/`, the extension/capability data layer: `useExtensions.ts` (installed manifests from `GET /extensions`, `contributionOf(kind, id)` for a card's contribution, `enabled` for the extensions actually wired up, `settled` for load-gated decisions) and `useCapabilities.ts` (capability list + the streamed add + remove/secret mutations).
- **[src/extension-host](src/extension-host)**, the real extension host: fetches `GET /extensions`, engine-checks and `import()`s git-installed bundles, activates the compiled-in first-party UI extensions (`builtins.ts`), everything through the manifest-gated `createExtensionApi` (`apiImpl.ts`).
- **[src/core-views](src/core-views)**: the reactive runtime view registry the shell renders from, plus the three privileged *core* view contributions (`infrastructure`, `live-status`, `directory-ui`) that are extension-shaped but deliberately in-app. `registry.ts` also owns **what the rail shows and in what order**, for core tiles and extension tiles in one table: the bands (Work · Judge · Set up · Know) and, per id, whether it is `always` on the rail or there only while it is **saying something**. Four tiles are permanent (Chat, Agents, Workspace, Preview: where you go, constantly); everything else, first-party and third-party alike, holds a tile while its badge is non-empty, while it is pinned, or while you are standing in it, and lives behind the rail's **More** menu the rest of the time. The scarce thing is rail tiles, roughly nine above a 945px viewport, so a tile that can never tell you anything was spending one all day: this is the rule that evicted Memory and Activity to the sandbox hub, applied to every tile rather than to the two that were caught by it. Nothing became less reachable: More lists every section whether or not it is on the rail, each has a `view.*` command in the palette ([`shell/commands/useNavigationCommands.ts`](src/shell/commands/useNavigationCommands.ts) — which derives a destination for every rail section, every sandbox-hub section and every settings section off the same tables those surfaces draw themselves from, so the palette cannot fall behind them), and a right-click pins one back for good ([`shell/railPins.ts`](src/shell/rail/railPins.ts)).
- **[src/shell](src/shell)**, the persistent shell: `WorkspaceShell.vue` (rail | workspace | chat grid), `ShellDesktop`/`ShellMobile`, `AccountPanel.vue`, `GoogleSignInWall.vue`, `QuickOpen.vue` — **one palette over four kinds** (agents, files, terminals, commands), where the first character of the query is the scope (`#` `@` `$` `>`, taught by the chips under the field) and the kinds are ordered against each other by their best-scoring row on one 0..1 axis ([`jumpSearch.ts`](src/shell/commands/jumpSearch.ts), rows assembled in [`useJumpRows.ts`](src/shell/commands/useJumpRows.ts)): `Mod+P` and `Mod+Shift+P` are two doors into the same room, not two palettes to pick between, and the thing a reader is looking for is found without first deciding what kind of thing it is — plus the part that outlives it: `WorkspaceRuntime.vue` (mounted by `App.vue` for the whole signed-in session, the daemon's liveness stream, presence, and `PoppablePanels.vue`, the single chat + terminal + preview instances). The shell only lends those panels a place to dock (`dockSlots.ts`), so a route outside it (`/setup`) can't tear a popped-out window down.
- **[src/features/chat](src/features/chat)**, the chat panel: `ChatPanel.vue` + its message view, tabs, and mode/provider menus. One instance with three exclusive homes: the side column, the rail (a Chat tile whose full-screen `/chat` section is the chat's only in-window surface, `pages/ChatSection.vue`; the user's choice between these two persists as `useLayout.chatHome`), or its own pop-out window. Which form the panel wears is derived from where it is actually drawn (`composables/chat/chatSurface.ts`). **The pop-out window earns one thing the other two homes do not**: a rail down its right edge ([`ChatSideRail.vue`](src/features/chat/panel/ChatSideRail.vue)) holding the two things a reader wants standing still rather than scrolling past. The focused chat's checklist is at the top ([`ChatRailChecklist.vue`](src/features/chat/panel/ChatRailChecklist.vue)) because a list is state and the transcript can only record it as events; underneath is plan headroom ([`ChatCapacityRail.vue`](src/features/chat/panel/ChatCapacityRail.vue)), which subscriptions still have room and how much, so "what can I start next" is answerable without leaving a window that has no shell around it. **The rail's presence is keyed on capacity alone**, never on the checklist: a chat picking up its first task would otherwise make a 240px column appear mid-turn and reflow the panel under the answer being read. **In the transcript the same checklist is an event, not a state**, which is why it is not drawn whole each time: the daemon rebuilds the full list from every `TaskUpdate` ([`task-checklist.ts`](../../_sandbox/sandbox/src/agent/run/task-checklist.ts)) and the fold parks each snapshot on its own bubble, so an N-task turn used to cost N² rows to say N things — 24 lines for three status flips was ordinary, and the worst recorded session drew 588. Only a turn's FIRST and LAST snapshots draw the list; the ones between draw one line for what moved and open to the same rows ([`ChatTodoList.vue`](src/features/chat/transcript/ChatTodoList.vue), the projection in [`transcript.ts`](src/features/chat/transcript/transcript.ts)), the way a hidden run's tool calls open to `ChatToolRows`. A new prompt restates the list in full, because a turn's opening list is what orients a reader scrolling into it. **The turn ENDS on the list for the opposite reason**: read top-down, that opening list is the most prominent thing in the turn and the least true by the end of it, with everything that happened since demoted to one-liners — a reader who saw `1/5` in full type above three thin rows read the turn as standing at one of five when it stood at four. So the last snapshot that moved anything draws in full as well (the state still standing where the reader stops), and the lines between it and the opener are made to state a MOVE and never a level: `0→1 of 5` rather than `1/5`, **absent entirely where the count held**, since a bare figure in the far-right slot is where every other UI puts what is true NOW and each of these is a stamp from earlier. The one move a finished/started pair reads as a completion and is not — the baton passing to a new task while the one it leaves stays open — is named on the row (`parked`), because otherwise the active row advances, nothing is ticked, the figure holds, and the count looks broken rather than honest. **A bar per ALLOWANCE rather than one per account**: a plan's 5-hour session and its week run out separately and reopen days apart, so a single bar at whichever is tighter left "87%" meaning either an hour's wait or the rest of the week rationed, with nothing on screen to say which. Each pool draws its own bar beside the LENGTH of the window it measures (`5h`, `wk`, `wk · Opus` where a plan meters a model separately), which is the only part of a pool's name that fits a 240px column and the part that says what the percentage costs. It appears only in width no pane can use — the transcript stops widening at its reading measure, and that surplus and only that surplus is what the rail takes ([`chatCapacity.ts`](src/features/chat/panel/chatCapacity.ts), `railFitsBeside`) — and it lists offers rather than accounts. **What holds an account off it is exhaustion**, not the 90% at which the rest of the app turns a number red and not any allowance the account happens to have run out of: only a pool that gates EVERY model, at the point a call is certain to be refused (`SPENT_UTILIZATION`), plus the two states no reading can contradict — a dead credential and a withdrawn account seat. A plan with a tenth of its week left runs the next task, and a full weekly Fable slice leaves the same sign-in serving Sonnet all week; both used to vanish from a column headed "Ready to run" while the Usage tab beside it showed them open. A provider with nothing left is named underneath with the instant it comes back, because an absent row otherwise means both "spent until Sunday" and "never connected". **A credential nothing can run on is counted rather than absorbed**: an expired sign-in, or a Google account the translator benched for having no Antigravity project, holds an untouched weekly allowance and can still serve no turn, so it is kept out of the ratio the heading prints (`1/31`, never `1/33`) and named underneath in the words of what it is missing (`blockedReason`, [`usageStatus.ts`](src/features/chat/session/usageStatus.ts)) — connecting one otherwise moved the bottom half of that ratio and nothing else, which reads as a fleet that just lost its last room. The Usage tab's plan-limits panel bands the same fact (`can't serve`, beside the capacity bar rather than inside it) and raises those accounts grouped by condition, since the fix belongs to the condition and not to each name. **The nine cards that ask the user something** — a plan, a question, a permission prompt, the browser and terminal help asks, the service, payment and capability offers, and a gated credential's release — are one shell ([`ChatCard.vue`](src/features/chat/transcript/cards/ChatCard.vue)) rather than nine hand-written copies of the same four lines of markup, which is what they had drifted into being: three different header tiers and two different opinions about a divider, across cards a user answers in the same turn. **None of them carries a ground or a rim**, so what holds one together is a single text column: the shell states the inset it starts at, the box its leading glyph sits in and the gap between the two, and the header, the body, a question's options, the document a card is about and the answers row all derive their edges from those three (`panel/chat.css`). Each supplies its own body and its answers; how it says it is settled is [`cardStatus.ts`](src/features/chat/transcript/cards/cardStatus.ts), one function per card instead of a chain of `v-if` spans inside the template. **The question card is the one with state of its own** ([`ChatQuestionCard.vue`](src/features/chat/transcript/cards/ChatQuestionCard.vue)): picks, typed answers and a draft mirrored per request id, so a half-answered card survives a reload; its options draw as a list on that column rather than as boxes, a wash marking the chosen row the way it does in every other list in the app. **The release card is the only one whose buttons may not be the reader's to press**: the owner gated that credential to an exact list of people and the daemon checks the verified identity on the reply, so the card names its approvers and greys its buttons for anybody else — a courtesy over a server-side rule, not the rule itself. **The permission card is the one with real work in its body** ([`ChatCommandBlock.vue`](src/features/chat/tools/ChatCommandBlock.vue)): a held command arrives as a program, not prose, so it is syntax-highlighted, and the daemon's own offsets say which fragment the rule stopped it for — [`commandPieces.ts`](src/features/chat/tools/commandPieces.ts) merges those two rulers (a mark edge cuts the colour token it lands in, both halves keep the colour) the way `pages/workspace/searchSnippet.ts` already does for a search hit. Everything unmarked is dimmed rather than recoloured, so the grammar still reads while the eye lands on the mark. When the owner has switched on the quick model's plain-sentence pass, the sentence leads and the command folds behind a labelled disclosure — never a hover (no touch or keyboard equivalent, on a safety prompt) and never a tab — with the marked fragments staying on the card either way, because hiding the command may not hide the evidence for why it was held.
- **[src/features/sandbox/gates/](src/features/sandbox/gates)**: the sandbox connect/authorize gates and switcher wrapping the workspace surface. A full gate is reserved for blocked causes, a reported removal, or a sandbox with no successful workspace snapshot; even an empty cached workspace remains mounted while transient failures recover automatically. What the gate SAYS is [`connectionNotice.ts`](src/features/sandbox/gates/connectionNotice.ts), a pure function of the classified failure plus what the platform knows, under one rule: **a wait is called a wait only while waiting can still repair it**. Past that it names a cause, and only a cause that was established — the edge's verdict that no tunnel is dialled in, a removal the removing machine reported, a refused wake. Silence establishes nothing, so silence becomes "this has gone on too long" with a door to the setup screen, never an accusation that a sandbox behind a closed laptop lid was deleted. The spinner follows `notice.waiting`, which is what keeps one off an ending. The one wait it does explain is a restart this browser asked for ([`live/sandboxRestart.ts`](src/features/sandbox/live/sandboxRestart.ts)): for two minutes that outranks every silence-shaped cause under it, the edge's `no-tunnel` verdict included — true of a container being replaced, and read as a fault by whoever pressed the button that replaced it — and then hands back, because a restart that never came back needs the words that come with a door.
- **[src/shell/hub](src/shell/hub)**, the shell both hubs are drawn with — the sandbox hub's index (This box · Configuration · Reach · Added by extensions) and the settings hub's — and the one thing a row says that the section cannot: **what is running behind it**. A hub mounts one section at a time, so the rebuild started on Environment leaves nothing on screen the moment Devices is opened, and these are the runs that take minutes. [`hubWork.ts`](src/shell/hub/hubWork.ts) is a module-scoped ledger of work in flight per row, so a run outlives the card and the section that started it and the mark ends when the work does, not when the reader clicks away; [`HubLayout.vue`](src/shell/hub/HubLayout.vue) provides each section its own address, so a card reports its run without being told which row it lives on — the same host-recreate button sits on Environment and on Overview's update card, and each reports where it was pressed. The mark itself is the icon rail's: the turning spinner in the one link ink [`viewBadge.ts`](src/core-views/viewBadge.ts) keeps for live work, beside the count chip rather than inside it, because a run is not an errand and a plate would make it look like one. Work nobody in this browser started is followed by whoever owns its query instead — a hosted sandbox's environment build is read by [SandboxHub.vue](src/features/sandbox/SandboxHub.vue) itself for that reason, since the section it belongs to is closed while it matters most. **The row's mark stops at the hub**, and four of those runs do not: a rebuild from a checkout, a hosted environment build, a staged update and a host recreate all end by REPLACING this sandbox's container, which reaches the reader wherever they are as a workspace that stops answering. [`live/sandboxRestart.ts`](src/features/sandbox/live/sandboxRestart.ts) is the ledger that survives that — mirrored to localStorage, because the container serving the page is the thing being replaced — and it holds an expectation, never a notice: the sandbox tile carries the turning mark while the work runs ([SandboxSwitcher.vue](src/features/sandbox/gates/SandboxSwitcher.vue), the Menu tab on a phone), the lane and the gate say what the silence is only once there IS one, and the outcome is delivered as a receipt by [`live/restartWatch.ts`](src/features/sandbox/live/restartWatch.ts), which follows the runs from the session root for the same reason the ledger exists: the screen that draws a build in full is the screen nobody is on when it lands.
- **[src/shell/presence](src/shell/presence)**: collaborator presence avatars/stack.
- **[src/push](src/push) + [src/shell](src/shell)**, how a notification reaches this device, and how the app knows when it is inside a native frame. One flow ([`composables/usePushNotifications.ts`](src/push/usePushNotifications.ts)) over two transports behind one driver seam ([push/driver.ts](src/push/driver.ts)): every browser (the Play-store TWA included) is web push straight from the daemon ([push/webPush.ts](src/push/webPush.ts)); the iOS shell ([\_editor/ios-app](../ios-app)) has no web push, so [push/nativePush.ts](src/push/nativePush.ts) registers the APNs token with the platform's push relay and stores the grant on the daemon as its channel. [shell/capacitor.ts](src/shell/window/capacitor.ts) is the ONLY place the injected native bridge is named (no Capacitor dependency exists in this package) and [shell/notificationTaps.ts](src/shell/notifications/notificationTaps.ts) is the native twin of the service worker's click handler, turning a tapped notification into the in-app route it points at. The **desktop app**'s frame is the third of these, and the only one the app draws part of: its window is undecorated ([\_editor/desktop-app](../desktop-app)), so the app draws the window's three buttons floating in its top-right corner and nothing else ([shell/window/WindowControls.vue](src/shell/window/WindowControls.vue)), and the page itself is the handle: [shell/window/windowGesture.ts](src/shell/window/windowGesture.ts) moves the window from the band along the top edge and from every empty stretch of background, leaving controls, lines of text, scrollbars, seams and overlays to themselves; a press it takes refuses `selectstart` until the button is up, because the webview answers a press on the background by anchoring a selection at the caret position NEAREST it — a line of text somewhere else on the screen entirely — and then extends it over the very travel that asks for the drag, and because the platform's move loop swallows the button's release, so a selection begun under a drag outlives it. [shell/window/controlsReserve.ts](src/shell/window/controlsReserve.ts) finds, from live geometry, which row of the layout runs into the buttons' corner and has to give up its right end. It is mounted at the app's root rather than in the shell for the notification lane's reason: a login screen, a gate and the mobile chrome a narrow window gets are all screens somebody has to be able to close the app from, and a popped-out panel is a fourth (below). Every press is an `intentic://window` link, the drag included — that window has no IPC at all. The same link is how the page does to its own window the three things a browser lets only a popup's script do — close it, raise it, widen it ([`environments/desktop.ts`](src/app/environments/desktop.ts) `closeOwnWindow`, `raiseOwnWindow`, `widenOwnWindow`): a browser popup gets `window.close()`, a window of the app gets `do=close`, answered on the window that sent it. A fourth entry there is not about the app but about a hole in its webview: WebView2 hands the app a `window.open` and a named target, and drops a `target="_blank"` press without raising anything, so every link out of the app drawn that way — provider sign-ins, docs, an agent's markdown link — did nothing at all inside the app. [`installDesktopLinks`](src/app/environments/desktop.ts) catches that press on the document and re-issues it as `window.open`, the shape the app does hear; it is installed from [`main.ts`](src/main.ts) rather than the shell, because the screens with the most such links (login, setup) are outside it. Where to DOWNLOAD the app lives apart ([`environments/desktopDownloads.ts`](src/app/environments/desktopDownloads.ts)), because that needs the deploy config and this module has to load wherever `floating.ts` does.
- **[src/skins](src/skins)**, whole-interface looks, as opposed to the colour the accent picker sets: one stylesheet per skin, each scoped to a `data-skin` attribute on `<html>` and therefore inert until Appearance selects it. The one here, `sanctum.css`, is the marketing site's own design system worn by the app (ash stone with a whisper of tooth in it, one gold rule, a flat unlit shadow for the rail and the overlays, stone and bronze plaques for the two filled button tiers, eased corners, and the app's own type in all of it), and it works by restating the design system's surface ramp, role tokens and radius scale rather than by naming a thousand components. It keeps one rule that is worth reading the notes for: **every surface a word sits on is flat in the low frequencies and opaque**, so a gradient never lands under the reading, while a fine speckle, which has no low frequencies to vary, may. `useSkin.ts` owns the attribute and the preference — and the preference holds `system` until somebody pins it, which resolves to sanctum under the dark scheme and to nothing under the light one, so the app's default look is the reader's OS's answer rather than a stored `sanctum` worn over daylight. The directory is the whole feature: [its README](src/skins/README.md) lists the four call sites that reach it, so removing skins is deleting it and undoing four lines.
- **[src/styles](src/styles)**, one generated sheet: every face this app serves, self-hosted (`faces.css`, rewritten by `node _tools/scripts/fonts.mjs`), so a workspace that is offline, air-gapped or behind a content blocker renders in the type it was designed in rather than in the system fallback. The **entry screens' material** used to live here too and no longer does: the marketing site's metals, ink, carved display type, frame kit and two button plaques are [`@intentic/entry-css`](../../_shared/entry-css/README.md), scoped to `.entry` and therefore inert on every route but the four a visitor can meet before the app: `/login`, `/setup`, and the desktop app's two handoff screens, `/desktop-auth` and `/desktop-auth/complete`. Those are the last stretch before the app's own look takes over — a visitor meets them within a minute of leaving intentic.dev, having picked no accent, no scheme and no skin — so they are dressed as the page they came from rather than as the workspace they have not seen. It lived inside `Login.vue` until `/setup` needed the same stone, which is the whole reason it is a file: the door and the rooms behind it share the material and differ only in composition. It left this package when a **fifth** screen needed it — the desktop launcher ([\_editor/desktop-app](../desktop-app)), which is what `/setup` hands the install to, and which is not a route of this app at all. The seal (`.entry-seal`) is there for the same reason the frame kit is: both handoff screens are one wait with a mark turning in it, and a copy in each would have drifted. Two things in [its header](../../_shared/entry-css/entry.css) are worth reading before editing it — why it restates `--color-*` and never `--role-*` (a custom property's `var()` is substituted where it is *declared*, so re-pointing a role token from a descendant changes nothing), and why the radius scale is deliberately left alone. It is imported **after** the skin, and the skin excludes `.entry` from its route-element backdrop by name.
- **Lazy-loaded sections** live in the feature that owns them: `features/auth/Login.vue`, `features/setup/Setup.vue`, `features/sandbox/SandboxHub.vue`, the infrastructure views under `core-views/`, `features/workspace/` (VSCode-like explorer + file viewer; **the editor section is two panes**, see below), `features/capabilities/Capabilities.vue` (the rail's "+": static core cards merged with cards derived from ENABLED extensions' `contributes.capabilities`, a config form with a live "This will add to your sandbox" effects panel), `Secrets.vue` (the capability-secret inventory, where the owner also names who has to release a credential before the agent may use it), and the `*Dialog.vue` overlays.
- **[src/preview](src/features/preview) + [src/composables/preview](src/features/preview)**, the live app preview: an evidence-driven Preview rail tile whose one panel shows the real dev server (clickable, hot-reloading) full-bleed under a single toolbar strip, in the `/preview` section or a pop-out window on the chat's machinery. It previews five kinds of thing: a repository's dev server, one app inside a monorepo, a **forwarded port** (the answer for a server nothing here started), the workspace's served `public/` page, and **any address the user types**, because a discovered list is a closed one. `previewModel.ts` is the pure half, what counts as previewable, which target the panel lands on unasked, and **the one list both the panel and the rail tile are built from**: the tile's badge previously used a second opinion about what counts, so a monorepo with no `_apps/` badged "1 running" over a panel saying there was nothing to preview. `usePreviewTargets.ts` wires it to the live `/panels`, per-monorepo `/apps`, `/ports` and `/public` reads; `previewSurface.ts` holds the panel's own existence, selection and typed address (once opened it stays mounted, parked behind its tile, so the previewed app's state survives every trip to the code). The workspace tree's per-repo eye routes here; the per-repo iframe tab it replaced (the preview extension's fallback directory view) is gone. **Nothing is framed until the address answers for itself**: the panel probes the daemon's preview proxy over a CORS-open path (`@intentic/ui` `portPreview.ts`, the daemon's `PREVIEW_PROBE_PATH`) rather than treating any settled request as reachable, because an address that reaches no sandbox still gets an answer, the edge's own 502, whose `X-Frame-Options` renders inside the iframe as a bare "refused to connect" with nothing to act on. Everything the panel cannot frame is a screen with a way out instead: an address that reaches no sandbox, a repo still installing, and the ordinary monorepo whose `dev` fans out across packages that pin their own ports, which no single hostname can stand for and which the panel resolves by forwarding the one server the user picks (`usePreviewTargets.forward`, which lands on the forwarded port's own target).
- **[src/features/sandbox/extensions/SandboxExtensions.vue](src/features/sandbox/extensions/SandboxExtensions.vue)**: the sandbox hub's Extensions section, **one index row with two pills** (`?view=browse`) over one shared search box: [ExtensionsInstalled.vue](src/features/sandbox/extensions/ExtensionsInstalled.vue) is what this box has, with the on/off switch, the purpose sections and the pinned "needs attention" group; [ExtensionsBrowse.vue](src/features/sandbox/extensions/ExtensionsBrowse.vue) is registry discovery. They were two hub rows (Extensions and Discover) and the merge is what puts the registry's update count on the row that can act on it, keeps the search text across both halves (so "nothing installed matches this, one published extension does" is a thing the surface can say), and leaves the section owning the instrument: pills, search, create, host reload, and the "updates checked …" line. In Browse, official rows are actionable only with current deterministic-scan and agent-audit evidence bound to the full source identity; the detail panel separates those checks from optional human review and states that manifest permissions do not confine browser code.
- **[src/features/sandbox/overview/SandboxAgent.vue](src/features/sandbox/overview/SandboxAgent.vue)**: the Agent tab, twenty setting groups behind a five-pill strip (`?section=`, default writes no param). The pills name **parts of the agent** — Models, Instructions, Tools, Safety, Finishing — and that single axis is the point: they used to name a subject three times (Accounts, Instructions, Safety) and a phase of a turn twice ("How it runs", "Landing work"), so nothing told a reader which axis their question was on and a setting was found by sweeping all five. Two placements are load-bearing and a split page can quietly undo either. **Every model in this sandbox is chosen on Models**, the safety judge's included: [AgentSafetyJudge.vue](src/features/sandbox/agent-settings/safety/AgentSafetyJudge.vue) names the model applying the policy and links to Models rather than holding a second picker, because "where do I choose a model" may not have two answers. And **both delegation controls are one group under Tools**, described in the Safety bullet below. `?connect=<provider>` outranks `?section=` (it is a request to sign in, and the account list leads Models), and Models being the default is what keeps the composer's bare `/sandbox/agent#models` landing on the anchor it names. **Models is itself several groups, and the catalog decides which row is in which**: [AgentModels.vue](src/features/sandbox/agent-settings/models/AgentModels.vue) draws one group per entry of the contract's `MODEL_ROLE_BLOCKS` (`model-roles.ts`) — one-shot helpers, the runs a click of yours starts, the runs that start without one — plus the cheaper-turns setting that is not a job at all. That is a landmark rather than a taxonomy: every job in the sandbox picks its own model, which is a page-long list, and the blocks are the distinctions the role table already makes (`kind`, `trigger`) rather than headings this page keeps in step by hand. A job's mark and its selection tick share one slot in [ModelRoleRow.vue](src/features/sandbox/agent-settings/models/ModelRoleRow.vue) — the glyph at rest, the box under the pointer and on focus — and an unset row states itself in a chip beside its name instead of the paragraph it used to spend under every row. **Each group is read in one of two views, and the switch sits in its own heading**: Advanced is that row-per-job list, Simple collapses the block into a single ordered list ([ModelGroupRow.vue](src/features/sandbox/agent-settings/models/ModelGroupRow.vue)). Simple stores nothing of its own — it reads the entries every job of the block holds and writes back to all of them, so the two views cannot report different settings — and a group opens collapsed only while its jobs agree, since folding away a distinction somebody made on purpose is the one thing a simple face may not do. **A job switched off from another tab leaves its block's group gestures while it is off** — only the safety judge has such a switch (`commandJudge`, on Safety) — so the collapsed row does not count it, name it or write to it, the master box does not tick it, and it is not a reason the block reads `jobs differ`: a row this page is refusing presses on is not a disagreement anybody could resolve here, and its own list is left standing for the day the judge comes back on.
- **[src/features/sandbox/agent-settings/behaviour/AgentRepoChecks.vue](src/features/sandbox/agent-settings/behaviour/AgentRepoChecks.vue)**, under **Finishing** and directly beneath the sandbox-wide checks: what each REPOSITORY declares for itself (`<repo>/.intentic/checks.json`, read through [useRepoChecks.ts](src/features/sandbox/environment/useRepoChecks.ts)), and the one decision about it that is the owner's — whether it runs. It sits here because this page is where somebody comes to ask "what happens when I push?", and an answer that lives only in a file tree is not an answer; the row above it is named **Before every push** for the same reason, since one command standing for four repositories is the thing this group exists to stop. The commands are printed in full rather than counted: the switch is somebody agreeing to run a command written in a file they may not have read, and "2 checks" would be asking them to agree to nothing they can see. The same row component serves the repository's own folder ([DirectoryChecks.vue](src/features/workspace/directory-ui/DirectoryChecks.vue), opened from the tree's shield — standing, like a persona's mark, because the file is a fact about that folder rather than an action available on any folder), so the two surfaces cannot drift into describing one file differently. A declaration that changed since it was adopted reads as held everywhere it appears, which is the state the whole switch exists for.
- **[src/features/sandbox/agent-settings/safety/AgentSafetyPolicy.vue](src/features/sandbox/agent-settings/safety/AgentSafetyPolicy.vue)** and the Agent tab's **Safety** section: the only surface that writes the daemon's own gate, and it is a TEXTAREA rather than a row of pickers. It used to be six four-valued `Picker`s over `commandRules`, a verdict per kind of hard-to-undo shell command — and they are gone not because the controls were wrong but because the thing behind them was: the verdict came from a regex over the command text, so `echo "rm -rf /"` written into a README raised the identical card to an actual recursive delete, and no arrangement of six switches separates those. The daemon judges each flagged command with a model that reads this document instead (`.intentic/config/safety.md`, `GET`/`POST /safety/policy`). Two things to know before editing the section. First, it is TWO halves and the second is load-bearing: **AgentSafetyLog.vue** renders recent verdicts *including the allowed ones*, because nobody can author a policy for behaviour they cannot see, and "why wasn't I asked about that" has no other answer. Second, one rule is deliberately NOT in the document and is stated on the page as such — wiping a block device or deleting under `/history` always asks and cannot be edited away, because a model can be argued into anything by text inside the command it is judging. The spawn posture is no longer part of this section: it is a four-valued picker over `actionRules`' `agents.spawn` ([spawnPosture.ts](src/features/sandbox/agent-settings/safety/spawnPosture.ts) holds the merge, because `actionRules` is shared with the outbound sniffer and a replacing write eats every send rule) and it leads **AgentSubagents.vue** under **Tools**, where the numbers bounding the same activity already were. Starting an agent costs money and undoes nothing, which is the wrong question for a gate about irreversible commands, and keeping it here left one concept under two names on two tabs. Still a picker rather than prose, which is not an oversight: "may this turn start a child agent" is a fact about the call rather than a guess about what a string means, so a switch answers it exactly and prose would only add a way to be misread.

## Conventions

Chat state across windows has one read boundary: [`chatStrip`](src/features/chat/panel/useChat-strip.ts).
It carries the visible owner's tabs, focus, pane order and workflow selection. Fleet cards, workflow highlights
and synthesis read that projection; hidden windows' conversation objects are only local working copies.
[`chatEcho`](src/features/chat/run/chatEcho.ts) binds snapshots to the elected floating-window identity, the
restored sandbox and a monotonic revision. Ownership changes, focus and page restoration trigger reconciliation;
periodic roll-calls recover missed messages. Tab persistence includes workflow selection for reload and docking.
The authority and recovery rules are documented in [Chat state across windows](../../docs/design/chat-window-state.md).

The setup picker's **My own computer** option remains available during hosted provisioning. Switching waits
only for the platform to record cancellation; resource deletion continues independently. Late provision and
poll responses cannot restore the hosted selection or open its workspace, and the local install receives a
new identity and setup code.

- **`<script setup lang="ts">` SFCs**; state in `ref`/`computed`; shared state in composables (no Pinia). PrimeVue imported directly from `primevue/*`; register-once bits (theme, tooltip) via `installUi`.
- **vue-query for request/response** (`useQuery`/`useMutation`, keyed + refetchable); streaming (chat tokens, sandbox liveness) stays manual with `ref` + `fetch`/`EventSource`.
- **Navigation never waits.** A route registered as a bare `component: () => import(…)` hands vue-router a promise, and the router completes the navigation only once the chunk has arrived, the click freezes for the length of the download, charged to whichever destination is heaviest. So every in-shell section registers through [`components/asyncView.ts`](src/components/asyncView.ts): the route component is synchronous and the view flips in the same tick; the CODE arrives behind an outline the way DATA already arrives behind skeletons, gated by the one reveal-delay/minimum-hold threshold pair ([`@intentic/ui composables/loadingReveal.ts`](../ui/src/composables/loadingReveal.ts)) so a warm chunk paints no placeholder at all. An index-and-body page's outline is [`components/SplitViewOutline.vue`](src/components/SplitViewOutline.vue) wearing the page's real title; full-bleed surfaces get none, their honest placeholder is the shell's background, and each draws its inner skeletons once mounted. [`router/prefetch.ts`](src/router/prefetch.ts) pulls every registered chunk at idle, which is what makes the outline a cold-network-only sight, and what keeps a long-lived window's chunks in hand across a redeploy. The stale-window recovery ([`router/staleChunk.ts`](src/router/staleChunk.ts)) is split accordingly: `router.onError` still covers the entry-point routes that load at route level, and `asyncView` owns it for the in-shell views, whose failures no router hook can see, the reload guard re-arms on a chunk RESOLVING, not on a navigation landing, because landing stopped being evidence the moment it became unconditional.
- **Memory vs disk is a rule, not a per-query choice** (`queryPersistence.ts`, asserted in `storageRule.test.ts`). The query cache is mirrored to IndexedDB *whole* (one structured clone of everything ever cached, per write) so the cost of a single heavy entry is charged to every other write for the rest of the session. Small, shape-stable things (rosters, lists, trees, view contents) go to memory **and** that mirror, which is what makes a reload paint instead of blanking. Anything measured in hundreds of KB does not: a file diff is two whole file texts (or, past the daemon's cap, a patch of the changed regions) and stays in memory alone, bounded by `gcTime`; a chat transcript is worth surviving a reload and gets a **per-record** store of its own (`chat/transcriptCache.ts`), so its size is charged to itself. Heavy queries say so by carrying `UNPERSISTED` in their key, on the query, where it cannot be forgotten, rather than in a denylist somewhere else. This matters more now that the background loader fills the cache on the app's behalf rather than only what someone clicked.
- PrimeVue components + Tailwind 4 utilities + `@intentic/ui` (`Page`, `Card`, `Code`, `InfoHint`, `useTheme`, `useHighlighter`); markdown via `marked` + DOMPurify; code via Shiki (`useHighlighter`). Full-file review analysis runs in its own worker; Monaco keeps its separate editor/diff worker.
- **SSE/ndjson consume pattern** (see `conversation.ts` / `intenticStream.ts`): read the `ReadableStream`, split on `\n\n`, take `data:` lines, `JSON.parse` into the event union, fold into refs.
- **Nothing reaches for the user's own machine unasked, and nobody is asked twice.** The loopback shortcut ([`endpoint.ts`](src/features/sandbox/secrets/endpoint.ts)) is the one place the app fetches an address on the machine the browser runs on, and Chrome 142 and after answer that with a Local Network Access prompt — a dialog about "devices on your local network" that names no benefit and, arriving unbidden at first paint, reads as the app looking around someone's computer. So the reach is gated three times. It is not attempted at all for a sandbox whose machine the platform placed elsewhere (a hosted VM can never be a loopback hop away). Then the BROWSER is asked what it thinks, under `loopback-network` and, for a Chrome before the 145 split, `local-network-access` ([`loopbackPermission.ts`](src/features/sandbox/devices/loopback/loopbackPermission.ts)): a browser that holds the grant already, one that has no such permission at all (WebKit, Firefox), and a desktop-app webview that does not enforce it are all reaches nobody needs to be interrupted about, and a refusal recorded in Chrome's own site settings is final. Only what is left — a browser that will genuinely raise that dialog, about a sandbox that might genuinely be here — gets the card, which states the benefit in one sentence and waits for a yes ([`localShortcut.ts`](src/features/sandbox/devices/loopback/localShortcut.ts)). That yes is kept per browser, matching the scope of the permission it stands for; a no is kept per sandbox, so the day a user sets one up on the laptop in front of them the question is asked again. Any future call that leaves for `127.0.0.1` belongs behind the same gate.
- **The explorer is a file system, so a file gesture lands in the frame it was made in.** The daemon's agreement that a file moved is a fresh walk of `/work` — measured at roughly 300ms warm on one repository, seconds on a cold or larger one — and every tree write used to `await` it before repainting, so a rename snapped back to the old name for a beat, a deleted row sat there looking undeleted, and a newly named file was simply absent until the walk returned. What the explorer draws is now the daemon's listing plus [`provisionalEntries.ts`](src/features/workspace/files/provisionalEntries.ts): what this browser has done that the listing has not caught up with, in both directions — `arriving` merges a row in (an upload, a create, a copy or move destination), `leaving` takes one out (a delete, the source of a move), and a rename is one of each in the same frame. The overlay grew out of the upload placeholders, which had solved exactly this problem for dropped files and for nothing else. **Every entry retires against the real listing rather than a timer** (`reconcileProvisional`: an arrival once the path is listed, a departure once it is not), so the provisional row is REPLACED by the real one instead of vanishing and coming back; a refused write takes its own row back, which is what makes drawing the optimistic case honest rather than a lie with a delay on it. All of it hangs off one function in [`useWorkspaceTree.ts`](src/features/workspace/explorer/useWorkspaceTree.ts) (`settleEach`), which confirms or reverts each item's rows on THAT item's own answer — a bulk delete where three paths are refused keeps the seventeen that landed — and fans the writes out through a bounded pool, since the per-path serial loop it replaced made a twenty-file delete twenty sequential round trips. The refetch is fired and never awaited: the rows it will paint are already painted. Two things deliberately stay pessimistic: an editor save, because its `baseHash` conflict is a real outcome the reader has to see, and a tab closing on delete, because a tab that closes optimistically takes an unsaved buffer with it.
- **A land is the one write this review does not read.** Pressing Land on the board takes seconds — a rebase per repository, then the patch applied under the repo lock — and the whole of it fires the daemon's file watcher, so the workspace review used to rescan every repo against a tree the patch was still half written into. Each of those passes is `git status` plus a diff per row per repo (`git.scan`, measured at 1–12s on an eight-repo workspace), its answer is thrown away seconds later, and it spends the very git subprocesses the land is queued behind, so it made the land it interrupted slower. Meanwhile the panel kept printing the answer from before the press — "No uncommitted changes.", a claim about a tree nobody was reading. The signal for both halves is the roster's own `landing` status ([`changes/landing.ts`](src/features/workspace/changes/landing.ts)), not a second wire field: the daemon raises it on the land lease and drops it when the patch is in the tree, so what the board shows and what this panel says cannot disagree. While it stands the change query is **disabled**, not merely un-invalidated — with `staleTime` at 0, opening the panel is itself a read, which is exactly the gesture being complained about — and the held rows stay on screen under a strip naming what is being carried in, with the refresh control disabled rather than inert. Re-enabling is its own refetch, so the pause ends with the land whether or not this browser was the one that asked for it, which is what covers an automatic land as well as a pressed one. Only a land BETWEEN turns reads as `landing` (`agents-registry.ts`'s `statusOf` keeps a turn's own end-of-turn land at `running`); the rescan skip for that case is the streaming guard [`systemEvents.ts`](src/features/sandbox/live/systemEvents.ts) already had.
- **One busy flag must never answer a second gesture by doing nothing.** The workspace shares one action runner between the file tree, the phone's browser and the editor's Ctrl+S, and [`useAsyncAction`](../ui/src/composables/useAsyncAction.ts)'s re-entry guard meant a save pressed during a pending delete was discarded in silence, buffer still dirty, nothing said. `useConcurrentActions` beside it is the same reporting with no mutex: `busy` COUNTS rather than latches, so one spinner still covers a whole wave, and the notice is cleared when a wave starts rather than per action, so a failure survives the actions finishing around it. The mutexed one is still right for a single button that must not fire twice; the choice between them is now visible at the call site instead of being a property nobody knew they had inherited.
- **The editor section is TWO panes, and almost nothing knows it.** The workspace's tab strip splits in two ([`pages/workspace/workspaceTabs.ts`](src/features/workspace/tabs/workspaceTabs.ts) holds the model: an `EditorStrip` of a `main` pane and a `side` one, each with its own tabs, focus and preview slot; [`EditorPane.vue`](src/features/workspace/files/EditorPane.vue) draws one and the desktop lays out two with a `ResizeSeam` between them). It exists for one reading the single pane could not hold: **a document beside the file it names**. A commit's changed-file list, a package's architecture page and the codebase-health report are all full documents WITH FILE LISTS IN THEM, and in one pane a click on a row replaced the very list that was clicked, so reading a commit was tab ping-pong. Hence the one routing rule, in `useWorkspaceTabs.openDiff`: **a diff asked for while a `document` tab is focused opens in the other pane.** It is keyed on the active tab rather than on who called, which is what makes the second file clicked land where the first did (by then the focused tab is a diff, not a document). Everything else opens where the reader is, because the Changes and Checkpoints lists live in the sidebar and were never covered up. Three properties keep this from leaking: `tabs` / `activeId` / `activeTab` / `previewId` are the FOCUSED pane's, so Quick Open, the URL mirror, the chat's context chip and the phone are untouched; `normalizeStrip` guarantees **no empty half** (the side empties → the split is over, the main empties → the side takes its place), so no pane can sit there as a blank column; and a split is open exactly while the side pane holds tabs, so there is no second flag to fall out of step. The surface tells the store whether a split may be opened at all (`splitAllowed`, false on a phone and on a pane too narrow for two readable halves) rather than the store asking the layout anything, and a pane that has just become too narrow folds its companion back in instead of closing the reader's tabs. **The explorer stands aside for a split** and says so with a dot on the toggle that brings it back — as its own ephemeral state, never the stored `sidebarCollapsed` preference, the same two-pieces-of-state rule the narrow drawer uses, so a split never changes what the reader will find in their next session. The chrome each pane teleports into is scoped per pane (`viewerChrome.ts`'s `CHROME_SCOPE`), because a teleport addresses its target by DOM id and two panes with one id would put the companion's breadcrumb above the main pane's file.
- **A running command's output is a terminal, never a box.** `useTerminalPanel().openFocused(session)`; the dialog beside it holds the state and the buttons, and is not modal. The rule, its two look-alike exceptions and the reasoning are in [`composables/terminal/useTerminalPanel.ts`](src/features/terminal/useTerminalPanel.ts). Opening one names a session that may not exist yet, so the caller says what it started ("Running your pre-push check", and the command) and the panel waits for it: a standing wait that the daemon's own change feed resolves whenever the terminal appears, not a race that expires. After a few seconds it stops holding itself empty and says what it is still waiting for, with a shell one click away. **The pre-push check and the push itself are two instances of one shape**, a command the daemon runs on a click and reports as a `CommandRun`: one watcher follows either to its verdict ([`composables/workspace/runWatcher.ts`](src/features/workspace/push/runWatcher.ts), behind `usePrepush` and `usePushRun`), one module says how a run ended and composes the fix it proposes ([`composables/workspace/fixProposal.ts`](src/features/workspace/health/fixProposal.ts)), and one card floats the question ([`shell/PushQuestionBody.vue`](src/shell/notifications/PushQuestionBody.vue)). A refused push therefore reads exactly like a red check, command, terminal, "Fix with agent", and a fix is proposed only where the code is known to be wrong: the repository's own pre-push hook said no. A rejected ref or a dead host gets git's reason and Try again, on the rule that sends no agent after a check that could not run. **A failure has attempts, and at most one live one.** The fix conversation is named after the failing gates, so the card can read off the fleet roster whether an agent is already on it and show that in the button's one slot (a chip while it works or holds a fix, "Continue" once it ended, "Fix with agent" when nobody is on it or the last fix landed), and the press is decided at the press, against the fleet as it stands then ([`usePushFlow.ts`](src/features/workspace/push/usePushFlow.ts) over the contract's `planFixAttempt`): continue the ended attempt with a nudge rather than the whole prompt again, or "Start over", which stops and archives it and opens `-attempt2` on a clean worktree. Attempts are separate conversations on purpose: overriding one in place would rewrite a record another window is showing, which is the class of bug the popped-out chat had already met. **Closing that card is "off my screen", not "that never happened".** It is a `question`, and the only gesture for "not now" used to also destroy the only record of a verdict that had cost three minutes to reach — leaving running the suite again as the one route back to what it had already found out. The verdict now stands (`usePushFlow`'s `standing`): the outgoing block in [`ReviewPanel.vue`](src/features/workspace/changes/ReviewPanel.vue) states it and its age where the press that raised it lives — beside the ↑/↓ counts, not over them, since a refused push leaves exactly as many commits waiting as before it — the rail keeps its mark a tone quieter, and clicking either puts the whole card back — same words, same proposal, same override, same terminal. **A press over a tree nothing has been written to since is answered from it rather than measured again**, which is the point: the daemon's file watcher, not a digest of the change list, decides that ([`workspaceChangedSince`](src/features/workspace/changes/live/useWorkspaceLive.ts)), since an edit to an already-dirty file changes no path and no count. A written-to tree demotes the verdict to history in the same line ("files changed since") and the next press spends the suite; so does "Run again", for the reader who wants it regardless. Only a red suite is ever reprinted — a stopped run and one that could not start measured nothing, and a refused send is about the remote, not the code.
- **An irreversible action asks about the thing, not about the click, and the daemon has to hand it the words.** Killing a terminal ends a tmux session for good, and the strip is a row of near-identical pills with a hover-× four pixels wide, so one pill off is a build, a suite, or an editor's unsaved buffers gone with no account of what was lost. The guard could not be built from what the list already said: `running` is unconditionally true for a user's shell whether it holds a prompt or a two-minute build, and a confirm keyed on that fires on every close and teaches the reader to click through it, worse than no confirm. So the DAEMON was made to say what is actually happening (`command`, the live pane's foreground process, `system/system.routes.ts`), the strip shows it before anyone reaches for the ×, and the dialog asks "Kill the terminal running `pnpm build`?" rather than "are you sure?" ([`pages/TerminalPanel.vue`](src/features/terminal/TerminalPanel.vue)). The generalisation for the next one: a guard is only worth having where there is something to lose, it belongs on every route to the action (button, menu row, chord, not just the one that was reported), and if the app cannot name what it is about to destroy, that missing name is the bug to fix first.
- **There is one composer, and where it can be written from is a question about WHERE IT SITS, not about copies.** The chat's home is the side column or the rail ([`composables/chat/chatPanelLayout.ts`](src/features/chat/panel/chatPanelLayout.ts)), and on the rail it has no column: off `/chat` the panel used to teleport to the parking stage, so every other section — the file tree, the fleet board, an agent's review, settings — was a screen with no way to say anything, and the way back was a navigation that replaced what the reader was looking at. Three surfaces had already grown around that hole and each one is fixed by closing it: a board starter fills a composer, the "New agent" press asks for a caret, and a summons carries `caret: true`, all of which were landing in a box parked off screen. Its home is now [`ChatQuickBar.vue`](src/features/chat/panel/ChatQuickBar.vue), a pill floating over the bottom of the section publishing a fourth dock slot, and what it grows into is **the panel itself**, teleported, wearing a `bar` presentation that withholds the list and the transcript and draws one chat's composer. That is why a message half-typed in the strip is in the box on `/chat` a moment later, and why the model, the effort, the attachments and the live turn are that conversation's and not a second set: nothing here is built twice. **Where it draws is derived, never listed** (`chatParked`: this window draws the panel, the home is the rail, and no section has published the full slot), which answers "which views show it" by shape — every one where no composer is already on screen — rather than by a table that the next section would be missing from. **It floats rather than taking a row of the shell's grid**, because growing it must not reflow the page the reader opened it to talk about. **Open, the composer is the whole of it** — no frame around it, no title over it, no readout row under it: the box draws its own edge, and a second one around it read as a tray the message box was sitting in, while every word in those rows was about a chat nobody was looking at. That is also why `bar` now withholds `ChatPaneStatus` and the panel's own surface, and why nothing in that presentation clips: the `@` and `/` lists stand above a composer that has no room over it. **Its height is never a number.** Whichever of the two forms is not showing leaves the flow, so the box is the size of what is in it at both ends; measuring them instead — the pill's off the text size, the composer's off whatever it held — is what left it standing open at full width with nothing in it, having taken its reading while the panel was still parked offscreen. **What moves is opacity, translate and scale, and nothing else ever.** The box GROWS OUT OF THE PILL, and what grows is a CLIP: the composer is laid out once at full size and revealed through a window opening from the pill's own footprint (in percentages, so neither a long title nor a grown draft can put it in the wrong place), while the pill scales up past it and dissolves. A `scale` on the box was the first two attempts and both were wrong for the same reason — 0.9 is 82px on an 816px box, measurably animated and perceptually instant, and anything dramatic enough to read is the TEXT growing, blurred, which is a zoom rather than a box opening. **The curve is the other half of whether it is seen at all**: a heavy ease-out spent 74% of the width in its first 45ms, so the frames recorded a grow the eye never got; the one there now is still nearly pill-sized at 15% of its run and a third open at 30%. An `animation` rather than a transition, with no `forwards` fill, so the clip returns to `none` when it lands and the `@` list that opens above the composer is not cut by a box that has finished opening. **Closing is that run backwards** — same curve, a little quicker, opacity held until 60% so the box is watched shrinking into the pill rather than simply ceasing to be there — and `chat-quick-woken` is what keeps it off the page load: the host STARTS in the state that animation ends at, so without a flag saying this box has been open at least once, every reader would watch the composer shrink into the pill on arrival, having never opened it. It is one width (51rem) at every state with each form centred inside it, because animating a width put the composer through its own container queries on every frame — the control row wrapped and unwrapped and the model's name appeared mid-flight — and a size is the one thing here that cannot move without the layout moving with it. Recording the frames is how each of these was found rather than argued about: `rAF` sampling the rects and computed styles said, in order, that the first version did the whole swap in ONE frame (0 intermediate frames, a 48px jump); that a peek moved the composer itself 13px up and 38px narrower as the card landed around it, which is a box moving under a pointer aiming at it; and that `transition-[opacity,transform]` animated nothing at all, because **Tailwind v4 puts `translate-*` and `scale-*` on the `translate` and `scale` properties, not on `transform`** — the classes applied, the transition list never covered them, and they kept jumping. The strip's composer now keeps ONE rect through everything (`chat-footer-strip`): a peek adds room above it, never around it, and the card it needs is drawn by the strip itself, spilling 8px past the box either side and 12px under it, so the card grows AROUND a composer that does not move. **The peek's two halves arrive and leave together**, which is why `chatBarPeek` (the panel draws its turns) outlives `peekOpen` (they are wanted) by exactly the exit duration: the turns belong to the panel and cannot fade after the flag that draws them has dropped. Both mount with the peek, so the way in is an ANIMATION and only the way out is a transition — a transition has no earlier value to run from on the frame a thing mounts, and the rAF that would give it one sets the flag a frame late, which is a frame Escape can arrive in and close the wrong thing. **The one thing the box cannot answer on its own is "what did it just say?"** — so there is an eye in the box's corner, and hovering it lifts what `bar` withholds (`chatBarPeek`): the same pane's own turns, growing UPWARD so the composer never moves under the pointer. The eye is the way IN and nothing else: it is not drawn at all while the turns are up, since taking the pointer off the box is what closes them and a mark that rode to the top of the transcript to offer a second way was answering a question nobody had. (Escape still closes it first, for the keyboard.) What the turns are read on is GLASS AT THE BOX'S OWN RECT — no wider, and stopping at the composer's own bottom edge, where the composer's opaque box hides it — because a card that stretched past the thing being typed in is the tray this whole strip exists not to be. The top of that glass feathers rather than cutting the line it lands on, which is also the only thing saying "there is more above" once the scrollbar is gone (it has to be: a bar arriving with the peek takes its width out of the composer's). It folds away the instant the pointer leaves, ahead of the box's own grace — the transcript is what the pointer asked for, the box is not — and a press keeps it, which is also its only door for a keyboard or a touch. **Three rules came out of building it.** A pointer that merely crossed the bottom of the section gets the box and never the caret, because that edge is also the way to a scrollbar and to the terminal, and an opening that stole the keyboard then held itself open over the page the caret was taken from. The resting form is a pill the width of its own words, not a bar the width of the composer: a 22rem box with a short line in it and nothing on its right read as a text field nobody had filled in. It is the kit's own `ui-chip` on a plate the strip draws for it — the plate, not the control, is what carries the card fill, the blur and the shadow, because floating over someone else's page is the one thing a chip's 6% ink wash cannot do and the only thing this needed that the kit does not already own (radius, padding, hover, focus ring, and a 44px target on a coarse pointer). What it wears on its left is the fleet card's own identity mark, ring and all (`AgentCard` → `IdentityTile`), not an icon of this component's choosing: one chat has one face wherever it is named, and the ring is a reading rather than a decoration — the arc goes round while a turn runs — at 2.4s a revolution, since this is a chat saying it is busy, not a button saying it is loading — and shows how full the context window is when none does. The form that is not showing goes to OPACITY 0, never `display: none` or `visibility: hidden`: the caret a summons sends arrives in that same render, and an unrendered box cannot take it — so the hidden form stays laid out, measurable and focusable, and what keeps it out of reach of a click or a Tab is `inert`, an attribute, which flips in the render rather than over a duration. And a card waiting for an answer turns the pill into a door rather than a disclosure: permission and question cards are drawn in the transcript, which this presentation deliberately has none of, so offering a composer there would read as the way to answer something the composer cannot answer.
- **A panel in a window of its own is a WINDOW OF THE APP, not a picture painted from this one.** The chat, the sandbox-global terminal and the app preview each float onto `/floating/<panel>` ([`pages/FloatingSection.vue`](src/features/chat/panel/FloatingSection.vue)), where a full copy of the app boots and renders that panel into the same dock slot the in-shell section publishes. Which window draws it is ONE shared fact: the floating window announces itself on a heartbeat and every window reads three views off that beat, `floats` (it is in a window of its own), `here` (and that window is this one), `shows` (this window is the one drawing it) ([`composables/floating.ts`](src/shell/window/floating.ts)). A window that goes away without saying so stops beating **and** stops holding its liveness token, and a claim is retired only when both agree, so a dock, a close, a crash and a killed window are the same event. Both, because a beat alone cannot tell a window that is GONE from one the browser has merely stopped running on time: a minimized window is a hidden page, whose timers Chrome throttles to about one a minute once it has been hidden five minutes, so a beat a minute read against a 2.5-second deadline was a killed window, and the chat somebody parked on a second screen and minimized was reclaimed out from under them — its rail tile back, the app navigating itself to `/chat`, a second live copy of the conversation mounted here. The token is a Web Lock named after the claim (uncontended by construction, since the name carries the claim's own id): held for as long as that realm exists, released BY THE BROWSER when it stops existing, and therefore not a thing a throttled or frozen window can fail to do on time. A floating window that hears an older claim on its panel closes itself, which is why there can never be two. **This replaced the opposite bet and the whole class of bug that came with it**: the panel's DOM used to be teleported into a near-empty second page over the `window.opener` bond, which bought a streaming turn riding along without re-attaching and cost ownership (the panel obeyed one copy of the app, and a click in any other was invisible out there with both windows healthy), multiplicity (`window.open`'s target name only deduplicates inside one browsing context group, so two tabs meant two floating chats), and a three-valued liveness protocol with a veil, two deadlines and two graces to tell a live panel from a photograph of one. Popping out and docking re-attach now, a turn by its run (the daemon hands back the run's rows whole) and a terminal by tmux redraw, and that is the whole price. Everything downstream got simpler with it: `document` in this code is always this window's, "is anyone looking?" is one document's visibility ([`composables/onScreen.ts`](src/shell/window/onScreen.ts)), and an observer or an animation frame belongs to the window its elements are in by construction rather than by being re-homed on every move. **Inside the desktop app the same `window.open` gets a second native window** (`windows.rs` intercepts it and builds one at the same URL, with the same frame the page remembered; the call itself returns null, as a refused popup would, and the panel stays put until that window announces itself over the very same channel), so nothing above changes there: the two webviews share one browser profile, so the heartbeat, the lock and the chat projection cross between them exactly as they do between two tabs. What differs is only what a script may do to its own window, and that goes by link (`closeOwnWindow`, above) — the reasoning is in [Floating panels in the desktop app](../../docs/design/desktop-floating-panels.md).
- **A link pressed in a popped-out window lands in the APP's window, and the panel does not move.** A floating window is one panel and no app, so following a link inside it replaced the chat the reader had deliberately put on a second screen with a view wearing an icon rail — the file mention was right and the window was wrong. Every in-app destination reached from a popped-out panel is therefore an *errand* handed to a window that has the shell in it ([`composables/mainWindow.ts`](src/shell/window/mainWindow.ts)), which opens it and raises itself; with no such window left, one is opened, and a file errand waits on the doorstep for it to boot. Which window gets it comes off the same kind of heartbeat the panels use, a window announces itself **while something is floating** (nothing popped out, nobody asking, no traffic) and says when its reader was last in it, so with two app windows open the errand follows the reader rather than seniority. The errand is addressed rather than broadcast, because two windows both deciding they were the right one would open the file twice and fight over the focus. Two doors into it, and they are the two shapes a destination has: a **file reference** carries more than a URL can say (the line, whose checkout the path names) and rides whole through [`openWorkspaceRef`](src/features/workspace/files/openFileRef.ts), while every ordinary **link** is caught by one delegated listener in the capture phase ([`pages/FloatingSection.vue`](src/features/chat/panel/FloatingSection.vue)) — before a `RouterLink` acts on its own click, and on the `document` rather than the panel's box, because the panel's overlays teleport to the body and their links are links too. A modified click (new tab, new window) is left to the browser everywhere, as it already was for file mentions.
- **A secure-context api is not an api this app has.** `crypto.randomUUID` exists on https and on localhost and is simply undefined anywhere else, and "anywhere else" is a self-hosted instance opened at `http://192.168.1.x:port`. Every id in the app therefore comes from [`composables/uuid.ts`](src/lib/uuid.ts), which uses that generator where it exists and shapes the same v4 bytes out of `crypto.getRandomValues` (unrestricted) where it does not. This was not theoretical: the throw landed in the floating window's route setup, so that window booted, crashed, self-healed by wiping the origin's stored state, and came back an empty rectangle. Anything else reached for off `window` gets the same treatment before it ships.
- **`index.html` has to be able to paint one frame on its own.** Everything else here is downstream of a bundle that has not arrived yet — 1.6 MB over about 150 requests — and until it runs, `#app` is an empty container: the document paints the canvas and the skin's grain, and then nothing. On a warm browser that gap is a few hundred milliseconds and nobody ever sees it. On a cold start — a new machine, an empty HTTP cache, a webview profile being created underneath it — it is however long the download takes, and the desktop app's *first launch after an install* spent the whole of it showing a dark rectangle, which is what "I installed it and got a black screen" was. So the container ships with a **boot frame** in it: the lotus, one line saying what is happening, and its own `<style>` in the head, since the stylesheet is one of the things it is waiting for. `app.mount("#app")` empties the container, so there is nothing to take down and no frame with both on screen, and the 600 ms animation delay means a start that finishes inside it is never seen at all. After ten seconds a second line offers a **Reload**, because a start that is STUCK must not look like one that is merely slow; `isConnected` is how a mount that has already happened cancels that. It draws nothing that talks to the app and starts no navigation — inside the desktop webview, an `intentic://` link asked for before `load` aborts the very fetches this frame is waiting on ([`_editor/desktop-app`'s README](../desktop-app/README.md)). [`bootFrame.test.ts`](src/bootFrame.test.ts) holds the shape of it.
- **A sandbox's view state belongs to that sandbox, and may only show what that sandbox has.** Switching sandboxes is switching machines, so anything that names or arranges one machine's things is remembered per sandbox and re-read on the switch ([`composables/sandbox/sandboxScope.ts`](src/features/sandbox/client/sandboxScope.ts) is the one place that does the re-reading): the editor's open files, the tree, the chat, whether the terminal panel is open, and how its tabs were split. The second half is the part that bites: remembered state is restored INSTANTLY and the machine's own answer arrives over a tunnel, so a view must never draw a remembered thing as though it existed. The terminal strip is the worked example, its tabs are derived from the daemon's session list intersected with the remembered arrangement ([`composables/terminal/useTerminal.ts`](src/features/terminal/useTerminal.ts)), because a tab restored out of storage for a session that isn't there cannot be clicked, and sat unresponsive over a panel saying nothing was open. A list that FAILS is the same case with no recovery of its own, every other thing that relists reacts to a list that ARRIVED, so a request the daemon refused changes nothing anyone is watching. It therefore re-asks a few times itself, and an outage longer than that ends with a relist the moment the daemon is reachable again. Left alone, the pane sat empty over a sandbox whose shells were running, until a `+` click made it list by accident. **The waiting itself gets a shape** (the rule `chat/providerAccounts.ts` states for accounts): the strip holds the remembered arrangement's places as inert skeleton pills and says it is looking, rather than stating "No terminals open." about a question still in flight, three different facts (nothing here, not asked yet, asked and refused) that used to share one sentence. And a switch is not the end of those terminals either: coming back reattaches each one, and an attach replays the pane's history from the daemon's own tmux ([`features/terminal/terminalSession.ts`](src/features/terminal/terminalSession.ts)), so the output you walked away from is there instead of a fresh prompt, with nothing kept on this side to get stale.
- **…and it runs as more than one copy.** Every browser tab with the app open is a full copy with its own chat-tab state, and the chat panel is drawn by exactly one of them at a time (a popped-out chat is a window of its own). Everything the chat says to the other windows travels on ONE channel ([`composables/chat/chatChannel.ts`](src/features/chat/run/chatChannel.ts)), stamped with the sandbox it is about, so notes arrive in the order they were sent and a window pointed at another box drops them all. They travel as JSON, because the browser copies a posted message by structured clone and structured clone refuses a Vue proxy, which is what a tab's snapshot carries for the conversation's ref'd objects (its session, its displaced pick): a summons for any chat with a session in it used to throw `DataCloneError` out of the click that made it, after the local apply and before any other window heard, so a click on the popped-out chat's rail moved that window and no other. Three kinds ride it. A *summons* ([`composables/chat/summon.ts`](src/features/chat/run/summon.ts)): a gesture that shows something in the chat (a board card, New agent, an accepted suggestion, opening a run) is never a plain store call but a broadcast, and every window applies the identical reveal ([`reveal`](src/features/chat/panel/useChat-reveal.ts)) to its own panel; closing from the board is a summons for the same reason, since a card is the conversation seen from the board rather than a tab of the window it is drawn in. Gestures **inside** the panel act there, under the rules only that surface knows, and then say what they pointed at (`relaySummons`). Acts (sending a queued prompt) happen once, in the window that was pressed, and reach the others as the daemon-side turn they become. The *strip* ([`composables/chat/chatEcho.ts`](src/features/chat/run/chatEcho.ts)): the window drawing the chat publishes every open tab as a card would draw it, plus the focus and the panes ([`composables/chat/tabFacts.ts`](src/features/chat/tabs/tabFacts.ts)), and everything outside the panel — the fleet board, its ring, the cross-sandbox board — reads the chat through one projection, [`chatStrip`](src/features/chat/panel/useChat-strip.ts): this window's own tabs while it draws the chat, the published strip while it does not, never a mix. A window that is not drawing the chat still holds a tab list, but it is a *shadow*, frozen at the moment the panel left plus every summons since, kept only as the surface its own actions run on and replaced from the seed when the panel returns ([`composables/windowStore.ts`](src/shell/window/windowStore.ts)). Every defect the popped-out chat has had was a reader taking one fact from that shadow and another from an echo: a draft card swept because the shadow looked empty, an unsent chip kept because the shadow still held sent words, a card that vanished and came back because the shadow was closed a beat before the drawing window said so. The strip carries the first line of an unsent message, never the message, since a card only needs a name; that line, the mark and the message's age are said by one component on the board's card and the rail's row alike ([`components/UnsentMark.vue`](src/components/UnsentMark.vue)). The *set-aside drafts* ([`composables/chat/closedDrafts.ts`](src/features/chat/drafts/closedDrafts.ts)): the words in a composer are the one thing a close must not be able to destroy, so closing a chat that holds an unsent message keeps its whole tab in a per-browser store, the board goes on drawing the card (undated, like every card the daemon has no row for), and opening it puts the message back. Only the window drawing the chat sets words aside, any other window's copy being the frozen shadow; the words are claimed once, by the window whose gesture reopens the chat, and ride the summons to the rest (`claimedSummons`), because a store with one reader and a reveal with many otherwise gave the message to whichever window asked first — the board's, which draws no chat. The board's × is the other kind of close: the chat panel, popped out or docked, is an operating surface (the subset of conversations the reader chose to look at), so its × takes a chat off that surface and sets the words aside, while a card IS the conversation, so its × closes it everywhere and takes the words with it in one press, on a card whose mark and close hint say what goes (`closeConversations`, [`useChat-tabs.ts`](src/features/chat/tabs/useChat-tabs.ts)). When the tab holding the focus closes, from the rail or from the board, the focus goes to the tab it was on before, not to whichever sits last in a strip sorted by lane. **Closing the LAST card means nothing is open**, and the board has to agree: the panel always holds a conversation, so the close leaves a blank standing ([`Conversation.standIn`](src/features/chat/session/conversation.ts)) — an empty composer to start in — and that blank is the one open tab the board does not card (`unasked`, [`tabFacts.ts`](src/features/chat/tabs/tabFacts.ts)). Carding it put a "New agent" in the Active lane wearing the selection ring the moment anyone emptied their chat window, so /agents claimed a session was selected while the window that emptied itself showed nothing. A window with nothing to restore opens on the same blank, it rides the pop-out handoff as a blank, and it stops being one the instant it stands for something the user did — a word typed in it, a turn sent from it, a New agent press claiming it — with no promotion for anything to remember.
- **Opening a chat from a card is a LOOK, not an opening.** A plain click on a fleet card or a history row opens the conversation the way a single click in the file tree opens a file: as the strip's one *peek* ([`Conversation.peek`](src/features/chat/session/conversation.ts)), which lives while the reader is reading it and is swept by the same write that moves the focus to the next card (`transient` in [`useChat-tabs.ts`](src/features/chat/tabs/useChat-tabs.ts), the rule an untouched "New agent" draft already obeyed). Skimming a lane of forty agents used to leave forty tabs to close one × at a time, and what makes it cheap to sweep them is that a chat's TAB IS NOT THE CHAT: the conversation keeps its card on the board and its row in History, its turn runs on daemon-side once the sweep has detached from it, and words in its composer spare the tab outright whatever else is true. It stops being a look the moment the reader makes it theirs — typing, sending, answering a card the turn is parked on, a pick, a rename, a column of its own, walking to the agent's page, or the pin the card wears — and every one of those goes through the one verb (`Conversation.keep`), so a promotion cannot be half-made. The mark is the workspace tab strip's, an italic title, on the rail card, the docked header, the phone's strip and the board's card alike; the board presses its pin through the summons channel (`keep`, [`summon.ts`](src/features/chat/run/summon.ts)), because the tab it saves usually lives in the window drawing the chat rather than the one the press landed in. The flag rides the tab snapshot, which is also the handoff between the docked panel and its own window, so popping the chat out does not close the chat being read, and a restored peek comes back a peek rather than as the one tab nobody asked to keep. A phone has no focus to move, so there the screen being LEFT is the event that sweeps it ([`AgentDetail.vue`](src/features/agents/review/AgentDetail.vue)).
- **A preference is one answer per account, so it is declared, not hand-rolled.** Which colour the app wears, how big its type is, whether a transcript draws its tool calls, which model and account the composer opens a new chat on: every one of these is `definePreference` ([`@intentic/ui` `composables/preference.ts`](../ui/src/composables/preference.ts)), which owns the guarded read, the guarded write, the DOM apply and telling the OTHER windows, as one definition. The last of those four is the reason it exists. Each setting used to own its own copy of the first three and none of the fourth, so a change on `/settings/appearance` repainted the window the reader was in and nothing else, and the chat they had deliberately put on a second screen sat in the old theme until it was reloaded: not a stale render but a different copy of the preference, which is why nothing in the panel could have noticed. The change travels two ways on purpose, a `BroadcastChannel` posted by the window the choice was made in (the mechanism a floating window's own existence already rides, so it demonstrably reaches exactly this pair of windows), and the browser's `storage` event, which catches what a posted note structurally cannot: a `localStorage.clear()` from the self-heal path, the anti-flash script in `index.html`, a hand edit in devtools. Both land in one seam (`receivePreferenceChange`), and **adopting a change is not making one**: the window that hears it applies and stops, because `read` normalizes (a column width is clamped to what THIS window can hold) and a window echoing its own reading back would ratchet the wide window's column down to fit a screen it isn't on. The line against window state is the namespace: preferences are `ui-*`, a window's own view state is `intentic.*` and stays out ([`composables/windowStore.ts`](src/shell/window/windowStore.ts)), which is why `terminalOpen` sits in [`composables/useLayout.ts`](src/shell/window/useLayout.ts) beside fifteen preferences without being one. **The composer's remembered picks are the case that shows why hand-rolling one is not a style question** ([`composables/chat/turnDefaults.ts`](src/features/chat/run/turnDefaults.ts), [`composables/chat/accountPreference.ts`](src/features/chat/accounts/accountPreference.ts)): they were read once at load into a private ref, which was harmless while a popped-out panel was DOM teleported into a bare window and shared the opener's realm, and became a bug the day that pop-out became a router-backed window running its own copy of the app. Two windows, two copies, neither told about the other: a model or account chosen in the floating chat was invisible to the fleet board's window, so "New agent" pressed on the board built the conversation from whatever that window had loaded with — hours earlier — and broadcast it to everyone, which is the whole of "it keeps switching my model and account back". Declared, the pick travels the moment it is made. A per-sandbox preference keeps the sandbox id IN its key (`ui-chat-accounts-<id>`) so a replaced workspace's sweep still finds it. **And a preference is declared when its module LOADS**, which is the one thing left to think about: a window that never imports the module holds no such preference, hears nothing, and never applied the stored value either. Harmless for a setting read by the surface it governs, since the window drawing that surface is the window that imported it — and wrong for the three that paint `<html>` (the scheme, the base text size, the skin), which apply to everything and are read by nothing in particular. `useSkin` was imported by the settings page and nothing else, so a popped-out chat never loaded it: the window still LOOKED right on the way out, because the anti-flash script writes `data-skin` from storage on every load, and then never changed again for the life of the window. The same gap hid a second bug in every window, `applyFont` is the skin's, so the face a skin asks for was missing until somebody opened `/settings/appearance` on that load. Those three are therefore installed for every window in one place, from `main.ts` ([`composables/theme/documentAppearance.ts`](src/features/settings/documentAppearance.ts)), and a new preference that paints the document belongs in that list.
- **Anything that floats over the app is one channel with one host, and where it appears is not a per-component choice.** Eight surfaces had grown up independently and no two agreed on anything: a receipt pill at the bottom centre, a second copy of that pill on the fleet board with its own store, its own dwell timer and its own transition CSS; a loopback offer dodging the receipt lane at a hardcoded `bottom-16`; a stale-build card and a degraded-transport card both at the bottom right, at the same z-tier, neither able to know the other existed, so whichever appeared second simply sat on the first; an upload panel underneath both by nothing more principled than its z-index; a failed push and a busy sandbox each taking the top of the viewport from a different tier; and the composer saying "The sandbox is busy" as raw text at the same moment the gate said it in a pill. Position said nothing about what kind of message it was, only about which file drew it, and that is not a system anyone can learn. There is now one store ([`composables/notifications.ts`](src/shell/notifications/notifications.ts)) and one lane ([`shell/NotificationHost.vue`](src/shell/notifications/NotificationHost.vue), mounted by `App.vue` above the router and outside any session), and the only thing that varies between items is how long they stay and what can be pressed on them — which is the thing that should vary. **Three kinds carry that difference**: a `receipt` happened and is over, so it retires itself and needs no acknowledgement; a `condition` is TRUE RIGHT NOW, so it stays exactly as long as it is true; a `question` is owed an answer, so only answering or waving it off retires it. **The two halves of the store are shaped by that split.** A receipt is imperative (`say`, `warn`): it happened at a moment, there is no state to read, one at a time, newest wins, because two stacked receipts is a notification centre and the second is always the one the reader wants. A condition or a question is DECLARED (`hold`) as a pure function of state, re-read every tick, with no `raise` and no `remove` — which is what makes "on screen" and "true" unable to drift apart, and why Dismiss runs the OWNER'S callback rather than splicing a local list the next tick would argue with. Every source is declared in one file, in a deliberate order ([`composables/notificationSources.ts`](src/shell/notifications/notificationSources.ts)); an item whose content is not two strings (a composed agent turn, an upload's per-folder progress) hands the lane a body component. **The stacking order is geometry, not severity**: the column is anchored to the bottom of the viewport and grows upward, so its last child never moves and its first child is the one that does. Receipts go on top, because the thing that appears and vanishes several times a minute must not shift a card someone is reading or reaching for; questions take the corner, the one position in the lane that is fixed. **The line against the in-flow `<Notice>`** ([`@intentic/ui` `components/notice.ts`](../ui/src/components/feedback/notice.ts)) is what the message is ABOUT: the lane is for the app and the session, and a failure that belongs to one form, one panel or one chat pane stays beside the control that raised it, where two chats side by side can each say it about themselves.

- **What analytics captures is a legal document's subject, so it changes with one** ([`composables/analytics.ts`](src/app/analytics.ts)). `main.ts` boots PostHog for the whole SPA: autocapture, SPA pageviews, session replay, and the milestone events call sites send through `track()`; a resolved session is `identify`'d with the account's id, email and name. The privacy policy and the sub-processor list are written FROM that file ([`_site/site-content/src/legal.ts`](../../_site/site-content/src/legal.ts)), so a change here that alters what leaves the browser is an edit to those documents and to `LEGAL_VERSION` in the same commit, not a follow-up. **Replay is deliberately unscoped for launch, and that is a temporary decision.** The only mask is `maskAllInputs`, which covers what a visitor types into a field and nothing else, so a recording reconstructs whatever the workspace had on screen: Monaco's rendered file contents, diffs, transcripts, file and branch names — and the `defaults: 2026-06-25` snapshot carries canvas capture parameters too, so a project with canvas recording on gets the terminal as frames. The bet is full-fidelity replay while the funnel is being learned, against a promise elsewhere on the site that code stays on your machine, and the policy is written to match the code rather than the other way round. Narrowing it later is configuration rather than a project: `session_recording.maskTextSelector: "*"` records the shape of every page and the text of none, and `posthog.stopSessionRecording()` on entering a sandbox workspace leaves the pre-workspace funnel at full fidelity.

Navigation, controls and file marks use the shared [UI icon pack](../ui/src/icons/iconSets.ts):
simple Khmer-inspired outlines on a 24-unit grid, with consistent strokes and open interiors.
[RailIcon.vue](src/shell/rail/RailIcon.vue) and [HubLayout.vue](src/shell/hub/HubLayout.vue) resolve section
identities through the pack's `sectionIcon`, so a section keeps its mark in the rail, menus and hub index.
Unrecognised views use their declared icon, then their label's initials. The rail uses larger marks;
section rows keep their own smaller, more legible icon tier and highlight the selected mark with its label.
The pack renders native SVG throughout, including window controls and library-supplied checkmarks, loading
indicators and dialog controls. Custom agent-setting row leads inherit the same icon tier through their slot.
Monaco's editor controls, search toggles and completion symbols use the pack as SVG masks, replacing its
bundled icon font. The shared initializer installs these before a code editor or diff view mounts.

## How to extend

**Default: write an extension, not a shell edit.** A new user-facing feature (a sidebar panel, a file
viewer, a command) is a contribution to the extension system, not a new page baked into the shell. This is
the whole point of the lean-core split: see the extension system in [ARCHITECTURE.md](../../ARCHITECTURE.md).

- **New panel / section:** add a first-party extension under [`_extensions/`](../../_extensions) (a
  `intentic-extension.json` manifest + an `activate` that calls `api.views.register`), and wire it into
  [src/extension-host/builtins.ts](src/extension-host/builtins.ts). It reaches the daemon only through the
  routes its manifest declares, and consumes the shared UI slice via `@intentic/extension-ui`. Start from an
  existing extension (e.g. [`_extensions/activity`](../../_extensions/activity)) as the template.
- **New file viewer:** contribute a `viewers` entry from an extension (see
  [`_extensions/viewers`](../../_extensions/viewers)): the host owns the fetch and hands your component the
  bytes. Don't add a branch to `FileViewer.vue`.
- **New reading of a diff:** `viewers/FileDiffPane.vue` is the one fork every review surface renders (document,
  table, bytes, patch, text) and `DiffToolbar.vue` owns the reading control. A binary format joins the document
  reading by being readable to `fileq` and named in `explorer/fileType.ts` (`isDocumentPath`); its Before / After
  reading is whatever viewer an extension registers for the extension, mounted once per side. See
  [docs/design/derived-diff.md](../../docs/design/derived-diff.md).
- **New sandbox call from an extension:** add the daemon route, declare it in the extension's manifest
  route allowlist, then call it via `api.sandbox.json` (validate the response against the
  `@intentic/sandbox-contract` schema). An undeclared route is refused by the host.

**Reserved for core** (edit the shell directly only for these): the editor surfaces themselves
(`WorkspaceTree`, `CodeView`, `FileViewer`, chat), the router/shell scaffolding in `router/index.ts` /
`WorkspaceShell.vue`, and the three privileged core view contributions in
[src/core-views/coreViews.ts](src/core-views/coreViews.ts) (`infrastructure`, `live-status`, `directory-ui`)
that are coupled to platform/onboarding internals a clean extension must not reach. New client state for a
core surface: a composable exposing a module-level `ref`.

## Key files

- [src/features](src/features): one directory per feature, each holding its own screens, components and state; `src/router/index.ts` is the map of the whole app.
- [src/shell](src/shell) (the window around a feature: rails, panels, notifications, the command palette), [src/lib](src/lib) (dependency-free utilities) and [src/app](src/app) (this build of the app: diagnostics, updates, environments). `src/app/i18n/` is the editor's own message catalog — every word on these screens, keyed `<section>.<file>.<what it says>` — registered before the app mounts and by `vitest.setup.ts` for every suite. `features/workspace/health/workspaceScope.ts` holds the one that is easy to miss: WHOSE copy of the workspace the view is showing. An isolated conversation works in its own checkout, so a file link written in its chat carries that conversation (`/workspace/…?agent=`), the tree and every file read follow it, and a banner names it, otherwise the same path quietly opens the shared tree's different file. Scoped files are read-only.
- [src/features/chat](src/features/chat): the conversation panel, its tabs and tool cards. A tool card draws an ACT (a file
  written, a command run); the one exception is a DOCUMENT the turn wrote for the reader, which
  `ChatDocumentBody.vue` draws as prose, and which the question and plan cards carry as the subject they are
  asking about. The pictures a turn's tools showed the agent (a screenshot, an image it read back) also stand at
  that turn's end while its run is folded (`transcript/shots/`), and open one viewer that walks the whole
  conversation's pictures.
- [../../_sandbox/sandbox/bin/agents](../../_sandbox/sandbox/bin/agents), the fleet board: cards, detail, review.
- [src/extension-host](src/extension-host): how an extension's views reach the app.
- [src/router/index.ts](src/router/index.ts): the full route table.
