# Documenting a repository

Architecture documents live in the repository they describe, at **`docs/architecture/`**:

```
docs/architecture/
├── repo.json      the map: components, glossary, reading order (authored)
├── repo.md        the repository's own page, plain language + figures (authored)
├── index.json     GENERATED by `intentic-docs check` — never write this by hand
└── <pkg-dir>/     one directory per package, mirroring its real path
    ├── doc.json   oneLiner, keyFiles, provenance (authored)
    └── doc.md     the page (authored)
```

`intentic-docs` is on your PATH:

```sh
intentic-docs facts    --repo <dir>                  # packages, dependency edges, sizes, revisions
intentic-docs validate --repo <dir> --from published  # documents parse, anchors resolve
intentic-docs check    --repo <dir> --from published --write   # rewrite index.json (staleness, orphans)
```

## The rule that matters most

**If your change alters what a package is for, how it relates to its neighbours, or which files a newcomer
should read — update that package's document in the same commit.**

This is the whole anti-rot mechanism. A staleness checker can only tell someone later that a document is
probably wrong; the commit that made it wrong is the only moment when fixing it is cheap and the reason is still
in someone's head. You are usually that someone.

What does *not* need a documentation edit: renaming a local, adding a test, fixing a bug the document never
described, changing an implementation detail the page deliberately does not mention. Documents here explain
shape and intent, so they should survive most edits untouched. If every change forces a documentation edit, the
document is too detailed — that is a signal to cut it back, not to update it more diligently.

When you do edit one, bump its `provenance.generatedAt` and set `provenance.sourceRev` to the current revision
of that package directory (`git log -1 --format=%H -- <pkg-dir>`), then run `intentic-docs check --write` so the
index agrees with what you changed.

## House style

Write for a capable engineer who has never opened this repository and has twenty minutes. They want to know
what is here, how the pieces relate, and where to start.

- **Not an API reference.** No lists of exports, signatures or options — `iq outline <path>` gives those for
  free, and repeating them produces a page that is long, stale within a week, and unread.
- **Plain language.** Short sentences. Expand an acronym the first time. Prefer the plain word.
- **Say what is surprising, and why.** That sentence is usually the most valuable one on the page.
- **Give reasons where they exist**, and where you cannot find one, describe what the code does rather than
  inventing a rationale.
- **One screen per package.** Length is a budget, not a target.
- **Use the repo's own vocabulary** — `repo.json`'s glossary is there so every page means the same thing by the
  same word. Add a term to it rather than coining a synonym on one page.

## Figures

Figures go inline, at the sentence they illustrate, as fenced blocks whose language names the kind. The body is
JSON; a fence that does not parse renders as a plain code block, so keep it valid.

````
```dag
{ "title": "How a turn reaches the model", "direction": "LR",
  "nodes": [{ "id": "web", "label": "Browser app", "note": "Vue", "accent": "1" },
            { "id": "daemon", "label": "Sandbox daemon", "note": "one per box", "accent": "2" }],
  "edges": [{ "from": "web", "to": "daemon" }] }
```
````

````
```bars
{ "title": "Lines of code", "items": [{ "label": "_apps/web", "value": 77114, "display": "77.1k" }] }
```
````

````
```stats
{ "items": [{ "label": "Packages", "value": "53", "note": "18 with tests" }] }
```
````

- `direction` is `"LR"` (default) or `"TB"`. Edges carry no labels — use `"dashed": true` for a weaker or
  dev-only relationship.
- `accent` is `"1"`–`"5"` or `"neutral"`, and belongs to a **component**: reuse the slot `repo.json` gave that
  component in every figure, so the diagrams across the set agree with each other.
- `bars` is one measure per figure. Two measures of different scale are two figures.
- `stats` values are text — write the units you mean.
- Do not narrate a figure in prose as well as drawing it. Say the thing the figure cannot: what to notice in it.

## Anchors

`doc.json`'s `keyFiles` is three to six entries — where a reader should actually start, with a reason each:

```json
{ "keyFiles": [{ "path": "_libs/graph/src/compile.ts", "line": 42, "what": "RawNode map → validated graph." }] }
```

Paths are repo-relative and **must exist** — `intentic-docs validate` fails on one that does not, and a dead
anchor is the clearest possible evidence that a document is out of date. Keep them pointed at files whose
*purpose* is stable, not at whichever file you happened to read last.

## When you are generating a whole set

The map comes first and is one job: `repo.json` + `repo.md`, deciding the components, the glossary and the
reading order. Only then are packages documented, one at a time, each using the map's vocabulary and its
component's accent. Writing package pages before the map exists is how a set ends up with a different
vocabulary per page and no map at all.

Documents are written into `.intentic/docs/<repo>/` first — the same layout, staged — when a run is producing
them for the owner to review. Editing an already-published document as part of a code change is different: edit
it in place, in the repo, in your own commit.
