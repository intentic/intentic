# The sandbox daemon

The Node process inside every sandbox that owns the workspace, runs each agent conversation in its own git worktree, lands the result onto the main tree, and keeps its records beyond the agents' reach.

```mermaid
flowchart LR
    editor["Editor"] --> front["intentic-front<br/>ports · tunnel"]
    front -->|"Unix socket"| daemon(["daemon<br/>src/main.ts"])
    daemon --> actor["one actor per<br/>conversation"]
    actor --> runtime["runtime adapter<br/>Claude · Codex · ACP …"]
    runtime --> wt["worktree<br/>/history/worktrees/id"]
    wt -->|"land: patch as<br/>uncommitted changes"| main["main tree<br/>/work"]
    main --> verify["land check<br/>verify-deps.ts"]
    verify -->|"red"| route["who fixes it<br/>land-breakage.ts"]
```

## The process

- `docker-entrypoint.sh` starts sshd, then [`intentic-front`](../../_sandbox/front) (Rust), which owns every port and the ingress tunnel and supervises `node dist/main.js`. The daemon listens only on a Unix socket, so a daemon restart drops no connection.
- **The front owns sockets and bytes; the daemon owns policy.** Every listener, the tunnel, every upgrade splice, a terminal's WebSocket and tmux client, and a preview's relay are the front's, and none of their bytes pass through Node. Every decision about them is Node's, asked once over the control socket ([`front-wire`](../../_sandbox/front/crates/front-wire/src/lib.rs)): whether a terminal may open and onto which session, created where (the front composes the tmux command), and what becomes of a preview request, an upstream to relay, a page Node rendered to write, or the outbox to hand back. Either side asks the other under one envelope, an id answered or refused within five seconds. The git change feed ([`feed.rs`](../../_sandbox/front/crates/front/src/feed.rs)) is the one piece of the front that is neither: a counter with no policy in it, since Node names each checkout and decides what a generation is worth, kept native because its inotify fan-out over every `.git` is cheapest there.
- [`main.ts`](../../_sandbox/sandbox/src/main.ts) loads config, builds every service in [`composition.ts`](../../_sandbox/sandbox/src/composition.ts), runs the boot steps and opens the readiness gate.
- The wire is the oRPC contract in [`_shared/sandbox-contract`](../../_shared/sandbox-contract) (one `*.contract.ts` per route group), served by [`router.ts`](../../_sandbox/sandbox/src/router.ts). `/events` and `/agent/attach` stream; the browser view is a WebSocket opened with a one-shot ticket. The daemon does not serve the editor itself.
- Terminals are served by intentic-front, one tmux control-mode client per session shared by every viewer, always as a WebSocket, over TCP or spoken by the editor on a stream of the edge's WebTransport session where the edge declares one ([`term/`](../../_sandbox/front/crates/front/src/term/mod.rs)); the daemon only answers whether a socket may open and onto what ([`terminal-plan.ts`](../../_sandbox/sandbox/src/terminal/terminal-plan.ts)).
- The file tree is held in memory by the workspace watcher's thread ([`resident-tree.ts`](../../_sandbox/sandbox/src/workspace/files/resident-tree.ts)) and re-listed only in the folders a batch touched; the tree route answers from it, and `/events` carries each batch as a `treeChanged` delta tabs patch their tree with.

## Agents

- A conversation is the durable unit and a turn is one run inside it. One actor per conversation ([`conversation-actors.ts`](../../_sandbox/sandbox/src/conversations/actor/conversation-actors.ts)) decides whether a new message starts a turn, steers the running one, or waits in the queue.
- [`runtime-table.ts`](../../_sandbox/sandbox/src/runtimes/runtime-table.ts) picks an adapter per provider and harness: the Claude Agent SDK, Codex, OpenCode, Cursor, ACP agents and pi. What each runtime supports is declared in [`agent-runtimes.ts`](../../_shared/sandbox-contract/src/models/agent-runtimes.ts), so the editor never offers a control the runtime would ignore.
- A turn runs detached from any client ([`turn-runs.ts`](../../_sandbox/sandbox/src/agent/run/turn/turn-runs.ts)). It is journaled in `/history/conversations.db` and resumed after a restart; transcripts live in `/history/conversations/<id>/`.

## Worktrees

- An isolated conversation works on branch `agent/<id>`, with one git worktree per repository under `/history/worktrees/<id>/` ([`worktrees.ts`](../../_sandbox/sandbox/src/conversations/worktrees/worktrees.ts)). Parallel agents cannot collide.
- Where the runtime supports it (`isolation: "namespace"`), [`isolation.ts`](../../_sandbox/sandbox/src/conversations/worktrees/isolation.ts) binds the worktree over `/work` in a mount namespace and puts the real tree at `/mnt/intentic-main`; other runtimes only start in the worktree. `node_modules`, `.venv` and `dist` are overlay mounts of the main tree's, so a worktree needs no install.

## Land

- Landing applies a conversation's changes to the main tree as **uncommitted changes**. `HEAD` never moves; the owner's commit is the review boundary ([`land.ts`](../../_sandbox/sandbox/src/conversations/land/land.ts), `landAgent`).
- It rebases the branch onto main ([`sync.ts`](../../_sandbox/sandbox/src/conversations/land/sync.ts)), reconciles the lockfile, and checks every repository's patch before writing any: one conflict and nothing is written. The `merge` mode writes conflict markers instead, and `measure` is a dry run.
- After a land, [`verify-deps.ts`](../../_sandbox/sandbox/src/workspace/deps/verify-deps.ts) runs the repository's `land` check, else its `verify` script, else `test`, on the main tree in the background. It is the one check work gets, and nothing waits on it. One project is checked at a time, and lands that arrive during a run wait and are measured together in the next. Every door (the land that ends a turn, the Land button, the reconciler's installs) calls the one land check built in `composition.ts`. A land waits in the verify store (`.intentic/records/verify.json`) until a run with a verdict answers it: a run the heavy-command queue skipped, one past the watch window, or one cut off by a restart leaves its lands for the next, which measures them together, and the daemon queues that next run itself at boot. The watch window (30 minutes) starts when the check itself starts, not while it waits for a queue slot. Every settled run also measures again what the project's pushes left open. `GET /workspace/mainline` ([`mainline-status.ts`](../../_sandbox/sandbox/src/workspace/deps/mainline-status.ts)) is what the editor shows of it: the Main line in the Agents board's status bar (what waits, what is being checked, each project's last verdict, who is working on a red one, and what pushes left behind) and a status on each session card.

## After a red land check

[`land-breakage.ts`](../../_sandbox/sandbox/src/conversations/land/land-breakage.ts) routes a red run the same way every time, in this order:

1. More work landed while it ran: wait for that check, which may already be green. At most three times per red streak.
2. A conversation still working has unlanded changes in a failing package: hold, tell it once, and route when it stops or after 45 minutes.
3. Lay the failures at a land: the one land the run covered, else the lands whose changed paths share a package with a failure (the workspace packages [`package-graph.ts`](../../_sandbox/sandbox/src/workspace/deps/package-graph.ts) reads from `pnpm-workspace.yaml`, deepest first). Nothing is re-run to tell several suspects apart: one fresh conversation handed all of them costs less than a test run per suspect on a shared machine.
4. Exactly one land named, and its conversation still has the work in mind (prompt cache warm, under 60% of its context window, not archived, sent fewer than two times this streak): send the failures back to it.
5. Otherwise start a fresh fix-up conversation ([`land-fix.ts`](../../_sandbox/sandbox/src/conversations/land/land-fix.ts)) with the failures, each suspect's changed files, the exact `git diff <from> <tip>` and `agents show <id>` to read its conversation. Its id is `land-fix-<project>-<streak>`, so every attempt at one streak shares it, and a streak gets at most two attempts.
6. Past those limits the red waits for a person.

When a suspect is a spawned child and its parent's turn is still live, the parent is told which of its children the red was laid at, a few of the failures and where they went, once per decision ([`child-lands.ts`](../../_sandbox/sandbox/src/agent/subagents/child-lands.ts)), so it neither relays them to the child the router already sent them to nor starts a second fixer. The same parent hears when a child's work lands and when a press of Land on one meets a conflict. A parent with no live turn is not woken for any of it. A turn that starts on a child without its parent (the sandbox's own re-run of a failed turn, a watch it left, another conversation's message, the red sent back to it) is announced as `run.started` and taken into the parent's supervision ([`children.ts`](../../_sandbox/sandbox/src/agent/subagents/children.ts) `adoptChildTurn`): its roster row reopens and counts as live, and its ending reaches the parent like any other.

Blame is decided once, as the run settles, and filed on it (`suspects`, and `named` saying whether the changed paths narrowed them or they are every land the run covered); a red with nothing new in it is laid at nobody. `GET /workspace/mainline` serves each red project's streak as `red` (`since`, `cause`, `named` and the latest decision as `fixer`), each project's check terminal as `session`, and each failure split into `units` (`name`, `path`), so the editor's rail, cards and panel read one answer rather than re-deriving it. Every decision is filed on the run and shown in the editor. Each red has one record, the same shape whatever went red (`RedSchema` in [`mainline.ts`](../../_shared/sandbox-contract/src/schemas/workspace/mainline.ts): its findings, suspects, whether blame narrowed them, and every decision), kept in the verify store for a land check and in the CI store for main's CI, and one streak rule decides what continues a red ([`red-streak.ts`](../../_shared/sandbox-contract/src/state/red-streak.ts)); each source answers by its own policy (`RED_POLICY`: a land check routes itself, a push waits for the owner, CI starts its fix agent). A red land check wakes whatever reacts to `deps.broken` only when the router reported it with nobody sent, so no automation becomes a second fixer. What the router carries for a red streak (a red waiting on the next check, a hold and whom it told) is kept in the verify store too, and re-evaluated at boot: a hold whose conversations stopped while the daemon was down is routed, one still working gets its timer back. The sends are counted from the decisions filed on the streak's runs and the fresh attempts from the fleet's own roster, so neither resets on a restart. Every write to the verify store is published to the editor. With the owner's "Repair what breaks after landing" switch (`autoRepair`) off, all of it is only reported. A red streak's end logs `mainline: red streak ended` with how long it lasted.

## What a push left behind

The pre-push hook reports and never refuses, so what it finds has to outlive the terminal it printed to. The hook leaves a report in the repository's git common dir (`intentic-push-report.json`, written by [`push-report.mjs`](../../_tools/scripts/verify/push-report.mjs) in this repository). The report holds the findings the push itself brought in, a measurement of every check and the linter, and the command that measures them again. [`push-checks.ts`](../../_sandbox/sandbox/src/workspace/deps/push-checks.ts) files the report into `.intentic/records/push-checks.json` when the push moves a remote-tracking ref, and only once the pushed head is on that ref, so a refused push leaves nothing behind. What a project's pushes left is one more red, the same record as a land check's and CI's: the project's push Red (source `push`, scoped to the project) owes every finding still standing, begins and ends by the one streak rule, and files every decision about it. `GET /workspace/mainline` serves what each push found as `pushed` and every red it holds, land and push, as one list `reds`, and the editor shows what a push red owes amber as "Left at push".

- A finding stays owed until a measurement no longer prints it or the owner dismisses it; each is a decision on the red (`resolved`, `dismissed`, naming the findings), and an undo of a dismissal takes it back, the red that dismissal ended included. Three measurements count: every later push, a recheck on the owner's press, and the land check itself, which leaves its measurement of the checks in the same store (`verify.mjs`); the sandbox runs a recheck after it only for an open linter finding. The push report and the tree verdicts share one file in the git common dir ([`push-store.mjs`](../../_tools/scripts/lib/push-store.mjs)), and what a change added is measured one way by the land check, the push and the recheck ([`measure-change.mjs`](../../_tools/scripts/verify/measure-change.mjs)). A landed fix therefore clears its findings minutes later.
- A finding names what measured it by a free `source`, the repository's own word for it (a check's id, `lint`, a hook), with the command that shows it again and whether a later measurement can clear it (`recheckable`): the one `Finding` shape every red holds. A report from a hook that named only the older `kind` enum is read into a `source` at the file and nowhere else. Any repository's tooling can write the report.
- A push the repository's own pre-push hook refused reached no remote and left no report, so the daemon's push run ([`push-run.ts`](../../_sandbox/sandbox/src/git/ops/push-run.ts)) files it itself: a push marked `refused` whose one finding, owed by the project's push red, is the end of what the hook printed. The next push of the project, refused again or gone, settles it.
- Nothing is sent anywhere by itself. This is unlike a red land check: the push already went and the tree still works, so the owner chooses when to act. "Hand to an agent" (`POST /agents/push-fix`, [`push-fix.ts`](../../_sandbox/sandbox/src/conversations/fix/push-fix.ts)) opens one isolated conversation with every open finding in the project, and the refused push's own card makes the same call: the daemon plans the attempt, and the editor only asks for it. When the push red began sets its id, so pressing again while anything is owed continues the same attempt, and the hand-over is filed on the red as its `fix-up` decision.
- Some findings are not recorded: the ones the hook calls already failing before the push, and the ones the base could not be asked about. Findings from the assertion ratchet, the lockstep and rustfmt are about commits that are already pushed, so no recheck can clear them. They end only when dismissed.

## Checks

- A repository declares its checks in `.intentic/checks.json` for the moments `edit` and `land` (`RepoChecksFileSchema` in [`settings.ts`](../../_shared/sandbox-contract/src/schemas/settings.ts)). The owner adopts the file, and a changed declaration waits for re-adoption. The `turn` moment is retired: a declaration naming it still parses and is shown, but runs nothing and is no part of what the owner adopts (a repository adopted while it counted stays adopted).
- [`repo-checks.ts`](../../_sandbox/sandbox/src/rules/repo-checks.ts) turns edit checks into `file.edited` rules. They run on every file an agent writes, and their output returns in that edit's result without stopping the turn ([`file-edited.ts`](../../_sandbox/sandbox/src/rules/file-edited.ts)).
- Nothing runs when a turn ends, nothing sends it back to work, and no check holds its land. The owner's `turn.ending` rules and the built-in `verify-ui-edits` are retired like `turn`: the settings still read them, their stored conversion drops them, and a save refuses a new one (`SandboxSettingsWriteSchema`). What a turn showed of its own work is recorded as its card's `proof` ([`turn-settlement.ts`](../../_sandbox/sandbox/src/agent/run/settle/turn-settlement.ts)): verified, unproven, failing or no-code from the checks it chose to run after its last edit, and how many rendered interface files it changed without looking. The editor badges it.
- A "Checks after landing" note ([`mainline-note.ts`](../../_sandbox/sandbox/src/workspace/deps/mainline-note.ts)) tells each conversation that nothing checks its work when it finishes, what runs after it lands, and which failures main already has. It goes out with the opening message, after a compaction, and whenever the main tree's reds change.

## Heavy work elsewhere

- A program is heavy by what it is, not by what an agent typed. Every line an agent runs carries the heavy-command table down ([`heavy-commands.ts`](../../_sandbox/sandbox/src/system/resources/heavy-commands.ts)): each node program it starts loads a hook first ([`heavy-hook.cjs`](../../_tools/constants/src/heavy/heavy-hook.cjs), through `NODE_OPTIONS`), and pnpm's own binary, bun and cargo are reached through thin wrappers first on its PATH (`bin/heavy-shims`). Both name the program that really runs (`vitest` under `pnpm test`, `tsc` under a make target) and match `<program> <args…>` against the table ([`heavy-rules.cjs`](../../_tools/constants/src/heavy/heavy-rules.cjs), which the repository's own scripts read too). A heavy program takes the toolchain class at once, then becomes the same run behind `bin/queue-run` (a slot, and memory first); nothing it starts is judged again. Switching the queue off leaves the class. `bin/tmux-run` ends everything a command started, in every process group, when it returns.
- `.intentic/config/heavy-commands.json` holds only the owner's overrides (settings, edits to a shipped rule by its id, the owner's own rules, `queue: false`), on top of the shipped table, so a fix to a shipped rule reaches every sandbox. A file of the earlier shape (the whole table, seeded once) is converted on read into what differs from anything a release shipped. A slot held past half of its own rule's max-hold is named in the daemon log.
- An agent's command reaches its pane by file: the hook writes the line, the command and its window name into a run directory and hands `tmux-run -f <dir>/line`, so no process's command line carries the agent's words and `pkill -f` on a pattern in them cannot kill its own call.
- The owner can send a kind of heavy work, and the check after landing, to a runner on one of their machines instead (settings `offload`, Agent → Tools → Where heavy work runs). A heavy program of such a kind becomes `bin/offload-run` as it starts, and [`verify-deps.ts`](../../_sandbox/sandbox/src/workspace/deps/verify-deps.ts) puts it in front of the check; both keep the queue's own prefix for when the runner cannot take it.
- `offload-run` snapshots the repository's working tree as one commit under `refs/intentic-offload/<run>`, uncommitted and untracked work included, and relays the run through [`offload.routes.ts`](../../_sandbox/sandbox/src/offload/offload.routes.ts) to the runner. The runner fetches it through the git door into `/history/offload/<repo>` ([`runner-command.ts`](../../_sandbox/sandbox/src/runners/runner-command.ts)), which it keeps between runs with its ignored files, reinstalls only when a lockfile or manifest moved, runs the repository's `offload:prepare` script when the tree changed, and runs the line behind its own queue. Output streams back as it comes; the exit brings every file the line changed as a patch, and the files it wrote to the variables asked for (the check's report, its tree verdict).
- A runner that is offline, predates offloading, stays full, or cannot fetch or install hands the line back, and it runs here with one line saying why. A line that resolved a secret never leaves.

## Priority and memory

- Every process the daemon starts for a purpose gets a workload class from whoever started it, never from its command line ([`workload-class.ts`](../../_sandbox/sandbox/src/workload/workload-class.ts)). The class sets its niceness, its IO class and its `oom_score_adj`, and children inherit all three, so the whole tree carries it. When memory runs out the kernel takes, in order: builds a heavy-command rule matched and the check after landing (800), agent commands and dependency installs (600), services, gateways, backends and panels (500), then agent runtimes, 100 plus 100 per spawn level, so a child goes before its parent. The daemon and whatever it starts without a class stay at 0.
- `spawnAs` applies the class in the same call that spawns the child: runtimes (Claude, Codex, ACP, pi), service processes, the translator, the extension and browser backends. The iq engine is classed as it forks, and `opencode serve`, which its SDK spawns with no hook, is found by a stamp set across that spawn. A pane shell (a panel, an install, the check after landing) is classed before the command is typed into it. An agent's command gets the command class as a shell prefix (`nice`, `ionice`, `choom`) inside `tmux-run`, and a heavy program within it takes the toolchain class as it starts. The front still lowers every direct child of the daemon to nice 10 and never raises one: it is the floor for the plain spawns that have no class (the git fork broker, rules, runner commands, the JS tool). Process metrics still label processes by command line ([`process-scan.ts`](../../_sandbox/sandbox/src/system/resources/process-scan.ts)), and that label ranks nothing.
- Whether there is room for more work is one formula ([`memory-room.mjs`](../../_tools/constants/src/memory-room.mjs)): the limit is `memory.high` (the entrypoint sets it to 90% of the cap, and past it the kernel throttles the whole sandbox into reclaim), else `memory.max`, else the machine's memory; used is the working set plus swap (the machine's own figures at a root cgroup, which keeps neither); free never exceeds what the machine has available; the stall is memory pressure `full`. Starting one more of a class needs its cost free (an agent runtime or a build 1 GiB), and work nobody waits on needs a person's turn on top.
- The daemon's [`ResourceBudget`](../../_sandbox/sandbox/src/workload/resource-budget.ts) is the only judge. One sampler takes the reading (every ten seconds, and fresh within a second when asked), and one ledger holds what admitted work takes for ninety seconds, until the reading shows it, keyed by where the work runs: a child sent to a runner holds nothing here and never waits on this box. `admit` answers run, wait or refuse. A person on a short box is told once a spell and then let through. A turn nobody waits on (a child, an automation) is held at the door until there is room, for up to ten minutes, and then turned away. A child is admitted while it shows as waiting, and the door takes that admission instead of judging the same turn again.
- `GET /system/metrics` serves the budget's snapshot: the gauge's used and limit are the gate's, and it turns amber exactly where a person's turn would be held (below the free memory that turn needs, or at the stall limit). A killed child is blamed on memory when the OOM count moved or the sampler saw the box short in the last five minutes.
- Heavy commands and test fan-outs ask the budget on a Unix socket of their own, `/run/intentic/room.sock` ([`room-socket.ts`](../../_sandbox/sandbox/src/workload/room-socket.ts)), never the daemon's public socket: `bin/queue-run` runs `memory-room --class toolchain --wait N` before it takes a slot, and `test-workers.mjs` sizes itself to the free memory the budget reports. Where no daemon answers (CI, a plain checkout), both apply the same formula to the same files.

## State

| Place | Holds |
| --- | --- |
| `/work` | the repositories, visible to agents, on its own volume |
| `.intentic/config` | tracked configuration: settings, personas, skills, capabilities, the environment overlay |
| `.intentic/records` | ledgers: agent sessions, land verdicts, chores |
| `.intentic/local` | rebuildable caches and browser profiles |
| `.intentic/identity`, `.intentic/secrets` | owner, members and passkeys; credentials |
| `/history` | the conversation store, transcripts, worktrees, git directories, snapshots and logs |

`/history` is a separate volume outside `/work`, so no command in the workspace can erase the recovery record. [`workspace-state.ts`](../../_shared/sandbox-contract/src/state/workspace-state.ts) lists every state file and its group, and the file API refuses the daemon's own entries.

Every stored file is read by every later release, from sandboxes that skipped any number of them. Each is declared with the conversions its shape has had ([`documents.ts`](../../_sandbox/sandbox/src/store/evolution/documents.ts)); the stores run them on every read and keep what they do not know on writes, so a store's next save persists the converted shape, and the first boot after an update moves documents and runs structural steps under a journal a rolled-back build undoes ([`state-convergence.ts`](../../_sandbox/sandbox/src/store/evolution/state-convergence.ts)). The promise and the rules for a change are in [COMPATIBILITY.md](../../COMPATIBILITY.md#stored-data).
