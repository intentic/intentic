# Testing notes for intentic itself

These notes are appended to every acceptance brief for this repository. They exist because the app under test is the same kind of thing as the tester: an agent walking intentic can start other agents, spend money, hand out credentials and land code. Read all of it before the first click.

## Two applications, one repository

The stories are grouped by where the user is in their journey, and the first group is not the same application as the rest.

- **`01-arrive/`** is the marketing site (`_site/site`, an Astro dev server). Its stories are walked against the site's own address.
- **Every other group** is the web application (`_editor/web`). Signed-in, and the address the run gives you.

A run resolves one address per group, so both can be covered in one run — but only if whoever started it aimed each group at the right server. **Check the base URL you were given against the group your story is in before deciding anything is broken.** A marketing-page story that lands on a sign-in screen has been pointed at the app; record that as `blocked`, name it, and stop.

## Signing in

The web app requires a session. A fresh browser has none, so **your first act on an app story is to sign in** at `/login` with the acceptance account for this environment. If no such account has been provisioned, that is not something to work around: record the story as `blocked`, with "no acceptance account" as the wall you hit, and stop. Do not sign up, do not reset anyone's password, and do not attempt to reach the API directly to mint a session.

Stories in `01-arrive/` are public pages and need no session at all.

## Setup stories, without setting anything up

`02-setup/` describes a flow that creates and destroys real infrastructure. You are not to create or destroy any of it.

- The setup flow can be **resumed for a sandbox the account already owns** — `/setup?sandbox=<id>`, where the id comes from the account's own sandbox switcher. That renders the real steps for a real sandbox, which is what those stories are about, without a sandbox being created.
- **Never press Create on a new sandbox**, never delete one, and never run any command you are shown. Copying a command to read it is fine; pasting it into a terminal is not.
- The attach lane probes an address you type. Probing an address that is obviously not a sandbox is a legitimate part of the story — that is how its error states are tested. Do not point it at anyone's real infrastructure.
- If a criterion genuinely cannot be exercised under these limits, mark that one criterion `untested` with the reason and carry on with the rest. Do not mark the whole story `blocked` for it.

## Capabilities, credentials and money

`03-equip/` walks the capability catalog. Most of what those stories promise is legible **without connecting anything**: the card, its description, the credential guide and its scopes, the fields, the validation, the disclosure of what will be added, and the state of connections that already exist.

- **Do not submit a capability form** unless these notes have been amended to name a throwaway credential for that provider. Reading, filling and validating a form is expected; applying it is not.
- **Do not remove a capability**, and do not confirm a removal dialog. Opening it to check that it asks is fine — then cancel.
- **Do not reveal, copy or quote a secret's value** anywhere in your report or your screenshots. That a secret exists and is masked is the finding; its value never is.
- **Do not sign in to, or out of, an AI provider account.** Those are real subscriptions, and signing out costs the owner the sandbox's ability to run.
- The final criterion of most capability stories is "the agent can actually use it". Where a connection already exists you may exercise it with a single trivial, read-only request. Where it does not, mark that criterion `untested`.

## Agents and blast radius

Several stories ask you to start an agent. That is real: it runs a real model against a real provider and it costs real tokens.

- Start **at most one** agent per story, give it a trivial task ("print the current date"), and pick the cheapest model offered.
- **Stop and discard the agent you started** before you finish the story. Leave the board as you found it.
- Never act on an agent you did not create — no landing, no discarding, no archiving, no renaming. Other people's work is running on this board.
- Never press "Delete all" in the archive. It is the one irreversible action in the product.
- Do not create or destroy sandboxes, and do not connect capabilities except as allowed above.

## Reading the app

- The surfaces these stories start from are `/login` and `/setup` (outside the workspace shell), and inside it `/agents` (the fleet board), `/capabilities`, `/sandbox/<tab>`, `/workspace` and `/ext/acceptance`. The rail on the left reaches the ones inside the shell.
- Much of the UI updates by polling rather than on navigation. When something has not appeared yet, wait and re-snapshot before calling it a defect — but say in the report how long you waited.
- The chat panel is docked beside the middle column on a wide window and is a separate screen on a narrow one. If a story's flow seems to be missing, check the viewport width before reporting it.
- A sandbox that is offline makes most of the workspace unreadable. That is a wall, not a defect in the story you were given: record `blocked` and say the sandbox was unreachable.
