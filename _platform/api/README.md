# @intentic/api

The **platform backend**, Hono + oRPC + Prisma + Better Auth. The platform is an **identity + sandbox-URL store**: it authenticates the user (Google) and stores the sandbox URL the browser tells it so the browser can reach the sandbox directly. It never probes the sandbox or tracks liveness and owns no infrastructure; it sits **off the command path with exactly one exception** (the free trial ([src/trial/](src/trial/))) and the browser otherwise talks to the sandbox daemon directly over the sandbox's own tunnel. Runs under `tsx` in dev on :6480 (the web dev-server proxies to it). Consumes [`@intentic/api-contract`](../../_shared/api-contract) (`implement`) + [`@intentic/prisma`](../../_platform/prisma).

## Responsibilities

- Authenticate the user (Better Auth + Google) and expose the typed oRPC surface (`me`, `setup.*`).
- Mint the per-user connection token + serve the setup one-liner. The workspace gate is enforced in the browser, which probes the daemon's `/health` directly: the platform never decides liveness.
- Store the sandbox's public `daemonUrl` the **browser** derives (`sandbox-<sha256(token)[:12]>.<zone>`) and writes (`setup.bind`), and serve it back (`setup.binding`) so the browser knows where to reach it. Persist nothing else about the sandbox.
- Serve the **free trial** ([src/trial/](src/trial/)): an OpenAI-compatible model API on intentic's own free-tier keys, so a user can chat before connecting any AI account. Metered per signed-in account per UTC day (`TrialUsage`), authenticated by the sandbox's connect token. It publishes **one synthetic model id** and picks the real model per message from a curated ladder ([trial-ladder.ts](src/trial/trial-ladder.ts)), discovery may only remove rungs from that ladder, never add to it, because Google declares `generateContent` for models that cannot serve an agent turn. The pool walks **(key, model) pairs** under one deadline, since quotas are metered per model: bounded header timeouts, short refusal quarantines, failover across both dimensions. A refusal is read as a fact about the credential and the walk moves to the next key; **silence is read as a fact about the rung**, which ends that rung's walk and cools the model for five minutes, because a model the upstream has stopped serving hangs identically on every key and discovering that key by key spends the whole deadline before the fallback rung is ever reached. Unsuccessful completions are refunded, `/trial/status` reports the health observed by real chat traffic and the model that last answered this account. **Health is a statement about the walk the caller just made**: a quarantine is a window nothing used to prune, and the ladder's capability listing rides the same pool under no model at all, so health read off the sideline maps made one 429 — on one key, or on a `models` GET no user was waiting for — a standing "degraded" for everybody on the platform, printed over answers that had arrived on the first attempt. **Off by default**, no `TRIAL_KEYS`, no trial.
- **Hold the keys a sandbox must not** ([src/wallet/](src/wallet/)): a sandbox agent can pay x402-charging endpoints in USDC, and the container it runs in is not a key boundary (its daemon and its agent are one root process tree), so the wallet lives here, one per account per network, owner-scoped and never pooled, with the key itself held by a custody provider ([wallet-custody.ts](src/wallet/wallet-custody.ts)) so the platform stores no key material either. Every signature is checked against **this** database rather than against anything the sandbox claimed: the wallet is the caller's, the token is USDC, the stated amount matches what the authorization moves, the validity window is short, and the per-payment ceiling and UTC-day cap both hold, the day's row is written inside the same serializable transaction that reads the day's total, so two turns cannot race one budget. The sandbox's own checks are the UX; these are the guarantee. **Off by default**, no `WALLET_CUSTODY_URL` + `WALLET_CUSTODY_KEY`, no wallet.
- Run the **push relay** ([src/push-relay/](src/push-relay/)): APNs forwarding for the iOS shell ([\_editor/ios-app](../../_editor/ios-app)), the one notification path that cannot go direct, Apple only accepts pushes from the app's vendor, so the daemon posts plain JSON here and the relay signs it on to APNs ([apns.ts](src/push-relay/apns.ts)). The capability model keeps both sides minimal: the signed-in app registers the device token and gets back `{deviceId, secret, url}`, which it stores on the DAEMON as the channel; a send is sessionless and proved by the secret alone (stored hashed), so the relay never learns which sandbox is calling and the daemon never holds an Apple credential. Refusals speak the daemon's own dead-channel codes (403/404/410) so its pruning works unchanged, and a notification's title/body pass through **readable**, the stated privacy trade against web push's end-to-end encryption; the payloads are pointers back into the workspace by design, never content. Android needs none of this: the Play app is a TWA riding ordinary web push. **Off by default**, no `APNS_KEY_P8`, no relay; the routes 404 and the shell reports notifications unsupported.
- Sell the **hosted plan** ([src/sandbox/hosted/hosted-plan.ts](src/sandbox/hosted/hosted-plan.ts)), the one paid thing on the platform ([docs/design/pricing-model.md](../../docs/design/pricing-model.md), [docs/design/billing-view.md](../../docs/design/billing-view.md)): a Stripe subscription (checkout, portal, webhook; Stripe stays the money's source of truth, `HostedPlan` is the local mirror) that makes the owner's hosted sandboxes always on and never collected, **one slot per hosted sandbox**: the subscription item's quantity is how many the account may have (`hostedSlotsOf`, read by the provision gate), written by the platform itself through `hostedPlan.setSlots` with Stripe's proration and refused below the number of machines standing. The mirror carries `cancelAtPeriodEnd` (the portal's cancel leaves the status active until the period ends, and the Billing page says "ends" rather than "renews"), and **no event's copy of a subscription is ever mirrored**: Stripe delivers events in no particular order, so the event names the subscription, its state is read fresh, and `syncedAt` (the platform's own clock at that read) is what a later write must beat, one clock on both sides of the comparison. Out-of-order delivery therefore cannot roll the row back, and neither can an event that arrives in the same second as a write of ours, which is what comparing our milliseconds against Stripe's whole-second `created` used to do (docs/design/billing-e2e.md). Checkout refuses an account already on the plan (a second subscription would charge invisibly) and reuses a resubscriber's Stripe customer. **A deleted account's subscription is cancelled with it** (`cancelHostedPlan`, before the cascade, from Better Auth's `deleteUser` hook and the admin erasure alike): it is the one thing about an account that is not a row of ours. `HOSTED_PLAN_COMP_EMAILS` grants the plan without a subscription (the free lane's slot count, always on). Nothing else reads it: every feature is in the free product, and money changes whose machine the agents run on, never what they can do. **Off by default**, no `HOSTED_PLAN_STRIPE_SECRET_KEY` + `HOSTED_PLAN_STRIPE_PRICE_ID`, no plan.
- Run the **hosted lane** ([src/sandbox/hosted/](src/sandbox/hosted/)) and **pay for what it costs**: one Fly machine + volume per sandbox on intentic's own credential, reached with no tunnel at all — the machine declares its front door as a Fly service and the edge answers requests for its hostname with a Fly replay to its app, so its env carries no grant and no edge address — and the two mechanisms that stop a free machine costing forever. **Awake hours** ([hosted-usage.ts](src/sandbox/hosted/hosted-usage.ts)) are metered per owner per calendar month (`HostedUsage`) against `HOSTED_MONTHLY_HOURS`, **live**: the used figure is the settled row plus the open stretch of every machine of the owner's that is up right now, so a machine awake for 39 hours no longer reads as 40 left. Enforced **at wake**, and past a grace by the hourly meter tick ([hosted-meter.ts](src/sandbox/hosted/hosted-meter.ts)): the machine stops from the inside (the daemon's idle-stop, decided by probes the owner is root over), and a machine that never stopped used to be one that was never charged, so forty free hours meant forty hours of stopping; the tick settles stopped stretches and stops a metered owner's running machines once the month is spent by more than `HOSTED_OVER_BUDGET_GRACE_MINUTES`, after the editor's meter has read zero and its strip has said so. An owner on the hosted plan is exempt entirely. The platform stamps the start of every stretch because it performs every wake, and closes it later by asking Fly when the machine stopped, since the machine sleeps from the inside and tells nobody. **Idle collection** ([hosted-idle.ts](src/sandbox/hosted/hosted-idle.ts)) destroys the machine and disk of an owner who is not on the plan after `HOSTED_IDLE_DAYS` unopened, one warning email earlier, never taking a machine that is currently running (`Sandbox.lastSeenAt` is a BOOT announce, so a long-running box reads as untouched) and never taking a machine whose owner is on the plan. The idle sweep rides the daily [retention.ts](src/retention.ts) job; the meter's settle rides its own hourly tick. A **warm pool** ([hosted-pool.ts](src/sandbox/hosted/hosted-pool.ts)) can pre-build `HOSTED_POOL_SIZE` machines per region so a claim writes the sandbox's env into one and starts it in seconds instead of pulling the image on demand. A pool machine's one boot is the daemon's own **prewarm** (`SANDBOX_PREWARM=1`, the daemon's `platform/prewarm.ts`): it pulls the image AND prepares the volume, the workspace repo, the starter site with its dependencies, the baselines, one run of the starter's dev server for its caches, then exits 0 and stops, holding no owner, so the owner's first boot finds every step already done and the starter serving in seconds. **The write IS the start**: replacing a machine's config takes it through Fly's `replacing` state, which refuses every start for a few seconds, so a claim that held the launch back and started the machine itself lost that race every time, refused 100% of claims, burned both warm machines of the caller's region per sign-up, and handed every reader the exact cold build the pool exists to spare, the launch therefore rides with the config and the claim's own start is only a confirmation. A claim that is refused moves to the next warm machine and only an exhausted pool falls back to the cold build, since a single dead row must not cost a reader the very minutes the pool exists to spare — with one refusal that stops the loop dead instead, because trying again cannot help: **this sandbox already has a machine**. `HostedMachine.sandboxId` is unique and the route's "does it have one" check is a read with no lock behind it, so two overlapping provisions (a second tab, a retried request, the desktop app beside the browser) both get past it and one loses its row-write. Read as "bad warm machine", that refusal branded, started and stranded every ready machine in the caller's region one at a time, for a sandbox that already had one; so the loser asks the database whose it is, abandons the claim, and the route answers with the winner's machine rather than a gateway error about a sandbox that is by then perfectly hosted. A five-minute reconcile, nudged immediately after every claim, so a spent slot starts rebuilding without waiting out the tick, keeps the pool at size (a small stock per region by default), **re-checks that every standing row still has a machine on Fly** (a row is a claim about a machine, not proof of one, and Fly's 404 is the only answer treated as death, a provider that cannot be asked is asked again next tick rather than drained), rebuilds it when the image moves, and drains it when switched off. **"The image" means the digest, not the tag**, and the difference is not pedantry: a row used to record the configured tag, so the reconcile compared a tag against the same tag and could never see drift, while a claim's config replacement handed Fly that tag again — which, after `sandbox:stable` is re-pushed, resolves to a *different* digest, so the machine had to pull a fresh rootfs before it could start and the thirty-second settle window expired long first. Measured: one re-push, then four claims, four `did not start after its config was replaced`, and four sign-ups paying the full cold build the pool exists to spare. [hosted-image.ts](src/sandbox/hosted/hosted-image.ts) now resolves the tag against the registry (cached per minute, **failing open to the tag** so a registry outage costs only what today costs), a row stores the digest its machine actually pulled, and a claim boots *that* digest — so a claim cannot change what the machine is holding, and therefore cannot make it pull. Drift becomes ordinary background work: a push drains the superseded stock and rebuilds it on a tick, with nobody waiting on it. **A pool machine has an identity before it has an owner.** The edge reaches a hosted sandbox by replaying to the app named `<prefix>-<sandbox id>` with no lookup, and Fly lets neither an app nor a machine be renamed, so the name has to be right at build: the pool mints a connect token per machine, names the app after its digest, keeps the token in the row (`HostedPoolMachine.token`, never in the stopped machine's env), and the claim writes the sandbox's row over to that identity — token, digest and `tunnelId` — in the same transaction that hands the machine over. Stock from before identities existed carries an empty token and is replaced. Pool-born and built-to-order apps are therefore named alike, and the Fly console's app list can never tell stock from a person's sandbox: every machine carries a Fly **metadata stamp** of what it currently is (`intentic_role`, rewritten with the config at claim, the one label the provider can be asked about and filtered on) **and whose it is** (`intentic_owner`, the owner's email): every other stamp is an id, so "who is this machine costing money for?" — the question somebody asks with a Fly bill in front of them and no database — used to need a join, and now does not. Warm stock deliberately carries no owner, which is also how the console tells stock apart from a person's sandbox. New and re-configured machines carry it; `pnpm --filter @intentic/api fleet --stamp` backfills the ones built before it existed, writing one metadata key per machine so nothing is restarted or woken, `HostedMachine.warm` remembers which origin a machine had, and `pnpm --filter @intentic/api fleet` ([hosted-fleet.ts](src/sandbox/hosted/hosted-fleet.ts)) prints the readable version by joining Fly's app list against the platform's own rows: taken (with owner), warm, claiming, orphaned. The provisioner also puts the platform's Ed25519 **public key** into every hosted machine's env (`PLATFORM_PUBLIC_KEY`), which is what lets a hosted daemon accept the **owner ticket** `sandbox.ownerTicket` mints (sandbox-contract's `owner-ticket.ts`): a minutes-long claim, signed with the reachability key, that the browser spends on the daemon's session exchange instead of a second Google sign-in; hosted machines only, owner only, the trust argument is in the contract module. **And the lane can run out**, because a Fly org's machine allowance is finite and the provider enforces it the only way it can: by refusing a create while somebody is watching a page for their first sandbox. [hosted-capacity.ts](src/sandbox/hosted/hosted-capacity.ts) makes that knowable *before* the button — the platform counts its own machines (sandboxes, warm stock and any builder in flight) against `HOSTED_MAX_MACHINES`, remembers a provider refusal for a few minutes **per region** (an org allowance is global; a region out of hardware is not, and the residency split means one must not speak for the other), and answers `hostedOffer.full`, which is what stops a browser arrival starting a machine it cannot get. Warm stock outranks both counts: claiming creates nothing, so a fleet sitting exactly on its ceiling still serves the next arrivals in seconds, while the pool stops prewarming and leaves the room for people. A provision that meets it anyway answers `SERVICE_UNAVAILABLE` with a sentence about machines rather than `BAD_GATEWAY` carrying Fly's own words, an overlay build refuses with `capacity` (its owner's sandbox is untouched), and the health watch mails the admins, because the remedy is a raised allowance and only a person can do that. **Off by default**, no `HOSTED_FLY_API_TOKEN`, no hosted lane.
- **Build the environment overlay a hosted sandbox approved** ([hosted-build.ts](src/sandbox/hosted/hosted-build.ts)), the lane's `ic sandbox rebuild`: a docker host's owner runs that themselves, a hosted sandbox has no host, so the platform builds the same bytes on a **builder machine** it creates inside the sandbox's own Fly app (buildkit, the recipe delivered as `files`, [hosted-build-script.ts](src/sandbox/hosted/hosted-build-script.ts)), pushes to that app's registry path, and replaces the sandbox machine's config with the image pinned by digest plus `SANDBOX_ENVIRONMENT_HASH`, the same replacement a restart is, volume intact; a stopped machine is left stopped and boots it on its next wake, so a build is never a way around the wake gate. The browser sends the approved content with its hash and the platform re-hashes it, pins the `FROM` to `HOSTED_IMAGE` and lints the rest to RUN/ENV (sandbox-contract's `overlay-lint.ts`), so only reviewed bytes are built. **Every build spends the platform's money on whatever RUN steps the recipe carries, and accounts are free to make**, so the brakes come in pairs: owner-only, from a session (nothing holding the connect token can start one); one build in flight per sandbox, won by a conditional update on the machine row; `HOSTED_BUILDS_PER_DAY` per owner with `HOSTED_BUILD_CONCURRENCY` and `HOSTED_BUILD_MINUTES_PER_DAY` platform-wide behind it; **builder minutes charged to the owner's month like awake minutes** and refused up front when fewer than the timeout remain; `HOSTED_BUILD_TIMEOUT_MINUTES` enforced by the script's own `timeout` and again by a per-minute reconcile that force-destroys what outlives it; a shared-CPU guest by default (`HOSTED_BUILDER_CPU_KIND`), worth nothing to anyone mining on it. The only credential in a builder is a deploy token scoped to the sandbox's app, minted per build through Fly's GraphQL ([fly-tokens.ts](src/sandbox/hosted/fly/fly-tokens.ts), the one call outside the Machines API) and revoked when the builder reports, and the reconcile keeps every building app to one sandbox machine and one builder, destroying anything else. The builder reports its exit, digest and log tail to `POST /sandbox/hosted-build-report/:id` under a per-build secret; the reconcile is the fallback for one that never does. `HOSTED_BUILDS_PER_DAY=0` turns the feature off.
- **Whose machine is whose, and what happens when one disappears.** The same stamp carries `intentic_platform` — a hash of this deployment's API URL **and its database's host/name** (`HOSTED_INSTANCE_ID` overrides it), so replicas and redeploys share one identity while a copy of the env file on another box gets its own, because it cannot reach the same Postgres; the URL alone would not have separated them, since a copied env file is how a laptop had the token in the first place. The orphan reaper destroys **only** apps that carry this deployment's stamp: a Fly org is shared by everything holding its credential, an app name says nothing about who made it, and a sweep that destroys every app its own database cannot explain will destroy another deployment's entire fleet. That is not a hypothetical, it is how every production machine was lost in one pass, each leaving behind the row that described it. Four rules make the sweep unable to repeat it: **ownership** (an app whose machines carry a foreign stamp, or no stamp at all, is left standing and reported, never collected), a **grace period** (a provision in flight owns Fly resources for minutes before its row exists), **emptiness as evidence** (an app holding no machine has no stamp to be proved by, so it used to stand forever — unprovable, relogged nightly, and counted as a stranger by the health watch on a schedule nothing could clear; a machine is the only thing that runs in an app, so past the grace window and with no row behind it there is nobody whose sandbox it could be), and a **circuit breaker** (a pass that wants to destroy more than a quarter of the fleet refuses outright and says so, because every way a database can be wrong reads to a reaper as "destroy everything"). The other half is recovery: a machine the provider no longer has now reports as `gone` rather than `unknown` ([hostedStatus](src/sandbox/sandbox.routes.ts)), the setup card says so in as many words, **`hostedRestart` builds a replacement** instead of failing forever on a row that can never be refreshed, and both the hour meter and the idle sweep settle and drop such a row rather than throwing on it nightly (it also held the owner's one-machine allowance, so they could not be given another).
- **Knowing before a user does** ([hosted-health.ts](src/sandbox/hosted/hosted-health.ts), [hosted-canary.ts](src/sandbox/hosted/hosted-canary.ts)). Every sweep above ACTS on the gap between the platform's rows and Fly; nothing watched the gap itself, so the outage above was visible only as one warning per machine per night. The health watch (`HOSTED_HEALTH_MINUTES`, read-only) reports rows whose machine has vanished, apps running a machine stamped by a **different** deployment — the *cause*, visible before anybody's machine is lost — row-less apps as **litter** (said out loud, never mailed, never counted against healthy), and warm stock against target, at `error` level and to `ADMIN_EMAILS`. Stranger and litter are two numbers rather than one because conflating them is what stopped this watch being read: an ordinary failed provision mailed the admins "another deployment is sharing this Fly org", which was not true, every six hours, about a fault no action could clear, so whose an app is gets asked of the provider with the same code the reaper judges by. It cannot, however, see a lane that is intact but no longer **works**: an image that stopped booting, a grant the hub refuses, a region out of capacity all look perfect from here and show up only as people who never arrive. So the canary (`HOSTED_CANARY_MINUTES` + `HOSTED_CANARY_EMAIL`, **off by default**, it spends a real machine per run) provisions a sandbox on the real path, waits for the same daemon check-in a person waits for, and destroys everything it made in a `finally` — except when the lane is **full**, where it stands down instead: on a fleet at its ceiling the canary's machine and the next person's are the same machine, and a run that failed to get one would mail "provisioning is broken" about a platform that is merely out of room. Being full is the health watch's alarm, and the one it mails about even though short warm stock alone never is: a pool that cannot fill is ordinary weather, a fleet that has reached its allowance is every new sign-up being turned away and no tick will fix it.

## Routes (see [src/app.ts](src/app.ts))

- `/api/auth/**`: Better Auth (Google OAuth redirect, the browser-minted Google ID token at `one-tap/callback`, session).
- `${API_BASE_PATH}/*`, the oRPC OpenAPI handler ([src/router.ts](src/router.ts): `me`, `setup.connect`, `setup.zones`, `setup.bind`, `setup.binding`). `bind` stores the browser-derived `daemonUrl`; `binding` reads it back.
- `/trial/*`: the free trial's model API (`/trial/status`, `/trial/v1/models`, `/trial/v1/chat/completions`), authenticated by the sandbox connect token. 404s entirely when `TRIAL_KEYS` is unset.
- `/hosted-plan/webhook`, Stripe's webhook for the hosted plan ([src/sandbox/hosted/hosted-plan.routes.ts](src/sandbox/hosted/hosted-plan.routes.ts)), signature-authenticated. The browser half (plan state, checkout, portal) rides the oRPC contract under `hostedPlan`. 404s entirely when the plan is unconfigured.
- `/wallet/*`, the agent wallet's signer ([src/wallet/](src/wallet/)), connect-token authenticated: `POST /wallet/ensure` create-or-return this account's USDC wallet (its address, never its caps: those are written only over the owner's session, `wallet.setPolicy`, from the editor as the card is saved, because a number the sandbox could set is no ceiling on the sandbox), `POST /wallet/sign` mint one EIP-712 signature over one fully-specified EIP-3009 transfer. 404s entirely when `WALLET_CUSTODY_URL` + `WALLET_CUSTODY_KEY` are unset.
- `/rpc/admin/*`, the **operator's surface** ([src/admin/](src/admin/)), rendered by the private `platform-admin` workspace extension riding the browser's own session. The reads: overview counts, the activation funnel + time-to-activate ([admin-funnel.ts](src/admin/admin-funnel.ts), off `Sandbox.firstAnnouncedAt`), the red-rows attention feed — stuck setups, unreachable sandboxes, announce refusals, past-due plans, lingering pool claims and stale builds, composed into sentences server-side ([admin-attention.ts](src/admin/admin-attention.ts)) — the hosted/trial cost meters ([admin-costs.ts](src/admin/admin-costs.ts)), 90-day trend lines off the daily rollup ([admin-trends.ts](src/admin/admin-trends.ts)), a searchable account directory, and a per-account support page ([admin-user.ts](src/admin/admin-user.ts)). The daily retention sweep also writes the rollup row (`AdminDailyStat`, [admin-rollup.ts](src/admin/admin-rollup.ts)) and mails the attention feed to the admins once per UTC day when it is non-empty ([admin-digest.ts](src/admin/admin-digest.ts)). The **mutations** ([admin-actions.ts](src/admin/admin-actions.ts): stop a hosted machine, GDPR erasure with the owner-flow teardown) sit behind a second deployment switch `ADMIN_MUTATIONS` (off by default — the panel's bytes are workspace-authored until pinned) plus a typed retype-the-target confirmation per call. Everything answers FORBIDDEN for everybody when `ADMIN_EMAILS` is unset. Every handler opens with `requireAdmin` ([src/guards.ts](src/guards.ts)) — the session email checked against the `ADMIN_EMAILS` allowlist (deployment config on purpose: no endpoint can mint an admin) — and is audit-logged with the caller's email. Read-only by design while the panel's bytes are workspace-authored. Answers FORBIDDEN for everybody when `ADMIN_EMAILS` is unset.
- `/health`: DB connectivity.

- [src/app.ts](src/app.ts): the Hono app factory + all route wiring; [src/router.ts](src/router.ts) + [src/context.ts](src/context.ts), oRPC.
- [src/auth.ts](src/auth.ts): Better Auth (Google sign-in + the desktop one-time-token handoff). Sign-in has

  this platform: so only a credential the browser holds can serve both, and asking for Google twice was
  costing sign-ups. It makes the platform a second CONSUMER of that credential, never its issuer.

## Conventions & gotchas

- The platform is **off the command path except for the free trial**: there is no relay, no socket to the sandbox, and no sandbox-originated calls other than the daemon's announce and its trial probe. The browser calls the sandbox daemon directly (authenticated by the user's Google ID token); the platform only holds the stored URL. Trial turns are the one thing that passes through, they are labelled as such in every surface that offers them ([`TRIAL_NOTICE`](../../_shared/sandbox-contract/src/models/agent-catalog.ts)), and connecting any account takes the user off that path for good.
- **Four documented secret exceptions**, all intentic's own credentials and all optional: `INTENTIC_CLOUDFLARE_API_TOKEN` (DNS in intentic's own zone: the loopback wildcard, the ACME challenge beside it, and the sweep — no tunnels, no per-sandbox records), `TRIAL_KEYS` (the free-trial pool), `HOSTED_PLAN_STRIPE_SECRET_KEY`/`HOSTED_PLAN_STRIPE_WEBHOOK_SECRET` (the hosted plan's Stripe account), and `APNS_KEY_P8` (the push relay's Apple key (the narrowest: only notification titles/bodies pass through). Everything else) Claude/git tokens, SSH keys, the user's Cloudflare, lives in the sandbox.
- `setup.connect` returns only the connection token + the connect-script URLs. The sandbox's public URL is **derived deterministically** from that token + the chosen zone (`sandbox-<sha256(token)[:12]>.<zone>`, the same id the sandbox's reachability grant names) and written by the browser via `setup.bind`: the sandbox never calls the platform.
- `GET /api/reachability/:id` answers the edge two things at once: whether the sandbox still exists (404 is the revocation) and which lane it is on — `hosted`, with the Fly app to replay to, or `tunnel`. Unauthenticated on purpose; the id is the leading label of every URL the owner has ever shared.
- Config is nested + SCREAMING_SNAKE-derived by `@puristic/env`; secrets are plaintext in the DB for now.
- Tests: colocated vitest suites (`pnpm test`), plus two gated tiers for the one thing this plane sells. `pnpm e2e:hermetic` runs [hosted-plan.e2e.test.ts](src/e2e/hosted-plan.e2e.test.ts), the whole money path (real app, Postgres testcontainer, Stripe stood in for) on every merge request; `pnpm e2e` runs [hosted-plan-stripe.e2e.test.ts](src/e2e/hosted-plan-stripe.e2e.test.ts), the Stripe client against Stripe's test mode, nightly, when `HOSTED_PLAN_E2E_STRIPE_SECRET_KEY` + `HOSTED_PLAN_E2E_STRIPE_PRICE_ID` are held ([docs/design/billing-e2e.md](../../docs/design/billing-e2e.md)).
